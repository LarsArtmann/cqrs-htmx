00What I Got Wrong in v1

Brutal honesty. The first report was directionally correct but missed major reuse opportunities and had type-safety violations.

Critical miss · Massive reuse opportunity

Did not discover templ-components has a full dashboard component library

templ-components/ (already a dependency of adminui!)

The v1 report proposed building CSS and components "following the adminui pattern" — implying we'd hand-build tables, stat cards, badges, pagination, layouts. But templ-components already ships all of this: recipes.Dashboard (full dashboard shell), layout.AppShell (sidebar + header + content), display.DataTable (sortable, paginated tables), display.StatCard (metric cards with trend), navigation.Pagination + navigation.LoadMore (cursor pagination), display.RelativeTime (live timestamps), display.CopyButton, display.Modal (confirm dialogs), display.StatusBadge, display.EmptyState, display.DefinitionGrid (metadata), forms.FilterDropdown, and 100+ icons including CQRS-relevant ones (QueueList, Bolt, ArrowPath, BugAnt).

Fix The dashboard should COMPOSE templ-components, not build parallel components. Only a JSON viewer needs to be built from scratch (no component exists for that).
Critical miss · Wrong implementation path

Only mentioned InMemoryStreamReader — missed the SQL-backed reader

storage/sql_aggregate_reader.go

v1 proposed auto-creating InMemoryStreamReader from the journal. But go-cqrs-lite already has storage.SQLStreamReader — a proper SQL-backed reader that queries a projection table (StreamProjection) with server-side filtering by type, tombstone status, and cursor pagination. This is production-grade, not a fallback. The dashboard should detect and prefer it.

Type safety violation

Used any for payload display and state reconstruction

v1 Config.StateReconstructors map + payload decoding approach

v1 proposed func(events) (any, error) for state reconstruction and map[string]any for payload display. This violates the project's own principle: "Strong types throughout — no any as a value type in domain logic." The dashboard needs a proper typed approach.

Fix Payload display should use a PayloadRenderer interface that returns formatted bytes (JSON pretty-print), not decoded Go types. State reconstruction should use a typed registration system with generics where possible. See the Type Model section.
Weak type model for capabilities

Used map[string]bool for capability detection

v1 capabilities struct

v1 proposed a struct of bool flags for capability detection. This is fragile and non-extensible. Adding a new panel means editing the struct, adding a field, updating detection logic in multiple places.

Missed modules entirely

Forgot scheduling (deadlines/timers) and catalog/docserver reuse

scheduling/ + catalog/docserver/

v1 completely missed the scheduling module — deadline timers are a dashboard-worthy concept ("show me all pending timers"). Also missed that catalog/docserver already serves HTTP docs (OpenAPI UI, AsyncAPI UI, D2 diagrams, health check) — these could be mounted alongside the dashboard for a unified ops experience.

Design flaw

Overview page assumed an event count that doesn't exist

v1 Panel 1 wireframe: "1,247 Events"

No Count method exists on event.Store, Journal, or Bundle. The listing.Page type explicitly documents: "No TotalCount — append-only logs make counts stale and expensive." The overview page's "total events" stat card is currently impossible without loading all events or adding a count query. This is a real API gap that needs solving.

Design flaw

Event browser assumed filtered journal access that doesn't exist

v1 Panel 2: "filters by aggregate type, event type, time range"

SeekableJournal.ReadFrom(ctx, afterEventID, limit) only does cursor pagination — no filtering by type, aggregate type, or time range. The SQL implementation does WHERE id > ? ORDER BY occurred_at ASC LIMIT ?. Client-side filtering on paginated results is broken (you'd filter within a page, not across pages). This needs either a new interface method or a raw SQL path.

Missed

Security model was hand-waved

v1 Config.Authorizer

Event payloads can contain PII (user emails, IP addresses, user agents). The dashboard needs a security model: payload redaction, metadata filtering, admin-only access to sensitive fields. v1 said "auth-agnostic" and moved on.

02Type Model Improvements

The v1 report violated the project's own type-safety principles. Here is the corrected design.

Capabilities — typed panel registry, not bool flags

// Each panel is a typed registration, not a bool flag.
// Panels self-register when their required interfaces are present.

type PanelID string

const (
    PanelOverview    PanelID = "overview"
    PanelEvents      PanelID = "events"
    PanelAggregates  PanelID = "aggregates"
    PanelProjections PanelID = "projections"
    PanelDeadLetters PanelID = "dead-letters"
    PanelCommands    PanelID = "commands"
    PanelQueries     PanelID = "queries"
    PanelTimeTravel  PanelID = "time-travel"
    PanelTrace       PanelID = "trace"
    PanelSnapshots   PanelID = "snapshots"
)

// A Panel is a self-contained dashboard section.
type Panel interface {
    ID() PanelID
    Title() string
    Icon() icons.Name
    RegisterRoutes(mux *http.ServeMux, basePath string)
}

Payload rendering — typed interface, not any

// PayloadRenderer formats event payloads for display WITHOUT
// decoding into consumer domain types. Returns formatted bytes.
type PayloadRenderer interface {
    // Render returns a human-readable representation of the payload.
    // For JSON-encoded payloads: pretty-printed JSON.
    // For CBOR-encoded: decoded to JSON then pretty-printed.
    Render(payload []byte, encoding codec.Encoding) ([]byte, error)
}

// DefaultPayloadRenderer handles JSON + CBOR without consumer types
type DefaultPayloadRenderer struct{}

// StateFold reconstructs aggregate state for time-travel display.
// Consumers register one per aggregate type. Uses generics.
type StateFold[S any] func(current S, evt event.Event) (S, error)

// StateRegistration binds an aggregate type to its fold function + initial state.
type StateRegistration[S any] struct {
    StreamType id.StreamType
    Initial    S
    Fold       StateFold[S]
}

// RegisterState adds a typed state reconstruction.
// The dashboard stores these as map[id.StreamType]StateEntry
// where StateEntry holds the initial state + fold func as
// func(any, event.Event) (any, error) internally.
func [S any] RegisterState[S](d *Dashboard, reg StateRegistration[S])
Why this is better StateFold[S] uses generics so consumers get compile-time type safety on their state type. The dashboard internally type-erases to func(any, event.Event) (any, error) for storage, but the consumer-facing API is fully typed. any appears only in internal storage, not in the public API.

Event filter — typed, not loose query params

// EventFilter is a structured filter for the event browser.
// Applied server-side when possible (SQL), client-side as fallback.
type EventFilter struct {
    StreamType   id.StreamType   // filter by aggregate type
    EventType    event.Type      // filter by event type
    StreamID     id.StreamID     // filter by specific aggregate
    CorrelationID id.CorrelationID // filter by correlation
    From         time.Time       // time range start
    To           time.Time       // time range end
    Limit        int             // page size
    AfterEventID id.EventID      // cursor
}

04API Gaps Discovered During Research

These gaps in go-cqrs-lite block dashboard features. Each needs a small upstream addition.

Gap · Blocks overview page

No event count method

event.Store / Journal / Bundle

The overview page needs "total events" but no count method exists. Options: (a) add Count(ctx) (int64, error) to a new EventCounter interface, (b) use a dedicated count projection, (c) accept that the overview shows "recent" not "total." Option (a) is cleanest — SQL stores already have the data.

Gap · Blocks event browser filtering

No filtered journal access

SeekableJournal.ReadFrom

Event browser needs filtering by type/aggregate/time. ReadFrom only does cursor pagination. Options: (a) add a FilteredJournal interface with filter params, (b) add a raw SQL path in the dashboard for SQL stores, (c) client-side filter within loaded pages (works for small stores only).

Gap · Blocks deadlines panel

No ListPending on TimerStore

scheduling.TimerStore

TimerStore.Due(now) only returns overdue timers. For a deadlines panel, we need "show all upcoming timers ordered by fire time." Needs a ListAll or ListPending method.

Verify: mount in test, GET / returns 200 with sidebar.

4

Overview page (summary cards + health)

handler_overview.go: dashboard() handler. Renders StatCards for available metrics. Shows Bundle.HealthCheck() / DebugStructured(). Shows projection health strip from Host.Status() (if available). Verify: overview renders with real data from a memory bundle.

Core panels (Phase 1 — 80% value)
