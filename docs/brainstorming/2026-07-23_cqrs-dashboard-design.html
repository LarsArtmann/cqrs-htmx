CQRS / Event-Sourcing Dashboard

A design study for a plug-in observability dashboard for go-cqrs-lite and cqrs-htmx. Covers placement, feature scope, architecture, UI design, phased implementation plan, and gaps beyond the dashboard itself.

00Summary

go-cqrs-lite exposes a complete introspection API — event journals, command/query audit logs, aggregate listing, projection health, dead-letter queues, snapshots, and time-travel queries — but provides zero UI for visualizing any of it. Every consumer who wants to inspect their event-sourced system today must build their own tooling from scratch. This is the single biggest gap in the ecosystem.

Market research confirms the pattern: EventStoreDB, Axon Server, and Marten+CritterWatch all ship rich admin dashboards (stream browsers, projection managers, DLQ explorers). Eventuous and every Go CQRS library ship zero. Building this dashboard would make go-cqrs-lite + cqrs-htmx the first Go-native CQRS stack with a built-in observability UI — a genuine differentiator.

The recommendation Build a new dashboardui/ module in cqrs-htmx (sibling to the existing adminui/), following the same pattern: templ components, self-contained CSS, one-call mount, auth-agnostic. Wire it to go-cqrs-lite's existing introspection interfaces. Read-only by default; write operations (reset, replay, purge) behind explicit opt-in.

01The Gap

The go-cqrs-lite ROADMAP already lists this as a raw idea (line 100): "CQRS-lite dashboard (web UI for inspecting aggregates, events, projections)". No design exists yet. This report fills that gap.

The problem is concrete. A developer using go-cqrs-lite today who wants to answer any of these questions has no tooling:

"What events does aggregate X have?"

Must write a one-off script calling store.Load(ctx, ref) and fmt.Println the results. No UI to browse event timelines.

"Is projection Y keeping up?"

Must call host.Status() and host.LagDuration() programmatically. No dashboard to see lag at a glance.

"What command caused this event?"

Command causation metadata exists (metadata.command.type, metadata.command.id) but there is no UI to trace the causal chain.

"What's in the dead-letter queue?"

Must call dlqStore.List(ctx, projectionName) manually. No UI to inspect or replay poisoned messages.

"What did the system look like at version 42?"

Time-travel queries (LoadToVersion, LoadToTimestamp) exist in the API but there is no UI to scrub through aggregate history.

"How many User aggregates exist?"

The listing.StreamReader interface exists for exactly this, but there is no UI to browse, filter, or search aggregates.

The existing adminui/ module in cqrs-htmx is often confused with this dashboard, but it is fundamentally different:

Dimension adminui/ (existing) dashboardui/ (proposed)
Scope User management CQRS/ES infrastructure
Answers questions about Users, tenants, members, roles Events, aggregates, projections, DLQ
Reads from usermgmt.Service go-cqrs-lite interfaces
Depends on cqrs-htmx root + usermgmt cqrs-htmx root + go-cqrs-lite core
Write operations Delete user, create/suspend tenant Reset projection, replay DLQ, purge

Six systems were studied to understand the state of the art in CQRS/ES admin UIs. The findings directly inform the feature design below.

Key insight No CQRS/ES tool in any language provides all nine capabilities. EventStoreDB and CritterWatch are the richest but both lack time-travel and correlation tracing. go-cqrs-lite already has the APIs for all nine — including time-travel and command causation tracing that no competitor offers. Building the dashboard UI on top would create the most complete CQRS observability suite in the ecosystem.

What the best dashboards get right

+
One-call mount (CritterWatch pattern) SignalR-connected dashboard drops into any ASP.NET app with one line. Our adminui/ already follows this pattern — dashboardui/ must too.
+
Live tailing via SSE (EventStoreDB) The stream browser pauses/resumes live event arrivals. cqrs-htmx already has full SSE support (Broadcaster, SSEStream, JournalSSEStore).
+
DLQ with replay + edit-and-replay (CritterWatch) The killer feature: inspect a poisoned message, see the full stack trace, edit the JSON, and replay — all from the UI. go-cqrs-lite has Host.ReplayDeadLetters() already.
+
Projection health grid (CritterWatch) All projections in one table with status, lag, progress percentage, stall detection. projectionhost.Host.Status() returns exactly this data.

03Introspection API — Already Complete

The most important finding: go-cqrs-lite already exposes every interface the dashboard needs. Zero new core APIs need to be built. The dashboard is purely a consumer of existing interfaces.

Event inspection

type EventSource interface {
    Load(ctx, ref) ([]Event, error)
    LoadFromVersion(ctx, ref, version) ([]Event, error)
    LoadToVersion(ctx, ref, maxVersion) ([]Event, error)
    LoadToTimestamp(ctx, ref, maxTime) ([]Event, error)

// Global event log (for the event stream browser)
type Journal interface {
    ReadAll(ctx) ([]Event, error)

type SeekableJournal interface {
    Journal
    ReadFrom(ctx, afterEventID, limit) ([]Event, error)  // paginated!
}

// Event accessor methods (all on ImmutableEvent)
evt.ID()          // id.EventID (ULID)
evt.Type()        // event.Type
evt.StreamID()    // id.StreamID (aggregate ID)
evt.StreamType()  // id.StreamType (aggregate type)
evt.Version()     // event.Version
evt.Payload()     // []byte (decoded via DecodePayloadAuto[T])
evt.Metadata()    // correlation, causation, user, source, tombstone
evt.OccurredAt()  // time.Time

type Bundle struct {

Bottom line Every single piece of data the dashboard needs is already exposed through a clean, interface-segregated API. The dashboard is a pure consumer — no new core APIs, no new store methods, no changes to go-cqrs-lite.

04Placement Decision

Three options were considered. The recommendation is decisive.

Option A: go-cqrs-lite module

Rejected. go-cqrs-lite is "library, not framework" — no transport, no HTTP, no templ, no HTMX. A dashboard is fundamentally an HTTP UI. Adding it here would violate the core design principle and pollute the dependency tree of a pure library.

Option B: dashboardui/ in cqrs-htmx

Recommended. cqrs-htmx is the HTTP/HTMX layer. It already has adminui/ following this exact pattern. The dashboard depends on cqrs-htmx (HTMX, SSE, templ, routing) AND go-cqrs-lite (introspection interfaces). Placing it here follows the established architecture.

Option C: Independent repo

Rejected. A separate repo adds release coordination overhead, version drift risk, and import complexity with zero benefit. The module has a clean dependency chain (cqrs-htmx root + go-cqrs-lite core). It belongs in cqrs-htmx as a sibling to adminui/.

Module dependency graph

cqrs-htmx/ ├── v4 (root) # HTMX, SSE, templ, routing, authz ├── usermgmt/v4 # Event-sourced user management ├── adminui/v4 # User/tenant admin panel (existing) ├── dashboardui/v4 # CQRS/ES observability dashboard (PROPOSED) │ ├── depends on: cqrs-htmx/v4 # HTMX patterns, SSE, templ integration │ ├── depends on: go-cqrs-lite/event/v4 # EventSource, Journal, SeekableJournal │ ├── depends on: go-cqrs-lite/command/v4 # CommandJournal (optional) │ ├── depends on: go-cqrs-lite/query/v4 # QueryJournal (optional) │ ├── depends on: go-cqrs-lite/listing/v4 # StreamReader (optional) │ ├── depends on: go-cqrs-lite/projectionhost/v4 # Host, DeadLetterStore (optional) │ └── depends on: go-cqrs-lite/snapshot/v4 # SnapshotStore (optional) ├── loginpage/v4 └── examples/
Why this works The dashboard's dependencies are all optional (except EventSource/Journal). If a consumer doesn't wire a CommandJournal, the command audit panel simply doesn't appear. The dashboard auto-detects available capabilities and shows only relevant panels — exactly like Bundle.DebugStructured() already reports which capabilities are wired.

05Feature Design

Nine panels, mapped directly to go-cqrs-lite introspection interfaces. Each panel is independently activatable based on which interfaces the consumer provides.

Panel inventory

# Panel Primary Interface Phase Key Capability
1 Overview Dashboard All available P1 Summary cards: events, aggregates, projections, DLQ depth
2 Event Stream Browser SeekableJournal P1 Global paginated event log with live SSE tail
3 Aggregate Browser listing.StreamReader P1 List/search aggregates, click into event timeline
4 Projection Dashboard projectionhost.Host P1 Status, lag, processed/errors, reset
5 Dead-Letter Queue DeadLetterStore P1 Inspect, replay, delete poisoned messages
6 Command/Query Audit CommandJournal / QueryJournal P2 Full dispatch audit trail with payloads
7 Time-Travel Inspector EventSource.LoadToVersion P2 Scrub through aggregate versions, reconstruct state
8 Correlation Trace Event metadata P3 Visualize command→event→derived-command causal chain
9 Snapshot Inspector snapshot.SnapshotStore P3 View/delete snapshots per aggregate

Panel 1 — Overview Dashboard

Goal: One-glance system health. Answers "is everything working?"

Data sources: All available interfaces, summarized.

Contains:

  • Summary stat cards: total events (from Journal count), total aggregates (from StreamReader), active projections (from Host.Status), DLQ depth (from DeadLetterStoreAdmin.Count)
  • Projection health strip: green/yellow/red per projection based on lag threshold (from Host.LagPerProjection())
  • Recent events: last 10 events (from SeekableJournal.ReadFrom with limit)
  • Recent dead letters: last 5 DLQ entries across all projections
  • System health: Bundle.HealthCheck() result

Live updates: SSE push for new events and projection status changes.

Panel 2 — Event Stream Browser (the crown jewel)

Goal: Browse, search, and inspect every event in the system.

Primary interface: event.SeekableJournal.ReadFrom(ctx, afterEventID, limit) for paginated access. Falls back to Journal.ReadAll for in-memory stores.

Features:

  • Paginated event table: ULID-based cursor pagination via ReadFrom. Columns: timestamp, event ID, type, stream ID, stream type, version, schema version
  • Filters: by aggregate type, event type, time range, correlation ID (filters applied client-side on paginated results, or via custom journal implementation)
  • Event detail view: click any event to expand — shows decoded payload (pretty-printed JSON via event.DecodePayloadAuto[T]), full metadata (correlation ID, causation, user ID, request ID, source IP, user agent, tombstone status, custom metadata), encoding, deadline
  • Live tail: SSE connection that pushes new events in real-time (using cqrs-htmx's Broadcaster + JournalSSEStore)
  • Pause/resume: like EventStoreDB's stream browser

Panel 3 — Aggregate Browser

Goal: List, filter, and drill into aggregates.

Primary interface: listing.StreamReader.ListWithStatus(ctx, opts)

Features:

  • Aggregate table: ID, type, current version, event count, last event timestamp, tombstone status (active/tombstoned)
  • Filters: by stream type (dropdown populated from observed types), tombstone policy (all/active-only/deleted-only), pagination via ListOptions.After + ListOptions.Limit
  • Aggregate detail: click into an aggregate — shows the full event timeline (via EventSource.Load), current state summary, snapshot info (if available), tombstone history
  • Auto-creation: if no StreamReader is configured, the dashboard auto-creates an InMemoryStreamReader from the journal

Panel 4 — Projection Dashboard

Goal: Monitor and manage projection health.

Primary interface: projectionhost.Host.Status(), Host.LagPerProjection()

Features:

  • Projection grid: one row per projection showing name, status (idle/running/live/backoff/draining/stopped/failed), checkpoint position, processed count, error count, restart count, lag duration, last error
  • Color-coded status: green (running/live), yellow (idle/backoff), red (stopped/failed)
  • Lag visualization: human-readable lag ("2.3s behind", "caught up") with trend indicator
  • Reset projection: button to call Host.Reset(ctx, name) — replays from beginning. Confirmation dialog. Behind ReadOnly = false opt-in.
  • Live updates: SSE push for status changes

Panel 5 — Dead-Letter Queue Viewer

Goal: Inspect, replay, and manage poisoned messages.

Primary interface: DeadLetterStoreAdmin.ListPaged, DeadLetterStoreAdmin.Count, Host.ReplayDeadLetters

Features:

  • DLQ summary: total count across all projections (from Count)
  • Per-projection filter: select projection to view its dead letters
  • Dead-letter table: event ID, event type, stream ID, error message, error code, error family (5-family taxonomy), failed timestamp
  • Detail view: full event payload + metadata + stack trace (the DeadLetterEntry.Event field contains the full event)
  • Replay: button to call Host.ReplayDeadLetters(ctx, projectionName) — replays all dead letters for that projection. Shows ReplayResult (replayed vs still failing).
  • Delete/Purge: individual delete (DeadLetterStore.Delete), purge all (DeadLetterStore.Purge), purge before timestamp (DeadLetterStoreAdmin.PurgeBefore). Behind ReadOnly = false.

Panel 6 — Command/Query Audit Log

Goal: Full audit trail of every dispatched command and query.

Primary interfaces: command.SeekableCommandJournal.ReadFrom, query.SeekableQueryJournal.ReadQueriesFrom

Features:

  • Command log table: timestamp, command ID, type, stream ref, payload summary, metadata (user, correlation, request ID)
  • Query log table: timestamp, request ID, type, payload summary, metadata
  • Detail view: full decoded payload + metadata
  • Cross-link: click a command's causation ID to jump to the events it produced (links to the Event Stream Browser filtered by causation ID)

Note: only appears if the consumer has wired a CommandStore or QueryStore. Most consumers don't persist queries — that panel gracefully hides.

Panel 7 — Time-Travel Inspector

Goal: Scrub through aggregate history and reconstruct state at any point in time.

Primary interfaces: EventSource.LoadToVersion, EventSource.LoadToTimestamp

Features:

  • Version slider: for any aggregate, a slider from version 1 to current version. Move the slider to see the aggregate's event timeline up to that point.
  • State reconstruction: if the consumer provides a fold function (decider.Decider[State].Fold), the dashboard reconstructs and displays the aggregate state at the selected version. This is the killer feature no competitor has.
  • Timestamp navigation: alternatively pick a timestamp and load via LoadToTimestamp
  • Diff view: show what changed between the previous version and the selected version (which events were added)
Unique differentiator No CQRS/ES tool in any language offers a time-travel UI. EventStoreDB, Axon, CritterWatch — none of them. This feature alone would make the dashboard noteworthy.

Panel 8 — Correlation Trace

Goal: Visualize the full causal chain: which command produced which events, which events triggered derived commands, which derived commands produced more events.

Primary data: event metadata (metadata.command.type, metadata.command.id via event.CommandCausalityFromContext), correlation ID, causation ID

Features:

  • Trace view: start from any event or command. The dashboard walks the journal to find all events sharing the same correlation ID, ordered by occurrence time.
  • Causal graph: visualize command → event → derived command → event chains as a tree/timeline. The deriver module's event→command derivation creates these chains; this panel makes them visible.
  • Cross-panel links: every event in every panel has a "view trace" link that jumps here

Panel 9 — Snapshot Inspector

Goal: View and manage aggregate snapshots.

Primary interface: snapshot.SnapshotStore.Load, SnapshotStore.Delete

Features:

  • Snapshot list: for any aggregate, show snapshot version, state size, creation timestamp
  • State viewer: decode and pretty-print the snapshot state (requires codec information)
  • Delete: remove a snapshot (behind ReadOnly = false)

07Config & Mounting API

Following the adminui/ pattern — Config struct, New(), Mount():

Config struct

type Config struct {
    // === REQUIRED ===

    // EventSource provides per-aggregate event loading (aggregate detail,
    // time-travel). Can be nil if only the global event log is needed.
    EventSource event.EventSource

    // Journal or SeekableJournal provides the global event log.
    // SeekableJournal is preferred (paginated). Journal is the fallback.
    Journal         event.Journal
    SeekableJournal event.SeekableJournal

    // === OPTIONAL (panels appear only if provided) ===

    StreamReader      listing.StreamReader           // Aggregate Browser
    ProjectionHost    *projectionhost.Host          // Projection Dashboard
    DeadLetterStore   projectionhost.DeadLetterStore // DLQ Viewer
    CommandJournal    command.CommandJournal         // Command Audit
    QueryJournal      query.QueryJournal             // Query Audit
    SnapshotStore     snapshot.SnapshotStore         // Snapshot Inspector
    EventBus          event.Bus                     // SSE live updates

    // === OPTIONAL (state reconstruction for time-travel) ===

    // StateReconstructor, if provided, enables state reconstruction
    // in the Time-Travel panel. Map aggregate type → fold function.
    StateReconstructors map[id.StreamType]StateReconstructor

    // === UI ===

    Title       string  # default: "CQRS Dashboard"
    BasePath    string  # default: "/dashboard"
    AccentColor string  # default: indigo (any CSS color)

    // ReadOnly = true (default) disables all write operations:
    // projection reset, DLQ replay/delete/purge, snapshot delete.
    // The dashboard becomes pure observation.
    ReadOnly bool

    // Authorizer controls access. If nil, allows all (consumer must
    // wrap with their own auth middleware). Follows adminui pattern.
    Authorizer func(r *http.Request) error
}

// StateReconstructor folds events into state for time-travel display
type StateReconstructor func(events []event.Event) (any, error)

Mounting patterns

Pattern 1: From Bundle (zero-effort)

import "github.com/larsartmann/cqrs-htmx/dashboardui/v4"

// Auto-wires everything the Bundle provides
panel, _ := dashboardui.FromBundle(bundle, dashboardui.Config{
    Title: "My App Dashboard",
})

// Optionally add things not in the Bundle:
panel.WithProjectionHost(host)
panel.WithDeadLetterStore(dlqStore)

mux.Handle("/dashboard/", sessionMiddleware(panel.Handler()))

Pattern 2: Explicit (full control)

panel, _ := dashboardui.New(dashboardui.Config{
    EventSource:       store,
    SeekableJournal:   store,
    StreamReader:      listing.NewInMemoryStreamReader(store),
    ProjectionHost:    host,
    DeadLetterStore:   dlqStore,
    Title:             "Ops Dashboard",
    ReadOnly:          false,  // enable reset/replay/purge
    Authorizer:        requireAdmin,
})

panel.Mount(mux, "/dashboard")

Pattern 3: Read-only observer (dev/prod safety)

panel, _ := dashboardui.FromBundle(bundle, dashboardui.Config{
    ReadOnly: true,  # no reset, no replay, no delete — just look
})

08UI / UX Design

Design principles

+
Follow adminui/ exactly templ components, self-contained stylesheet (no Tailwind, no build step), automatic light/dark theming, configurable accent color. The generated Go is committed so consumers never run a code generator.
+
HTMX-driven interactivity Live search, inline actions, SSE for real-time updates. No React, no SPA, no client-side routing. Just HTMX partial swaps.
+
Read-only by default Observation is the default mode. Write operations (reset, replay, purge) require explicit ReadOnly = false and show confirmation dialogs.
+
Density over decoration Developers use this to debug. Information density matters more than whitespace. Tables, monospace timestamps, color-coded status badges.

09What Else Is Missing

Beyond the dashboard itself, the research surfaced three additional gaps in the ecosystem. These are not part of the dashboard scope but are worth addressing.

Gap · Medium impact

Composite readiness checker

cqrs-htmx root · App.HealthHandler()

The existing App.HealthHandler() is a basic liveness check. A CQRS app needs a readiness check that answers: is the event store reachable? Are projections caught up (Host.LagDuration() < threshold)? Is the DLQ depth below threshold? This composite check should be composable and expose a /readyz endpoint distinct from liveness.

Recommendation Add cqrshtmx.ReadinessHandler(checks ...ReadinessCheck) that aggregates event-store ping, projection lag, and DLQ depth. Each check is a function returning (ok bool, detail string).
Gap · Medium impact

CQRS admin CLI (cqrs-admin)

go-cqrs-lite/cmd/ · sibling to cqrs-gen, cqrs-lint, cqrs-bench

The dashboard covers interactive inspection. But for automation, CI/CD, and scripting, a CLI is needed: cqrs-admin events list, cqrs-admin projections reset --name search_index, cqrs-admin dlq replay --projection search_index, cqrs-admin aggregates list --type User. This mirrors how Marten has a projections CLI alongside CritterWatch.

Recommendation The dashboard's data.go layer should expose a clean ReadModel API that both the HTTP handlers and a future CLI can share. Design the CLI after the dashboard stabilizes.

A /debug/cqrs JSON endpoint that dumps system state (capabilities wired, event count, projection status, DLQ depth) would be useful for programmatic monitoring and the dashboard's own overview page.

11Risks & Tradeoffs

Risk · Manageable

Large event stores + in-memory operations

SeekableJournal.ReadAll fallback · InMemoryStreamReader

Journal.ReadAll() loads ALL events into memory. For large stores this is dangerous. The dashboard MUST prefer SeekableJournal.ReadFrom (paginated) and only fall back to ReadAll for in-memory stores. InMemoryStreamReader has a cached mode but the initial scan is O(n).

Mitigation The Config should detect SeekableJournal vs plain Journal. For plain Journal, show a warning: "Pagination not available, loading all events." The overview page should never call ReadAll — it should use StreamReader counts or a dedicated count method.
Risk · Manageable

Write operation safety

Host.Reset() · ReplayDeadLetters() · Purge()

Host.Reset() replays ALL events through a projection from scratch. This is expensive and potentially destructive (if the projection has side effects). Purge() deletes all dead letters permanently.

Mitigation ReadOnly = true is the default. All write operations require explicit opt-in AND a typed confirmation dialog (like CritterWatch's "type DISCARD to confirm"). Reset operations show a warning about cost.
Tradeoff · Acceptable

Payload decoding requires type registration

event.DecodePayloadAuto[T] · dashboardui

The dashboard doesn't know consumer event types at compile time. It can't call DecodePayloadAuto[UserCreated] because it doesn't import consumer types. The raw payload bytes are always available, but pretty-printing requires decoding.

Approach The dashboard shows raw payload as JSON pretty-printed (most events are JSON or CBOR encoded). For CBOR, use codec.CBORCodec{}.Decode() to get a map[string]any. For JSON, json.Unmarshal to map[string]any. Both produce displayable pretty-printed output without knowing consumer types. Optionally, consumers can register type hints via Config.PayloadTypeRegistry for typed decoding.
Tradeoff · Acceptable

Filtering on SeekableJournal

SeekableJournal.ReadFrom · no filter parameter

SeekableJournal.ReadFrom(ctx, afterEventID, limit) supports cursor pagination but not filtering (by type, by aggregate, by time range). The dashboard must either filter client-side (load pages, filter in Go) or require a custom journal implementation.

Approach Phase 1: client-side filtering on loaded pages. For power users, document how to implement a filtered journal (the event.SeekableJournal interface is simple). Future: propose a FilteredJournal wrapper in go-cqrs-lite that pushes filters to the SQL layer (where SQLEventStore already supports WHERE clauses).
