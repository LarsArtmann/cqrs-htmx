Identity Model Redesign

Actor, Tenant, Impersonation

A first-principles redesign of the usermgmt identity and authorization model: unifying Users and Bots under a sealed Actor interface, introducing first-class Tenant aggregates, typed Membership, role hierarchy (Super Admin vs Tenant Admin), and durable Impersonation with audit trails.

01Current State

The usermgmt module models identity as a single human-centric concept: User. There is exactly one ID type (UserID), one aggregate (User), and one role list (flat, no hierarchy). The Casbin authorization model uses a free-form string domain parameter with no typed tenant entity. No bot identity, no tenant lifecycle, no impersonation, no role inheritance.

02Problem Catalog

Critical

P1 — No Actor Abstraction: UserID Is the Only Identity

usermgmt/id.go:11, usermgmt/user.go:20-32, context.go:13

UserID is the sole identity type. Every authentication flow, session, context key, and audit trail assumes a human. There is no way to represent a bot, service account, or system identity. The User struct is human-centric (Email, WebAuthn credentials, OAuth2) — machine authentication via API tokens is structurally impossible without shoehorning a bot into human fields.

Fix Introduce a sealed Actor interface union. Both User and Bot implement it. Authorization, sessions, and audit key on ActorID — never UserID directly.
Critical

P2 — No TenantID: Casbin Domain Is a Raw String

usermgmt/authz_types.go:45-59, usermgmt/authz_roles.go:8, es_casbin_projection.go:63-66

The Casbin RBAC-with-domains model accepts a domain parameter as a free-form string. There is no TenantID branded type, no Tenant aggregate, no tenant lifecycle, and no tenant-scoped resource isolation. The current default assigns each user's own ID as their domain (es_casbin_projection.go:64) — a hack, not a design.

Fix Introduce TenantID = brandid.ID[tenantBrand, string] and a Tenant aggregate with its own event stream. Replace all string domain parameters with typed TenantID. Introduce a Membership entity linking ActorID → TenantID with scoped roles.
Critical

P3 — No Role Hierarchy: Single Flat Admin

usermgmt/authz_types.go:34-43, usermgmt/authz_roles.go:74-78

Four roles exist (admin, user, viewer, owner) with zero inheritance. The default policy seeds a single wildcard: {admin, *, *, *, allow}. There is no distinction between "super admin" (global) and "tenant admin" (scoped). A flat admin either has access to everything or nothing — no middle ground.

Fix Add RoleSuperAdmin with a Casbin g2 hierarchy: super_admin > admin > user > viewer. Seed global policy for super_admin (domain *) and tenant-scoped policy for admin (domain = tenantID).
Critical

P4 — No Impersonation: Sessions Lack Origin Tracking

usermgmt/user.go:96-101, usermgmt/store.go:13-18, usermgmt/middleware.go:39-59

Session carries only Token, UserID, and timestamps. There is no field recording "who created this session on behalf of whom." An admin cannot act as another user for support/debugging without the user's actual credentials. No audit trail of the impersonation chain exists. There is no ImpersonatedBy or Origin field.

Fix Replace Session.UserID with Session.ActorID and add a sealed SessionOrigin union: DirectLogin{AuthenticatedAs} vs Impersonation{By, Reason, At}. Events on a separate audit stream (ImpersonationStarted, ImpersonationEnded).
High

P5 — Roles Live on User Instead of Membership

usermgmt/user.go:24, usermgmt/es_state.go:15, es_events.go:15-19

UserState.Roles is a flat []Role on the User aggregate. The RolesUpdated event carries a Domain field, but the domain-to-roles mapping is implicit — the read model and Casbin projection must reconstruct it. This means a user's roles are coupled to their identity rather than to their tenant membership. Moving a user between tenants is impossible without destroying and recreating role assignments.

Fix Move roles to a Membership entity: {ActorID, TenantID, Roles}. A user can have different roles in different tenants. Role changes emit MembershipRolesChanged events on the Membership's own event stream (or a tenant-scoped stream).
High

P6 — No Bot Authentication: API Tokens Don't Exist

usermgmt/middleware.go:76-85 (extractToken — session/cookie only)

The extractToken function in middleware handles session cookies and Bearer tokens, but all tokens resolve to a UserID via SessionStore.Find(). There is no APIToken type, no token-to-bot lookup, and no scope-based authorization (bots need scopes like read:users, not full RBAC role membership).

Fix Add Bot aggregate with APIToken (hashed, never stored plaintext). Middleware checks both session store and API token store. Bots authenticate via Authorization: Bearer <token> resolved to BotID.
High

P7 — Event Metadata Lacks PerformedBy / Impersonation Context

context.go:134-165 (EventOptionsFromContext), usermgmt/es_events.go (all payloads)

EventOptionsFromContext propagates UserID, CorrelationID, and RequestID into event metadata. But there is no PerformedBy or ImpersonatorID field. When an admin impersonates a user and triggers a command, the resulting event would record only the target user's ID — the admin who actually performed the action is invisible.

Fix Extend EventOptionsFromContext to also propagate ActorID (effective) and ImpersonatorID (real actor, if impersonating). These become event metadata fields queryable for audit.

03The Vision

+
Actor as the unifying abstraction Authorization, sessions, audit trails, and context propagation all key on ActorID. Users and Bots are just auth-mechanism variants of the same concept. Adding a new actor type (e.g., System) is O(1) — implement the interface.
+
Typed TenantID replaces string domain The Casbin domain parameter becomes a branded TenantID. Compile-time prevention of accidentally passing a user ID or free-form string as a tenant scope.
+
Membership decouples roles from identity An actor's roles are scoped to their tenant membership — not embedded in their identity. Users can have different roles in different tenants. Role changes don't touch the User aggregate.
+
Role hierarchy enables Super vs Tenant Admin Casbin g2 inheritance: super_admin > admin > user > viewer. Super admin gets wildcard across all domains. Tenant admin is scoped to one tenant. Impossible to accidentally escalate.
+
Impersonation is a first-class, audited operation Sessions carry their origin (direct login vs impersonation). Every impersonated action records both the effective actor and the impersonator. Full audit trail on a separate event stream.
+
Impossible states are unrepresentable Sealed interfaces prevent constructing an Actor that isn't a User or Bot. SessionOrigin union prevents a session that claims to be impersonating without recording who impersonated. Type switches are exhaustive.

04Actor Model — Sealed Union

The core insight: "Bot and Users are both Actors." An Actor is anything that can authenticate, be authorized, hold a session, and be audited. We model this as a sealed interface — only types in the usermgmt package can implement it.

Before — Single flat type
After — Sealed Actor union
// id.go — the ONLY identity type
type UserID = brandid.ID[userBrand, string]

// No Bot, no System, no API token auth
// Everything keys on UserID
// Sealed ActorID — both User and Bot satisfy it
type ActorID interface {
    String() string
    Kind() ActorKind
    actorID() // unexported seal
}

type UserID = brandid.ID[userBrand, string]
type BotID  = brandid.ID[botBrand, string]

// Both implement ActorID via .String() + .Kind()
func (UserID) actorID() {}
func (BotID)  actorID() {}

Full Actor Type Definitions

// ActorKind discriminates actor variants for type switches
type ActorKind int

const (
    ActorKindUser ActorKind = iota
    ActorKindBot
)

// Actor is the sealed union of all identity types.
// Only User and Bot implement it (via the unexported actor() method).
type Actor interface {
    ID() ActorID
    Type() ActorKind
    DisplayName() string
    actor() // unexported — seals the union
}

// User — Human Actor (existing type, updated)
type User struct {
    ID               UserID
    Email            string
    DisplayName      string
    Credentials      []WebAuthnCredential
    ExternalAccounts []ExternalAccount
    EmailVerified    bool
    TOTPEnabled      bool
    // NOTE: Roles REMOVED — moved to Membership
}

func (u *User) ID() ActorID         { return u.ID }
func (u *User) Type() ActorKind    { return ActorKindUser }
func (u *User) DisplayName() string { return u.DisplayName }
func (u *User) actor()                   {}

// Bot — Machine Actor (NEW aggregate)
type Bot struct {
    ID         BotID
    Name       string
    TenantID   TenantID   // bots are always tenant-scoped
    Scopes     []Scope      // e.g. "read:users", "write:catalog"
    TokenHash  []byte       // SHA-256 of API token, never plaintext
    LastSeenAt time.Time
    CreatedAt  time.Time
    RevokedAt  *time.Time   // nil = active
}

func (b *Bot) ID() ActorID         { return b.ID }
func (b *Bot) Type() ActorKind    { return ActorKindBot }
func (b *Bot) DisplayName() string { return b.Name }
func (b *Bot) actor()                   {}

// Exhaustive type switch — compiler enforces all cases
func doSomethingWithActor(a Actor) {
    switch v := a.(type) {
    case *User:
        // human-specific logic (e.g. send email)
    case *Bot:
        // machine-specific logic (e.g. check scopes)
    default:
        // This should NEVER execute — build-breaker if it does
        panic(fmt.Sprintf("unhandled actor type: %T", v))
    }
}

05Tenant Model — Organizational Boundary

A Tenant is an organizational boundary that scopes actors, resources, and authorization. It replaces the free-form domain string in the Casbin model with a branded TenantID. A Membership links an Actor to a Tenant with scoped roles.

Tenant Aggregate (Event-Sourced)

type TenantID = brandid.ID[tenantBrand, string]

type TenantStatus int
const (
    TenantActive    TenantStatus = iota
    TenantSuspended
    TenantDeleted
)

type TenantState struct {
    Name      string
    Status    TenantStatus
    CreatedAt time.Time
}

// Events
type TenantCreatedPayload struct {
    SchemaVersion int    `json:"schema_version"`
    Name          string `json:"name"`
}
type TenantSuspendedPayload struct {
    SchemaVersion int    `json:"schema_version"`
    Reason        string `json:"reason"`
}

// Membership — Actor ↔ Tenant link with scoped roles
type Membership struct {
    ActorID  ActorID
    TenantID TenantID
    Roles    []Role  // scoped to THIS tenant only
}

Membership replaces UserState.Roles

Currently UserState.Roles is a flat list on the User aggregate. In the new model, roles move to Membership. A user with admin in Tenant A and viewer in Tenant B has two Membership entities — the User aggregate knows nothing about roles.

06Impersonation — Act on Behalf Of

Impersonation allows a Super Admin to create a session that acts as another actor (User or Bot) for support, debugging, or testing. The session records both the effective actor (who they're acting as) and the impersonator (who they really are). Every action taken during impersonation is audited with the full actor chain.

Session with Sealed Origin

// SessionOrigin — sealed union for login provenance
type SessionOrigin interface {
    origin() // unexported seal
}

// DirectLogin — normal authentication (user logged in themselves)
type DirectLogin struct {
    AuthenticatedAs ActorID  // == Session.ActorID
}
func (DirectLogin) origin() {}

// Impersonation — admin is acting as another actor
type Impersonation struct {
    By     ActorID   // the real admin
    Reason string    // mandatory audit field
    At     time.Time
}
func (Impersonation) origin() {}

// Session — now carries ActorID + Origin
type Session struct {
    Token     string
    ActorID   ActorID       // who the session acts AS
    Origin    SessionOrigin // how this session came to be
    CreatedAt time.Time
    ExpiresAt time.Time
}

// Impersonator returns the real actor, or nil if direct login.
// Consumers use this for audit logging.
func (s *Session) Impersonator() (ActorID, bool) {
    if imp, ok := s.Origin.(Impersonation); ok {
        return imp.By, true
    }
    return nil, false
}

// Impersonation audit events (separate stream, NOT on User aggregate)
type ImpersonationStartedPayload struct {
    SchemaVersion int      `json:"schema_version"`
    Actor         ActorID `json:"actor"`          // target (acted as)
    By           ActorID `json:"by"`            // impersonator
    Reason        string  `json:"reason"`
}
type ImpersonationEndedPayload struct {
    SchemaVersion int      `json:"schema_version"`
    Actor         ActorID `json:"actor"`
    By           ActorID `json:"by"`
}

Security Guards (Non-Negotiable)

  • Only super_admin can initiate impersonation
  • Cannot impersonate another super_admin (no privilege escalation)
  • Reason field is mandatory — empty reason = rejection
  • Max impersonation session duration enforced (e.g., 1 hour)
  • All impersonated commands carry impersonated=true in metadata
  • Impersonation events on a separate audit stream — tamper-evident

07Role Hierarchy — Super vs Tenant Admin

The current flat role list gains a Casbin g2 hierarchy. Super Admin inherits from admin (which inherits from user, which inherits from viewer). The key distinction: Super Admin's policy is seeded in domain * (global), while Tenant Admin's policy is scoped to a specific TenantID.

Updated Role Constants and Casbin Model

const (
    RoleSuperAdmin Role = "super_admin" // global wildcard
    RoleAdmin      Role = "admin"       // tenant-scoped wildcard
    RoleUser       Role = "user"        // standard member
    RoleViewer     Role = "viewer"      // read-only
    RoleOwner      Role = "owner"       // resource ownership
)

// Updated Casbin model with role hierarchy (g2)
const modelWithHierarchy = `[request_definition]
r = sub, dom, obj, act

[policy_definition]
p = sub, dom, obj, act, eft

[role_definition]
g = _, _, _       # user → role assignments
g2 = _, _         # role hierarchy (inheritance)

[policy_effect]
e = some(where (p.eft == allow)) && !some(where (p.eft == deny))

[matchers]
m = (p.sub == "*" || g(r.sub, p.sub, r.dom) || g2(p.sub, inheritedRole) && g(r.sub, inheritedRole, r.dom))
  && (p.dom == "*" || r.dom == p.dom)
  && (p.obj == "*" || r.obj == p.obj)
  && (p.act == "*" || r.act == p.act)`

// Seed policies
func defaultPolicies() []Policy {
    return []Policy{
        {RoleSuperAdmin, "*", "*", ActionAll, EffectAllow},
    }
}

// Role hierarchy seed (applied on NewAuthz)
func defaultRoleHierarchy() []RoleLink {
    return []RoleLink{
        {RoleSuperAdmin, RoleAdmin},   // super_admin inherits admin
        {RoleAdmin,      RoleUser},    // admin inherits user
        {RoleUser,       RoleViewer},  // user inherits viewer
    }
}

08Events & Commands

The new aggregates (Tenant, Bot, Membership) each get their own event streams. Impersonation events go to a separate audit stream. The User aggregate loses Roles (moved to Membership) but keeps identity and credential events.

Tenant Aggregate

Events: TenantCreated, TenantRenamed, TenantSuspended, TenantReactivated, TenantDeleted

Commands: CreateTenant, RenameTenant, SuspendTenant, ReactivateTenant, DeleteTenant

Bot Aggregate

Events: BotCreated, BotRenamed, BotScopesChanged, BotRevoked, BotDeleted

Commands: CreateBot, RenameBot, UpdateBotScopes, RevokeBot, DeleteBot

Membership Aggregate

Events: MemberAdded, MemberRolesChanged, MemberRemoved

Commands: AddMember, UpdateMemberRoles, RemoveMember

Impersonation Audit Stream

Events: ImpersonationStarted, ImpersonationEnded

Not an aggregate — append-only audit log. Stream key: impersonation-{actorID}. Queryable for compliance.

09Context Propagation

The root context.go gains ActorID and ImpersonatorID context keys alongside the existing UserID, CorrelationID, and RequestID. EventOptionsFromContext propagates the full actor chain into event metadata for auditing.

Before — UserID only
After — ActorID + Impersonator
func EventOptionsFromContext(ctx context.Context) []event.Option {
    if uid := UserIDFromContext(ctx); !uid.IsZero() {
        opts = append(opts, event.WithUserID(uid))
    }
    // No impersonator tracking
    // No actor kind
}
func EventOptionsFromContext(ctx context.Context) []event.Option {
    if aid := ActorFromContext(ctx); aid != nil {
        opts = append(opts, event.WithActorID(aid))
    }
    if imp := ImpersonatorFromContext(ctx); imp != nil {
        opts = append(opts, event.WithImpersonator(imp))
    }
    // Full actor chain in every event
}

10Decision Log

D1: Sealed interface union over string discriminator

Chose: ActorID as a sealed Go interface with UserID and BotID as implementations.
Rejected: Single ActorID type with a Kind field (type ActorID struct { value string; kind ActorKind }). Reason: runtime discrimination is error-prone. The sealed interface forces exhaustive type switches and prevents constructing an ActorID with an invalid kind.

D2: Roles on Membership, not on User

Chose: Move Roles from UserState to Membership.
Rejected: Keep roles on User but add a TenantID field to each role assignment. Reason: a user's identity should not change when their role in a tenant changes. Coupling roles to identity means tenant transfers require User aggregate mutations — breaking the single-responsibility of the User aggregate.

D3: SessionOrigin sealed union over boolean field

Chose: SessionOrigin as a sealed interface with DirectLogin and Impersonation variants.
Rejected: Boolean IsImpersonated field plus optional ImpersonatorID. Reason: a bool + optional pointer can represent IsImpersonated=true, ImpersonatorID=nil — an impossible state that the type system should prevent. The sealed union makes this unrepresentable.

D4: Impersonation events on a separate audit stream

Chose: ImpersonationStarted/Ended on a separate impersonation-{actorID} stream, not on the User aggregate.
Rejected: Add impersonation events to the User's event stream. Reason: impersonation is not a state change to the User aggregate — it's an operational action performed BY an admin. Mixing it into User events would pollute the domain model and make User replay include impersonation side-effects.

D5: TenantID branded type over typed domain string

Chose: TenantID = brandid.ID[tenantBrand, string].
Rejected: Keep domain string but validate it as a TenantID at the Authz boundary. Reason: branded types prevent cross-assignment at compile time. A function expecting TenantID cannot accidentally receive a UserID or free-form string.

11Anti-Patterns to Avoid

Trap

Embedding User into Bot for code reuse

Do NOT embed User into Bot to reuse fields like Email or DisplayName. Bots don't have emails. Embedding creates a false "is-a" relationship and promotes fields that don't belong. Use composition via the Actor interface instead.

Trap

Using ActorID.String() as a Casbin subject

Do NOT pass ActorID.String() directly as the Casbin subject without encoding the actor kind. If user_01J... and bot_01J... produce the same string, Casbin policies would be ambiguous. The string encoding MUST include the kind prefix: "user:01J..." or "bot:01J...".

Trap

Storing API tokens in plaintext

Bot API tokens must be stored as SHA-256 hashes — never plaintext. The token is shown once at creation time and compared via subtle.ConstantTimeCompare on authentication. This mirrors the existing session token pattern.

Trap

Impersonation without mandatory reason

Every impersonation session MUST have a non-empty Reason. This is the audit justification. An empty reason is a rejection at the command-validation level, not a warning. Without this, impersonation becomes an unaudited backdoor.

Watch out

Default tenant on registration

When a user registers without a tenant context, decide explicitly: do they get a personal tenant (like GitHub personal accounts), a shared default tenant, or no tenant (unassigned until invited)? This is a product decision, not a technical one. Document the choice and enforce it in RegisterUserCmd validation.

12Migration Roadmap

This is a foundational data-model change. It touches the identity, authorization, session, and context layers. The migration must be incremental — each step compiles, passes tests, and ships independently.

1

Add branded types: ActorID, BotID, TenantID

Add the new branded types alongside existing UserID. No behavior change — just type definitions and the sealed Actor / ActorID interfaces. Existing code continues using UserID.

2

Introduce Tenant aggregate and Membership entity

New event-sourced Tenant aggregate with its own commands/events. Membership entity links ActorID to TenantID. CasbinProjection gains Membership event handling. No changes to existing User/Session yet.

3

Migrate roles from User to Membership

Move UserState.Roles to Membership.Roles. Existing RolesUpdated events become MemberRolesChanged. Add migration projection to replay old User events into Membership events. User aggregate loses the Roles field.

4

Add role hierarchy (g2) to Casbin model

Update defaultModel to include g2 role inheritance. Seed super_admin > admin > user > viewer hierarchy. Update defaultPolicies to seed super_admin with domain *.

5

Add SessionOrigin sealed union

Extend Session with Origin field. Update SessionStore interface and implementations. Existing sessions get DirectLogin{AuthenticatedAs: UserID} as default origin.

6

Implement impersonation Service methods + audit stream

Add Service.BeginImpersonation(actorID, reason) and Service.EndImpersonation(token). Create impersonation audit stream. Wire security guards (super_admin check, max duration, reason validation).

7

Add Bot aggregate + API token authentication

New event-sourced Bot aggregate with API token auth. Update session middleware to check both session store and API token store. Add Scope type for bot-specific authorization.

8

Update context propagation + EventOptionsFromContext

Add WithActor/ActorFromContext and WithImpersonator/ImpersonatorFromContext to root context.go. Extend EventOptionsFromContext to propagate actor chain into event metadata.

9

Generalize Authz to use ActorID + TenantID

Update Authz.Enforce to accept ActorID and TenantID instead of raw strings. Update CasbinProjection to derive policies from Membership events. Bridge old UserID-based callers via adapter functions.
