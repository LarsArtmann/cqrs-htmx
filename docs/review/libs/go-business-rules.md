## What it is

Severity-aware validation for Go: rules return the *degree* of failure (Info / Warning / Error / Critical — `Severity` re-exported from go-finding) instead of pass/fail. One runtime dependency (go-finding), GOEXPERIMENT=jsonv2 required (Go 1.27+). Surface map: the `Rule` interface (`Name/Check/Severity/Message`) with immutable `RuleImpl` builders (`WithName/WithSeverity/WithMessage/WithDescription/WithTags`); ~50 pre-built builders across numeric/string/collection/time (`builders_time.go`, injectable "now")/network (`builders_network.go` — Luhn credit cards, E.164-ish phones, postal codes)/precision/format classes; composites (`All/Any/When/Not/Or/Xor`); the `NewValidator()` fluent builder producing a `ValidationResultError` with per-severity filtering, `Merge`, `ForEach`, JSON marshaling; observability via synchronous listeners (`RuleEvaluated`/`ValidationCompleted` events) and a concurrent `Stream` mode (`ContextRule`, `WithConcurrency`) for I/O-bound rules. Nested modules: `adapters/cqrslite` (publishes validation events onto a go-cqrs-lite event bus as durable, CBOR-safe domain events — `businessrules.rule.evaluated.v1` / `businessrules.validation.completed.v1`), `listeners/otel` (OTel spans/metrics), `examples/sse` (Datastar live feed). Checkout HEAD `53473a3` = `v2.2.1-5-g53473a3`; `[Unreleased]` is a Go-toolchain-floor raise to 1.27 only — no API pending. Upstream hygiene note: v2.2.1 was CI/chore/dependency work with no CHANGELOG section, and `doc.go:135` still says `Version = "2.2.0"`.

## How cqrs-htmx's rule surface looks today (why 0 import sites is correct)

- **Domain rules ARE deciders.** identity-model and legalparty-model express invariants as event-sourced decide functions — `legalparty-model/decider.go:16` (`LegalPartyDecider()`) and the fold/decide pairs — that either emit events or reject with typed errorfamily sentinels (identity-model/errors.go carries 28 `NewRejection`/`NewConflict` constructor lines). The outcome set is deliberately binary: accept-and-emit vs reject-with-code; there is no warning-tier or advisory-tier outcome anywhere in either model (verified: no `warning`/`Warning` outcome vocabulary in their non-test sources).
- **Edge validation is binary too.** Decode/validation at the transport edge wraps into ONE rejection code (`cqrshtmx.validate.failed`, huma/options.go:235) with field context for the UI; a severity ladder would have nothing to feed.
- **Declarative rule documentation + spec-test generation already has an owner.** `gfl-usermgmt/` is the executable-spec case study: `usermgmt.gfl` (graph-features-language — features, owners, event expectations, rejection codes per aggregate) generates the scenario tests (`usermgmt_test.go:1` "generated by gfl generate tests") that pin decider behavior — the documentation-and-tests job a rule library might otherwise be recruited for.
- **Format-class checks are hand-rolled canonical parsers.** legalparty-model's registry facts parse via go-legalparty-backed aliases (`aliases.go:15-20` — `ParseLEI`/`ParseVATID`/`ParseTaxNumber`/…), which own the canonical semantics businessrules' generic format builders would only approximate.

## Why cqrs-htmx should NOT adopt it

The library positions itself as the business-validation layer above structural validators (README.md:101-105: "businessrules complements type/format validators … Structural: type, format, required fields / Business: domain rules, severity levels"). This repo's business rules do not live in a pre-dispatch validation layer at all — they live inside event-sourced deciders whose only outcomes are emit-or-reject, documented and spec-tested by gfl scenarios. Adopting a severity-graded validation runner alongside that would create a second, competing rule-expression substrate with no warning-tier consumer to justify it. The [docs/LIBRARY_INTEGRATIONS.md](../../LIBRARY_INTEGRATIONS.md) (2026-05-13, superseded) suggestion — "add example showing validation in command mapper" — was optional/educational and never executed; this report supersedes it with an evaluated not-adopted verdict.

## Flip conditions

1. **A severity-graded outcome need appears in a domain** — the concrete shape: legalparty-model registry facts growing a warn-but-allow tier (e.g. "VAT checksum invalid" = reject vs "registry record not yet verified" = warn/proceed), or any consumer asking for advisory-tier feedback on a command. That need does not exist today and is the first thing to re-check.
2. **Rule reuse across modules as data** — a second model wanting to import another's rule set as composable rule values (deciders share state machines, not rules; gfl shares documentation, not runtime).
3. **Validation-run audit as domain events** — a consumer ask to persist pre-dispatch validation runs onto the event bus (`adapters/cqrslite` exists precisely for this repo's stack and would be the entry point).

None of the three is on any TODO/ROADMAP row today; re-ask, don't re-verify.
