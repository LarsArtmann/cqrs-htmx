## What the library is

Live route discoverability for `http.ServeMux`: `*http.ServeMux` cannot enumerate its patterns, so `Registry.Handle/HandleFunc` mount a route on the mux AND record it in one declaration (the registry, not the mux, is the source of truth); `Register` mounts `GET /endpoints`, which serves the recorded routes as a self-describing listing — content-negotiated per RFC 9110 §5.3 from `Accept` (browsers get an HTML table, API clients JSON), one URL with `Vary: Accept`, `no-store`, never 406 (falls back to JSON), never panics (mux rejections surface as errors), and atomic snapshots so routes can be added while a listing serves. Master (unreleased, b785f40) now negotiates across ALL `Accept` header lines, not just the first — a second line can raise a representation's weight, exactly as RFC 9110 describes.

## Should cqrs-htmx use it?

No — `RoutePostures()` is the better answer for this repo: declared manifests feed drift gates and a behavioral authz matrix (compile/CI-time proof), while `/endpoints` is a display page that proves nothing and would publish a route inventory over HTTP. The one honest seam was evaluated and rejected on the merits: `setup.Mount(mux *http.ServeMux)` (setup/mount.go:35) is the only mux cqrs-htmx owns, and an opt-in `Config.EndpointsListing`-style flag COULD thread an `endpoints.Registry` through it — but per capability #2 the registry would capture only layer-granularity rows that `RoutePostures()` already states with richer columns. If a live listing is ever asked for, the right shape is rendering `Bundle.RoutePostures()` (posture + `Why` included) at an opt-in, session-gated path — stdlib-only, no new dependency, no information cqrs-htmx doesn't already declare. Until that ask exists: no adoption, no TODO row. (The 2026-11-15 B13/B14 QUERY + OpenAPI consumer work and the 2026-11-21 CSP-knob wave both passed this seam without a flip trigger firing.)
