Module Integration & Full-Stack Composability

How well do cqrs-htmx's 21 composable sub-modules integrate with each other, and should the library offer a prebundled "full-stack" model that includes samber-do-auditlog and go-health-dashboard?

00Executive Summary

cqrs-htmx has excellent internal module hygiene: clean dependency direction (identity-model ← usermgmt ← root, zero cycles), interface-driven seams (auth strategies via structural typing, Enforcer duck-typing), and 21 independently versionable Go modules. The architecture is fundamentally sound.

However, the library has a composition gap: while individual modules are superbly decoupled, there is no wiring layer that helps consumers compose them. A consumer wanting admin panel + CQRS dashboard + login page + health checks must manually wire ~37 lines of boilerplate across 5 Config structs, with no adapter from *usermgmt.Service → dashboardui.Config's 12 fields. The FromBundle method referenced in dashboardui's doc comment is vaporware. Two competing Broadcaster types (root vs datastar) add confusion.

Recommendation: Phased Wiring Kit (not a monolithic framework)

Add an optional setup/v4 module that provides convenience adapters and a MountAll helper — without adding any external dependencies to existing modules. External integrations (go-health-dashboard, samber-do-auditlog) go into separate optional modules (health/v4, auditlog/v4) so consumers who don't need them pay zero cost. This respects the library principle ("never enforce defaults consumers might disagree with") while eliminating the wiring tax.

01Current Module Topology

The dependency graph is acyclic and well-layered. Here is the actual import topology:

Layer 0 — Foundation (no cqrs-htmx deps) identity-model/v4 ← pure domain types, fold functions, Authz engine datastar/v4 ← go-datastar + go-sse only (ZERO root/usermgmt dep) Layer 1 — Core Library root (cqrs-htmx/v4) ← App builder, HTMX/SSE, middleware, error mapping NO import of usermgmt (clean boundary confirmed) Layer 2 — Domain Services usermgmt/v4 → identity-model (26 re-export files, deprecated) → root (4 files: error status, event catalog, projection status) usermgmt/{totp,webauthn,oauth2}/v4 → usermgmt interfaces via structural typing Layer 3 — UI Modules (depend on Layer 1 + 2) adminui/v4 → usermgmt (*Service) + root (RecommendedSecurityMiddleware) loginpage/v4 → usermgmt (*Service) only dashboardui/v4 → root (Broadcaster + JournalSSEStore) + go-cqrs-lite NO usermgmt dependency (pure CQRS/ES observability) Layer 4 — Cross-Module Verification integration_test/v4 → ALL modules (16 test files, compile-time + runtime contracts)

Dependency direction is correct

Dependencies always point toward stability (identity-model at the bottom, UI modules at the top). The root → usermgmt zero-import boundary is a deliberate design decision that keeps the core CQRS/HTMX library usable without any user-management dependency. Datastar is architecturally decoupled — it shares only go-cqrs-lite/event types with the rest of the ecosystem.

02Internal Integration Gaps

Six concrete findings where the sub-modules could integrate better with each other. Ordered by impact.

P1 — High Impact

No adapter from *usermgmt.Service to dashboardui.Config

dashboardui/config.go (12-field Config) vs usermgmt/service_core.go (Service holds all 12 internally)

dashboardui.Config requires 12 fields (Journal, EventSource, ProjectionHost, CommandJournal, SnapshotStore, EventBus, etc.) — all of which *usermgmt.Service holds internally but does not expose in a dashboardui-compatible shape. A consumer must manually extract each one. The FromBundle method referenced in dashboardui/dashboard.go:15 is vaporware — it appears only in brainstorming docs and a stale doc comment, never implemented.

Fix Add a standalone adapter function in a new setup/v4 module: setup.DashboardConfig(svc *usermgmt.Service) dashboardui.Config. The Service already exposes Journal(), EventBus(), ProjectionStatuses() — the adapter maps these plus internal fields via accessor methods. Keeps dashboardui dependency-free from usermgmt while eliminating the wiring tax.
P1 — High Impact

No "mount everything" helper — each UI module wired independently

adminui/handler.go, loginpage/handler.go, dashboardui/dashboard.go, usermgmt/http.go

A consumer wanting the full UI experience must manually: (1) create usermgmt.NewAuthHandler(svc) + auth.RegisterRoutes(mux), (2) create adminui.New(adminui.Config{Service: svc, ...}) + panel.Mount(mux, "/admin/"), (3) create loginpage.New(loginpage.Config{Service: svc, ...}) + handler.RegisterRoutes(mux), (4) create dashboardui.New(dashboardui.Config{...12 fields...}) + dash.Mount(mux, "/dashboard/"), (5) wire session middleware + CSRF + HTMX + security headers. That's ~37 lines of boilerplate with no compile-time safety net — a typo in the middleware order silently breaks auth.

Fix Add setup.MountAll(mux, setup.Config{Service: svc, App: app, ...}) in the new setup/v4 module. It mounts all UI panels, auth routes, and returns a struct with handles to each panel for further customization. Optional fields (Admin, Dashboard, Login) control which panels mount. Reduces ~37 lines to ~8.
P2 — Medium Impact

Two competing Broadcaster types with the same name

root: sse_broadcaster.go (cqrshtmx.Broadcaster) vs datastar: broadcaster.go (datastar.Broadcaster)

Both wrap sse.Broadcaster[sse.Event] from go-sse, but they are completely separate types in different packages. A consumer using both HTMX SSE and Datastar patches has two fan-out hubs with no shared abstraction. There is no documentation explaining when to use which, or how to share a single underlying broadcaster.

Fix (a) Document clearly that they are separate by design (HTMX SSE events vs Datastar patches are different wire formats). (b) Expose the underlying *sse.Broadcaster[sse.Event] on both so consumers who want cross-transport fan-out can subscribe to one hub. (c) Consider an interface: type EventBroadcaster interface { Subscribe() <-chan sse.Event; ... } that both satisfy.
P2 — Medium Impact

adminui and dashboardui have non-overlapping observability with no bridge

adminui/handler_audit.go (domain audit log) vs dashboardui/handlers_health.go (liveness/readiness) + handlers_projections.go (projection health)

adminui has domain audit logging (usermgmt.AuditEntry) but no health endpoints. dashboardui has health checks (/-/healthz, /-/readyz), projection health, DLQ management, and time-travel — but no domain audit. Neither knows the other exists. A consumer running both gets two SSE streams, two nonce middleware chains, and no unified observability view.

Fix Add a setup.MountAdmin(mux, opts) that mounts both panels under a shared layout with cross-links (dashboard links from admin, admin links from dashboard). Share the SSE broadcaster and nonce middleware. Longer term: add a health-check handler to adminui (delegating to dashboardui's or go-health's).
P2 — Medium Impact

No full-stack example — the composition is unproven

examples/ (9 examples, none wire adminui + dashboardui + loginpage together)

The 9 existing examples each demonstrate one slice: basic (root only), admin-demo (adminui + usermgmt + totp), dashboard-demo (dashboardui + go-cqrs-lite), datastar-demo (datastar only), samber-do-demo (DI wiring, but no UI modules). No example wires all UI modules together. This means the composition is unproven and integration friction is invisible. The samber-do-demo even discards the resolved *cqrshtmx.App with _ = app.

Fix Create examples/fullstack-demo/ that mounts: root App + usermgmt Service + totp/webauthn + adminui + dashboardui + loginpage + SSE broadcaster + samber/do container. This is the single highest-leverage action: it proves composition, surfaces integration friction, and serves as the copy-paste template for real apps.
P3 — Polish

integration_test doesn't verify the full UI stack

integration_test/ (16 test files, none mount adminui/dashboardui/loginpage)

integration_test verifies auth interfaces, error sentinels, CSRF composition, catalog compilation, typed dispatch — all contract-level. But no test mounts adminui, dashboardui, or loginpage against a real Service/App. There is no test verifying that usermgmt.Service.ProjectionStatuses() actually feeds cqrshtmx.ProjectionStatusHandler correctly end-to-end.

Fix Add a fullstack_test.go to integration_test that mounts all UI modules and verifies: (1) admin panel renders with a seeded user, (2) dashboard shows projection health from the real Service, (3) login page renders correct auth buttons based on Service config.

03Should We Offer a Full-Stack Bundle?

The question: should cqrs-htmx offer a prebundled "full-stack" model that includes samber-do-auditlog (DI audit logging + HTML visualization) and go-health-dashboard (real-time health dashboard)?

Short answer: Yes, but as optional integration modules — never as hard dependencies.

The ecosystem is already aligned (all use Go 1.26.5, GOEXPERIMENT=jsonv2, samber/do v2, templ-components, go-sse, httputil, flake.nix). The integration surface is natural. But bundling them into existing modules would violate the library principle and explode the dependency tree.

The Case For

1. Wiring is non-trivial

go-health-dashboard needs a *health.Probe, which needs a do.Injector with registered services. samber-do-auditlog needs do.HookProviders passed to the injector. Mapping usermgmt's ProjectionStatusProvider to go-health's check interface is non-obvious. A wiring kit eliminates this tax.

2. Demand signal exists

The samber-do-demo status doc (docs/status/2026-08-09_05-12) explicitly lists "samber-do-auditlog integration" and "go-health integration" as gaps. go-health-dashboard already demonstrates the pattern with its Register(injector, probe, opts...) convenience function.

3. Observability gap is real

cqrs-htmx has no built-in health endpoint (dashboardui's /-/healthz is CQRS-specific, not kubelet-grade). go-health-dashboard gives /healthz, /readyz, /startupz with Datastar SSE real-time updates. samber-do-auditlog gives DI lifecycle visualization. Both are production-grade concerns.

4. Clean integration surface

go-health-dashboard accepts nonce values (strings), not nonce infrastructure. samber-do-auditlog hooks into do.Injector hooks. Neither requires cqrs-htmx to change its internals. The integration is pure wiring, not coupling.

The Case Against (Hard Dependency)

1. Dependency explosion

go-health-dashboard pulls: templ, templ-components, go-datastar, go-sse, go-health, samber/do. If bundled into root, every consumer — even those who only want CQRS dispatch — gets these transitively. This is the exact problem go-health-dashboard's own README warns about.

2. Library principle violation

cqrs-htmx's #1 principle: "Never enforce defaults consumers might disagree with." A hard dep on go-health-dashboard enforces Datastar + templ + go-health on every consumer. Many consumers use HTMX (not Datastar) or have their own health-check infrastructure.

3. Versioning coupling

cqrs-htmx is v4 with 21 modules and a complex release flow (local replaces, cross-module version drift). Coupling releases to go-health-dashboard (v0.2.0) and samber-do-auditlog (beta) adds coordination overhead and blocks independent releases.

4. Unnecessary for root-only consumers

Path A consumers (root App only, no user management) are the majority use case. They need zero of this. The bundle must be opt-in, not default.

The Right Design: Optional Integration Modules

The solution that satisfies both sides: separate optional Go modules that depend on both cqrs-htmx internals and the external library. Consumers who want the integration go get one module; everyone else pays nothing.

Wrong: Hard Dependency
Right: Optional Module
// root go.mod — EVERYONE pays
require (
  go-health-dashboard  // +templ, +datastar, +go-health
  samber-do-auditlog   // +samber/do (already there)
)
// health/v4/go.mod — only consumers who opt in
require (
  cqrs-htmx/v4
  cqrs-htmx/usermgmt/v4
  go-health-dashboard
)
// everyone else: zero cost

Proposed Module Layout

cqrs-htmx/setup/v4 (NEW — internal wiring, zero external deps) → root, usermgmt, adminui, dashboardui, loginpage Provides: DashboardConfig(svc *usermgmt.Service) dashboardui.Config MountAll(mux, opts MountAllConfig) *MountedPanels FullstackConfig struct (bundles all Configs) cqrs-htmx/health/v4 (NEW — go-health + go-health-dashboard integration) → usermgmt, go-health, go-health-dashboard Provides: NewHealthProbe(svc *usermgmt.Service, opts ...) *health.Probe NewHealthDashboard(probe, opts ...) *dashboard.Dashboard ProjectionHealthCheck(svc) health.Check (bridges ProjectionStatusProvider) cqrs-htmx/auditlog/v4 (NEW — samber-do-auditlog integration) → root, usermgmt, samber-do-auditlog Provides: WithAuditLog(opts ...) []do.HookProvider RegisterAuditLogPanel(mux, report) (mounts the HTML report viewer)

Why three modules instead of one?

Each external integration has its own dep tree. A consumer who wants health checks but not DI audit logging should not pull samber-do-auditlog's dependencies. Three modules = three independent opt-in points. This mirrors how cqrs-htmx already separates usermgmt/totp, usermgmt/webauthn, and usermgmt/oauth2 — each auth strategy is its own module.

Overall: 4.4/5 — Good

Architecture is fundamentally sound. The only dimension below 4 is Composability (3/5) — not because modules can't compose, but because the library provides no help composing them. The action roadmap targets this dimension exclusively. Addressing it would bring the overall score to ~4.7/5.

05Action Roadmap

Seven concrete steps, ordered by impact-to-effort ratio. Dependencies noted where they exist.

1

Create examples/fullstack-demo/ — the kitchen-sink proof

Effort: M (~4hr) · Impact: High · Dep: none
Mount root App + usermgmt Service + totp + adminui + dashboardui + loginpage + SSE in one runnable example. This is the single highest-leverage action: it proves composition, surfaces every integration friction point, and becomes the copy-paste template. Do this FIRST — it will inform the design of the setup module.

2

Create cqrs-htmx/setup/v4 module with internal wiring adapters

Effort: M (~6hr) · Impact: High · Dep: Step 1 surfaces the friction
New Go module: setup.DashboardConfig(svc) dashboardui.Config, setup.MountAll(mux, opts) *MountedPanels, setup.FullstackConfig struct. Zero external dependencies — depends only on internal siblings (root, usermgmt, adminui, dashboardui, loginpage). Add to go.work. The flake.nix forEachGoModule apps pick it up automatically.

3

Document the Broadcaster duality and expose underlying sse.Broadcaster

Effort: S (~2hr) · Impact: Medium · Dep: none
Add a Broadcaster.Raw() *sse.Broadcaster[sse.Event] method (or equivalent) to both root and datastar modules. Write a short guide (docs/guides/sse-and-datastar.md) explaining when to use which and how to share a fan-out hub for cross-transport scenarios.

4

Add fullstack integration test to integration_test/

Effort: S (~3hr) · Impact: Medium · Dep: Step 1 or 2
Mount all UI modules against a real Service. Verify: admin panel renders with seeded user, dashboard shows projection health, login page renders correct auth buttons. This locks the composition contract.

5

Create cqrs-htmx/health/v4 module — go-health + go-health-dashboard integration

Effort: M (~6hr) · Impact: High for production users · Dep: none (independent)
New Go module bridging usermgmt projection health → go-health checks. health.NewProbe(svc, opts) auto-registers usermgmt's ProjectionStatusProvider as a health check. health.NewDashboard(probe, opts) returns a *dashboard.Dashboard pre-configured with the same nonce extractor and security posture as adminui/dashboardui.

6

Create cqrs-htmx/auditlog/v4 module — samber-do-auditlog integration

Effort: S (~3hr) · Impact: Medium for DI users · Dep: none (independent)
New Go module: auditlog.WithAuditLog(opts) []do.HookProvider for one-line DI audit logging. auditlog.MountReport(mux, report) for the HTML visualization. This closes the gap explicitly noted in the samber-do-demo status doc.

7

Write docs/guides/fullstack-wiring.md — the integration guide

Effort: S (~2hr) · Impact: High for discoverability · Dep: Steps 2, 5, 6
Single guide showing the 4 integration paths (setup-only, +health, +auditlog, full-stack). Decision tree: "do you need health checks? → add health/v4". Cross-link from README and SKILL.md. This is the discoverability layer that makes the optional modules findable.

Pareto insight: Steps 1-2 deliver 80% of the value

The fullstack example (Step 1) and the setup module (Step 2) together eliminate the composition gap for the majority of consumers. Steps 5-6 (health, auditlog) are high-value for production users but can ship independently. Step 7 ties it together with documentation. All steps are additive — none changes existing modules or breaks consumers.

06Architectural Strengths

+
Zero import cycles across 21 modules The dependency graph is a clean DAG. identity-model at the bottom, UI modules at the top, integration_test as the verification layer.
+
Interface-driven seams everywhere Enforcer duck-typing (no casbin import in root production code). Auth strategies via structural typing (totp/webauthn/oauth2 don't import usermgmt). dashboardui capability detection (panels auto-activate based on which interfaces you provide).
+
Root → usermgmt zero-import boundary The core CQRS/HTMX library is usable without any user-management dependency. This is the library's most important architectural property — it makes the root module usable by anyone, not just apps that need auth.
+
Compile-time contract verification integration_test/assert_test.go verifies auth strategies satisfy usermgmt interfaces at compile time. This prevents accidental interface drift across independently versioned modules.
+
Library principle consistently applied "Never enforce defaults consumers might disagree with." No mandatory CSP/HSTS/CSRF — all opt-in. No built-in router. No hard dependencies on observability stacks. This makes the library safe to adopt incrementally.
+
dashboardui is decoupled from usermgmt by design This allows the CQRS observability dashboard to work with ANY event-sourced system, not just usermgmt. It's a feature, not a bug — the wiring adapter (Step 2) is the missing piece.
