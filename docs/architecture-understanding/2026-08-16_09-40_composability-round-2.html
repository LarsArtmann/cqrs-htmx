00Summary

The 2026-08-09 review asked "how do the sub-modules integrate?" and its answer was executed: setup.New(Config) composes service + three panels + health in one call, health/ and auditlog/ bridge external ecosystems without touching core, and the SSE broadcasters share raw hubs across transports. The composability question has moved up a level: the remaining friction is no longer whether modules compose but whether consumers can inject their own advanced constructions — a service built with SecurityHooks or MaxUsers, a custom SSE topology — without forking the composition root. This session shipped exactly those three seams, each test-verified hermetically.

The bottom line Rubric average 4.3/5 ("Good"). The architecture is no longer the bottleneck for composition. The two live risks are external: a broken published tag (storage/v4 v4.7.0, re-pinned to v4.6.0 here) and a self-inconsistent sibling master (go-cqrs-lite metaengine/planner.go) that keeps workspace-mode builds red until it is fixed upstream.

01Findings

Ordered by impact. The first three were shipped and verified during this review (see section 02); the rest form the forward roadmap, harvested into TODO_LIST.md.

P0 · Fixed this session

Advanced service construction was impossible to combine with the composition root

setup/setup.go New() · usermgmt/service_core.go · ServiceConfig

setup.New always built the service itself from a subset of ServiceConfig (10 of 30+ fields). Consumers needing SecurityHooks, MaxUsers, snapshot stores, custom AuditLog, or checkpoint stores had to choose: hand-wire ~37 lines of panels and middleware, or give up their advanced config. The composition root and the full service surface were mutually exclusive.

Fix: shipped (a) Service.Journal() / Service.EventBus() accessors expose the exact infrastructure a built service publishes to. (b) setup.Config.Service adopts an already-constructed service: the bundle sources Stores from the accessors, mounts all panels on top, and never closes what it did not build. Conflicting construction fields are rejected loudly, not ignored. See section 02.
P1 · Fixed this session

No shared SSE endpoint — every consumer hand-rolled the bus-to-SSE bridge

dashboardui/sse.go startEventBridge · (pattern copied per app)

The event-bus → SSE bridge (subscribe, envelope JSON, heartbeat-free pump) existed only inside dashboardui, unexported. Applications wanting a live feed of domain events for their own UI copied the bridge by hand — duplication of both code and security decisions (is your feed gated?).

Fix: shipped setup.Config.SSEPath mounts a session-gated (401 without auth) shared endpoint streaming every committed event as the same JSON envelope dashboardui uses. Bundle.Broadcaster exposes the hub for custom fan-out, replay wiring, or Raw() hub-sharing with DataStar. Validated in the path guards (shape, root reservation, distinctness). See section 02.
P0 external · Mitigated here, fix belongs upstream

Both build modes were red at HEAD: broken published tag + broken sibling master

storage/v4@v4.7.0 sql/keyset.go:43 · go-cqrs-lite metaengine/planner.go:137

The 07:43 dep sweep bumped five modules onto storage/v4 v4.7.0, a tag that does not compile (assigns an undeclared err) — hermetic (GOWORK=off) builds failed. Simultaneously the sibling go-cqrs-lite master carries a committed inconsistency in metaengine (newIdempotencyTracker() called with no arguments against an int-taking signature), breaking workspace-mode builds via the go.work replace.

Fix: mitigated locally, flagged upstream usermgmt, adminui, loginpage, setup, systemadapter re-pinned storage/v4 to the last-good v4.6.0 with a cqrs-lint-suppressed justification comment. Upstream actions needed: go-cqrs-lite repairs master's metaengine call site and publishes a corrected storage tag (or retracts v4.7.0).
P1 · Open

ServiceConfig is a 30+-field god-config; setup mirrors a drifting subset

usermgmt/service_core.go:75-160 · setup/config.go

ServiceConfig grew by accretion (stores, TTLs, eviction knobs, per-strategy session stores). setup.Config re-declares 10 of those fields, so every new ServiceConfig capability re-opens the "add to setup too?" question — exactly the drift the adoption seam now lets consumers route around, but the duplication itself remains for the default path.

Recommendation Long term: collapse setup's mirrored fields into ServiceConfig usermgmt.ServiceConfig embedded in setup.Config (one source of truth, one place to add fields), or introduce functional options on NewService. The adoption seam makes this a non-breaking migration: advanced consumers already bypass the mirror.

02Shipped this session — verified

Three composition seams, each implemented, documented (setup README + doc.go), and covered by tests run hermetically (GOWORK=off, the same mode the nix gates use).

Seam 1 · usermgmt

Service.Journal() / Service.EventBus()

usermgmt/service_core.go · service_infrastructure_accessors_test.go

The service now exposes the exact event.Store and event.Bus it was built with. Consumers wiring projections, read models, or SSE on top of an existing service no longer re-track ServiceConfig values. Tests assert instance identity for both explicit and defaulted infrastructure.

Seam 2 · setup

setup.Config.Service — bring your own

setup/setup.go · setup/composability_test.go

Adoption is pointer-identity verified; Stores wire from the accessors; panels mount on the adopted service; conflicting construction fields are rejected with a named-fields error; and Bundle.Close demonstrably leaves the adopted service functional (a user registers through it post-Close). Lifecycle ownership stays with the caller — documented in the field comment, the README, and doc.go.

Seam 3 · setup

setup.Config.SSEPath + Bundle.Broadcaster

setup/sse.go · setup/mount.go · composability_test.go

One field mounts a session-gated SSE feed of every committed event (dashboardui-compatible JSON envelope). Tests verify the 401 gate, the bus→hub bridge delivering a real domain event within 5s of Register, opt-in default (no broadcaster unless configured), and full path validation. The hub is exposed for custom payloads and cross-transport sharing.

◆What the target composition looks like now

The seams compose: advanced service construction and the one-call bundle are no longer mutually exclusive. 

// Advanced construction + full bundle + live feed, all together:
svc, err := usermgmt.NewService(usermgmt.ServiceConfig{
    EventStore:    myPostgresStore,          // SeekableJournal
    SecurityHooks: usermgmt.SecurityHooks{...}, // was unreachable from setup
    MaxUsers:      10_000,
})
// ...
bundle, err := setup.New(setup.Config{
    Service: svc,      // adopt — bundle never closes it
    SSEPath: "/sse",   // session-gated live feed of committed events
})
defer func() { _ = svc.Close() }()     // caller owns the service
defer func() { _ = bundle.Close() }()  // bundle owns panels + broadcaster

mux := http.NewServeMux()
bundle.Mount(mux) // /auth /admin /dashboard /sse /health /
// custom real-time payloads ride the same hub:
ch := bundle.Broadcaster.Subscribe()
Why this state is better Every capability of ServiceConfig is now reachable alongside the composition root; real-time event feeds cost one config field instead of a hand-copied bridge; and the ownership contract makes embedding the bundle inside a larger system (samber/do, appkit) free of double-close hazards.
