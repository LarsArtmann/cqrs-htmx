What is excellent

Clean CQRS/HTTP composition model

The App.Command(type, opts...) → http.HandlerFunc pipeline with ordered HandlerOptions is a textbook example of composability. Consumers compose behavior (auth → decode → validate → dispatch → render) without the library dictating router, persistence, or auth model. This is the library's killer feature.

Auth strategy extraction (v4 achievement)

Moving WebAuthn/TOTP/OAuth2 from a single usermgmt module into 3 independent modules behind structural-typing interfaces is exemplary. Consumers import only the strategy they need; the usermgmt core stays auth-agnostic. scripts/check-module-isolation.sh verifies each builds standalone.

Honest module boundaries

12 go.mod files, 8 of which build standalone under GOWORK=off. CI enforces this. Dep budgets are checked (scripts/check-dep-budgets.sh). Replace directives are policed (scripts/check-replace-directives.sh). This is a well-disciplined multi-module workspace.

Library principle upheld

No mandatory CSP/HSTS/CSRF — all opt-in. Framework-agnostic (net/http, Chi, Gin). Duck-typed interfaces (Enforcer ← casbin, TemplComponent ← templ). Consumers never fight the library's defaults.

Coupling hotspots & structural debts

High usermgmt file-prefix sprawl — 55 files using es_* prefix

usermgmt has 185 .go files in a single flat directory. 55 use es_ prefix, 21 use service_ prefix. The aggregate prefix is the module. Within es_, there are clear sub-domains (es_bot_*, es_membership_*, es_tenant_*) but they are not separated into packages.

Why it matters: New contributors cannot answer "where does tenant logic live?" without grepping. Coupling between es_membership_decide.go and es_state.go is invisible from package layout.

Fix: Split usermgmt into internal sub-packages: internal/user, internal/membership, internal/tenant, internal/bot, keeping the public Service type in the root. Preserves go.mod boundary; improves navigability.

High service_*.go god-service pattern — 21 files, one Service type

21 files named service_* all attach methods to a single *Service type. service_core.go (432 lines) defines it; service_login.go, service_register.go, service_oauth2.go, service_tenant.go, service_membership.go, service_bot.go, service_impersonation.go, service_misc.go, etc. all extend it. Service has become a god object.

Why it matters: Any change to Service fields forces recompile of all 21 files. The type's responsibilities are unbounded. Hard to test in isolation.

Fix: Extract focused services that compose into the top-level Service: UserService, TenantService, MembershipService, BotService, OAuth2Service, SessionService. The facade Service embeds them for backward compat.

Medium App.Command/App.Query duplication (app.go:201-256)

90% identical bodies (build cfg, enrich, dispatch). Already flagged in code-quality scan. Extract a shared dispatchHandler helper parameterized by dispatcher + nil-sentinel.

Medium go.work local replace directives — upstream publishing bug

go.work contains replace directives pointing all go-cqrs-lite modules to /home/lars/projects/go-cqrs-lite/*. The comment block (added 2026-07-18) documents that 13 of ~40 go-cqrs-lite submodule tags still use broken zero pseudo-versions despite the v4.0.1+ releases. The replaces are therefore still required for local development.

Why it matters: Every developer who clones this repo without the sibling checkout hits confusing build failures. CI works because it runs GOWORK=off, but local go test ./... in the workspace requires the sibling repo.

Fix (upstream): Cut a clean consolidated go-cqrs-lite release (v4.0.3+ or v4.1.0) from a tree where every submodule go.mod has been go mod tidy-resolved against real published versions, then drop the replaces. Tracked separately.

Medium examples/datastar-demo — 5 files, no go.mod hygiene shown

One example uses Datastar instead of HTMX. It is the only example without a README. Mixed messages for a library branded "cqrs-htmx". Either (a) document it as "Datastar works too, here's how" or (b) move to a separate repo to keep brand clear.

Low CI version skew — local golangci-lint v2.12.2 vs CI v2.11

Local runs show 187 root issues; CI passes. The 0.0.x version skew plus the depguard misconfiguration (see code-quality-scan) means lint is not actually gating anything meaningful in root. Submodules are clean.
