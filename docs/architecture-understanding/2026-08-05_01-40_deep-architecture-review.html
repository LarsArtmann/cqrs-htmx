ARCHITECTURE REVIEW · 2026-08-05

Deep Architecture Review

An evidence-based assessment of modularity, coupling, composability, and service-orientation across the cqrs-htmx multi-module Go library workspace.

19 Go modules ~30.3k prod LOC 0 import cycles Verdict: Good (4.0/5)

This review maps the full structure of the cqrs-htmx workspace, measures coupling and dependency direction against the Stable Dependencies Principle, checks domain alignment against docs/DOMAIN_LANGUAGE.md, and scores all seven architecture dimensions per the assessment rubric. Every finding cites concrete code paths and metrics gathered on 2026-08-05.

Verdict: GOOD (4.0 / 5.0). The architecture is structurally sound: a clean multi-module workspace with zero import cycles, a textbook-correct dependency profile (stable domain core, volatile UI leaves), and standout composability via structural typing and middleware composition. The largest structural debt — the usermgmt god-package and the Service god-object — is already documented and deliberately deferred (ADR-0019 Blocked by Go's method-receiver constraint; ADR-0038 deferred to a coordinated v5 major bump; ROADMAP "Not Planned" with sound reasoning: sub-package extraction within one module yields zero dep-tree benefit without consumer demand). This review's value-add is independent confirmation of those decisions via quantitative coupling metrics, plus the SDP-perfect profile that explains why the architecture is healthy despite the debt. The genuinely open items are the Casbin port and re-export-layer retirement.

Coupling metrics & instability (Stable Dependencies Principle)

Instability I = Ce / (Ca + Ce). I=0 = maximally stable (dependents only); I=1 = maximally volatile (dependencies only). The SDP rule: dependencies must point toward stability (lower I).

This is a textbook SDP-correct profile. Dependencies monotonically point toward lower instability: the stable foundation (root, identity-model) sits at I=0 and the volatile presentation leaves (adminui, loginpage, dashboardui) sit at I=1. No dependency points "up" the stability gradient. This is the single strongest property of the architecture.

03Dependency Direction

Strength

Domain layer is infra-clean (with one exception)

identity-model/*.go (23 prod files)

The pure domain module imports no net/http, database/sql, or framework packages. It depends only on go-cqrs-lite/event, go-error-family, go-branded-id, and the standard library. Clean ports are defined as interfaces in identity-model/interfaces.go (TOTPProvider, WebAuthnProvider, OAuth2Provider, store interfaces) using only primitive types so implementations need not import the domain. This is dependency inversion done right.

Tradeoff

Casbin is a concrete dependency in the domain, not behind an interface

identity-model/authz.go — type Authz struct { enforcer *casbin.Enforcer }

Authz directly embeds *casbin.Enforcer (a concrete third-party struct). The domain package cannot compile without Casbin on the build path. This is documented as intentional ("Casbin is a first-class dependency"), and the blast radius is well-contained: only one file (authz.go) imports casbin; the rest of the workspace depends on the Authz type, not on Casbin directly. Still, it is the single dependency-direction violation — the domain owns a concrete policy engine rather than an Enforcer port.

Strength

Root → siblings boundary is genuinely clean

root *.go (51 prod files)

The root module imports zero cqrs-htmx sibling modules in production code (verified: the only mention of usermgmt is a doc comment in doc.go). Root test files also import zero siblings. The downstream coupling (siblings depend on root) is one-way. This is the correct library shape: the core never reaches up into consumers.

Quasi split-brain

identity-model has two doors via the usermgmt re-export layer

usermgmt/id.go, errors.go, events.go, ... (26 alias files)

26 of usermgmt's production files are pure re-exports of identity-model types (type UserID = identitymodel.UserID, var aliases for fold functions, constructor wrappers). Because these are type aliases (=), the two paths refer to the same type — this is NOT a true split brain (no duplicate definitions). But it inflates usermgmt's exported surface to 819 symbols and gives consumers two equivalent import paths for every domain type. The re-export layer is a deliberate backward-compat migration shim; the risk is that it never gets retired.

05Strengths

What already works well — preserve and replicate these patterns.

+
Structural typing for auth strategies The three auth modules (totp/webauthn/oauth2) have zero internal imports. They satisfy identity-model interfaces via structural typing, so any implementation can be swapped without recompiling the consumer. Exemplary dependency inversion.
+
Composable middleware & builder pattern The go-cqrs-lite dispatchers passed to Config implement Use(mw ...), so all 27 middleware factories (logging, retry, circuit breaker, OTel, idempotency) compose with zero glue. Combined with the HandlerBuilder and Config builder pattern, new features combine existing pieces. This is why Composability scores 5.
+
Low change ripple The last 15 commits touch 1–10 files each, almost entirely within a single module (e.g. dashboardui pagination). No "small feature, 5+ packages" smell. Module boundaries successfully localise change.
+
Duck-typed external libraries Enforcer (Casbin), TemplComponent (templ), and auth provider interfaces are defined locally against the consumer's needs. Consumers import only the external library they actually use — the library never forces a framework.
+
Opt-in everything (library principle) No mandatory CSP/HSTS/CSRF. Everything is opt-in so consumers never fight enforced defaults they disagree with. This is the right posture for a library/SDK.
+
Decided & documented architecture 45+ ADRs, a domain glossary, and per-module CHANGELOGs mean the architecture is recorded, not implicit. Naming is consistently domain-driven (no util/common/helpers grab-bags).

06Findings

Known · ADR-0019/0038

usermgmt god-package — acknowledged debt, deferred to v5

usermgmt/*.go — 91 prod files, 10,464 LOC, 819 exports, single package

Finding (independently confirmed): Every file declares package usermgmt, fusing event-sourcing internals (38 es_* files), the Service (10 files), SQL infra (7 files), HTTP presentation (7 files), and 26 alias shims with no package-level encapsulation. This is the lowest dimension (Cohesion 3/5).

Already decided: ADR-0019 records that decomposition is blocked by Go's method-receiver constraint — *Service methods must live in the package where Service is defined, so a naive sub-package move is illegal. ADR-0038 proposes full decomposition and defers it to a v5 major bump. ROADMAP "Not Planned" argues (correctly) that sub-packages within one Go module yield zero consumer benefit (same go.mod = same transitive dep tree); only separate Go modules reduce deps, and no consumer has asked. Decomposition triggers are documented (consumer needs a subset, >30% divergent deps, compile-time pressure at ~3s — currently none met).

Recommendation: respect the deferral, keep the seams clean. Do NOT split now — it would break the method-receiver contract with no consumer payoff. The current "clean seams between aggregates, separate files per concern" organisation is the right holding pattern. Action: keep the es_* / service_* / sql_* prefix discipline intact so the v5 module split (when triggered) is mechanical. This review confirms the existing decision.
Known · ADR-0038

usermgmt.Service god-object (74 methods) — deferred to v5

usermgmt/service_*.go — 74 methods across 10 files, 38 struct fields

Finding (independently confirmed): *Service exposes 74 methods (up from the ~52 recorded in ADR-0038 on 2026-07-19) fusing ≥6 contexts: auth, bot, impersonation, login, membership, oauth2, register, tenant, misc, core. The trend confirms the ADR's observation that every new feature extends the same type.

Already decided: ADR-0038 proposes decomposition into focused services sharing dependencies via composition, deferred to a v5 bump for the same method-receiver reason. The growth since the ADR (+22 methods) validates the deferral rationale: the debt is real and growing, but bounded by the v5 boundary.

Recommendation: track the growth, defer the fix. This is the reason Scalability caps at 4/5. No v4 action beyond keeping the per-file grouping intact. When v5 lands, execute ADR-0038's service decomposition alongside the module split.
P2 · Medium

Casbin is concrete in the domain layer

identity-model/authz.go — enforcer *casbin.Enforcer

Finding: The domain package embeds a concrete Casbin enforcer rather than defining an Enforcer port. Coupling is contained to one file, but the domain cannot compile without Casbin.

Impact: Low today (Casbin is a sound choice and the contract is narrow), but it makes the domain non-substitutable and is the sole dependency-direction blemish in an otherwise SDP-perfect graph.

Recommendation (judgment call) Define a minimal Enforcer interface in identity-model covering only the methods Authz calls, and have Authz depend on the interface. Default to the Casbin implementation. This is a P2, not urgent — flag it as an accepted tradeoff if Casbin-lock-in is intentional.
P3 · Low

The 7-file-per-aggregate ritual resists feature scaling

usermgmt/es_{bot,membership,tenant}_{commands,decide,dispatch,events,readmodel,state}.go

Finding: Adding a new aggregate to usermgmt requires touching ~7 files following the es_X_* pattern. This is consistent (good) but mechanical and repetitive.

Recommendation Either accept the ritual as the cost of explicit CQRS structure, or introduce a codegen/template for new aggregates. Low priority — consistency already makes it predictable.
P3 · Low

Re-export layer has no retirement path

usermgmt/id.go, events.go, errors.go, ... (26 alias files)

Finding: The 26 identity-model alias files inflate usermgmt's surface to 819 symbols and offer two import paths per domain type. They are backward-compat shims with // Deprecated: markers on some, but no end-of-life plan.

Recommendation Document a deprecation timeline and direct new consumers to import identity-model directly. Track via the docs-health HARVEST process.

07Action Roadmap

Ordered by leverage and dependency constraints. Each step is traceable to a finding above.

1

Split usermgmt into layer sub-packages P1 L

Move es_* internals into usermgmt/es (unexported), sql_* into usermgmt/store, and *_http.go into usermgmt/http. Keep the top-level package as the public facade (Service, Config, setup structs). Type aliases preserve the public API — no consumer breaks. Do this first: it unblocks steps 2–4 and is the highest-impact single change. Effort driver: mechanical file moves + import rewriting across 91 files.

2

Decompose the Service god-object P2 M

Extract focused services (User/Membership/Tenant/Bot/Auth) that compose shared dependencies. Top-level Service embeds or holds them. Reduces the 74-method surface and makes each context independently testable. Depends on: step 1 (sub-services belong in sub-packages).

3

Interface the Casbin dependency (or accept & document) P2 S

Define a narrow Enforcer port in identity-model and default to the Casbin implementation, OR record an ADR accepting Casbin as an intentional domain fixture. Either resolves the open dependency-direction question decisively.

4

Plan the re-export layer retirement P3 S

Set a deprecation timeline for the 26 identity-model alias files, update examples to import identity-model directly, and track residual usage. Harvested from this review into TODO_LIST/ROADMAP via docs-health.

5

Optional: aggregate scaffold/codegen P3 M

Reduce the 7-file-per-aggregate ritual with a template generator. Only if adding new aggregates becomes frequent. Otherwise the explicit CQRS structure is fine as-is.

No P0 findings. The architecture is not actively blocking development and there are no production incidents caused by structure. The roadmap is debt pay-down and polish, not emergency repair.
