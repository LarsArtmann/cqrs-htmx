DataStar Beyond the Adapter

00Summary

DataStar support in cqrs-htmx is currently a single, deliberately thin adapter module (datastar/v4, ~700 LOC of production code): script serving, signal decoding, a response builder, a replay-capable broadcaster, and an EventBridge. The ready-made UI panels (adminui, dashboardui, loginpage) are HTMX-only. The interesting finding is that dual HTMX + DataStar support already works today at the transport layer: both broadcasters embed the same go-sse fan-out hub, and the coexistence pattern is documented in docs/guides/sse-and-datastar.md.

The bottom line Extending DataStar is not a transport problem (solved) but a per-panel rendering problem. The highest-value moves are cheap: a first-class setup option that mounts DataStar alongside HTMX on one shared hub, and documentation of the route-split pattern. Converting the existing panels to dual-mode rendering is the expensive, lowest-value path and should not be done speculatively.

02Benefits of Wider DataStar Support

Benefit · UX

1. Client-side reactive state without a SPA

DataStar signals give login and admin forms client-side validation and instant feedback, eliminating server roundtrips that HTMX requires for every interaction. ROADMAP estimates the loginpage conversion at ~3h precisely because the surface is small.

Benefit · Footprint

2. One 11.76 KiB file replaces four pieces

DataStar subsumes what the root module currently ships separately: htmx core (2.0.10), the SSE extension, idiomorph, and hand-rolled JS. A DataStar-native consumer needs only datastar.js from ds.ScriptHandler().

Benefit · Architecture fit

3. SSE-first matches CQRS/event-sourcing

DataStar's philosophy — backend as source of truth, SSE as default transport, no optimistic updates — is identical to this library's event-sourced model. dashboardui's projection-health panel is the natural showcase: signal patches instead of polling.

Benefit · Resilience

4. Built-in reconnect replay

NewBroadcasterWithReplay gives a bounded ring buffer with Last-Event-ID backfill out of the box. The ROADMAP's "offline sync evaluation" item asks whether this can simplify or replace parts of sync-worker.js/sync-client.js.

Benefit · Ecosystem

5. Differentiation and consumer choice

The library principle is "never enforce defaults consumers might disagree with." Offering a first-class DataStar path widens the addressable audience (the DataStar community is active and Go-friendly) without taking anything away from HTMX consumers.

Benefit · Maintenance

6. The whole stack is in-family

go-datastar and go-sse are LarsArtmann libraries. There is no third-party SDK risk; the starfederation SDK was already fully replaced (datastar CHANGELOG, v4.1.0).

03Can Both Be Supported?

Yes. Three models, in increasing order of coupling and cost:

Model How Cost Verdict
A. Route-split coexistence HTMX endpoints and DataStar endpoints on different routes, one shared hub via NewBroadcasterFromHub. Zero — works and documented today Ship it (docs)
B. Dual-mode handlers Each handler detects HX-Request vs DataStar and renders either an HTMX fragment/headers or a patch stream. High — two response shapes per handler, doubled test matrix, contradicts "impossible states unrepresentable" Avoid
C. Parallel panel variants adminui stays HTMX; separate DataStar-native panels (the ROADMAP's dashboardui/adminui/loginpage variant items). Medium — ~17h total per ROADMAP estimates Only on demand
Key insight The transport duality is already solved by the hub. What remains is a rendering decision per UI surface — and rendering is where the cost lives, not in SSE.

What extending DataStar support could concretely look like, ordered by value per hour:

bundle, _ := setup.New(setup.Config{

// One hub feeds both the HTMX /sse feed and the DataStar feed.

// 3. dashboardui DataStar variant (ROADMAP, ~8h):
//    signal patches replace polling for projection health.

// 4. loginpage signal-based forms (ROADMAP, ~3h).

This is the target Items 1-2 make dual support a first-class, discoverable feature for under a day of work. Items 3-5 stay gated on actual consumer demand, consistent with YAGNI and the library's opt-in principle.

05Risks and Costs

Risk · Maintenance

Two frontend vocabularies in one library

Every guide, example, and support answer doubles. The docs already carry a "Choosing a Transport" table; more surface means more of that. Mitigation: keep HTMX canonical for the ready-made panels; DataStar is the opt-in path for consumers building their own UI.

Risk · Tests

Coverage gates and test matrix growth

Every new module in this repo gets a coverage gate, lint config, and cqrs-lint config. New panel variants mean new modules (the repo's own library principle prohibits bundling DataStar into existing panels — see ROADMAP.md on go-health-dashboard dependency pulling).

Risk · Ecosystem

DataStar's smaller ecosystem

HTMX has the larger community and more third-party answers. Low weight here because go-datastar/go-sse are in-family and the SDK is already fully owned.

Risk · Scope

Speculative panel conversion

Converting adminui/dashboardui to dual-mode (Model B) before any consumer asks for it would be the classic premature generalization the repo's own data-model guidance warns against.
