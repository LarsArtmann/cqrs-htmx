gThe One Question I Can't Answer Myself

Should ADR-0030 (Phase 2b IndexedDB) be Accepted or Rejected?

ADR-0030 proposes IndexedDB persistence for the offline command queue so writes survive closed tabs. It's currently Proposed — the only Proposed ADR in the repo. The design is sound (SharedWorker + IndexedDB, reactive detection, ACK-driven cleanup), but:

  • Is there a real consumer demand for this? No production user has requested write survival across closed tabs.
  • Does IndexedDB add unacceptable complexity? It's ~200 LOC of JS in a SharedWorker, plus lifecycle management.
  • Should we wait for OPFS instead? ADR-0029 explicitly deferred OPFS to Phase 2b. OPFS may be simpler than IndexedDB for this use case.
  • If not now, when? Or should the ADR be Rejected as YAGNI?

This is a product decision, not a technical one. The library provides the ACK protocol and queue infrastructure; IndexedDB persistence is a consumer concern that the library could ship as an optional module. I cannot determine from the codebase whether the maintainer wants to own this or leave it to consumers.

Decision needed: Accept ADR-0030 (implement IndexedDB), defer (leave Proposed), or Reject (leave to consumers).
