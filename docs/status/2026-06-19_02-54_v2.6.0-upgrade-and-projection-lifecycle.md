## a) FULLY DONE ✅

### This Session — v2.6.0 Upgrade (2026-06-19)

1. **Dependency bump — all 7 modules** — Every go-cqrs-lite dependency (`command`, `event`,
   `id`, `query`, `decider`, `memory`, `projection`, `storage`, `catalog`, `signing`,
   `encryption`, `dispatcher`, `codec`, `listing`, `snapshot`, `otel`) bumped from `v2.5.0`
   to `v2.6.0` via `go get` + `go mod tidy`. No breaking API removals affect cqrs-htmx (the
   only removed upstream symbol, `pebble.DeleteEventsBefore`, was never used here).

2. **Adopted `RunReplay`/`RunLive` — killed the `time.Sleep(50ms)` hack**
   (`usermgmt/es_projection_setup.go`). The old code started `runner.Run()` in a goroutine
   then slept 50ms hoping the projection would catch up. The new code:
   - Calls `runner.RunReplay(ctx)` **synchronously** — replays all history, returns only
     when the read model reflects every committed event.
   - Spawns `runner.RunLive(ctx)` in the background to tail live events.
   - This was **cqrs-htmx upstream feedback gap #1**, now resolved.

3. **Fixed a latent subscription race the sleep was _also_ masking.** Removing the sleep
   exposed it immediately: 5 WebAuthn tests failed with "user not in read model after
   register". Root cause: `RunLive` couples subscribe+block in one method, so the first
   `Publish` can beat the subscription registration. Rather than re-add a sleep, added a
   `subscribeSignal` wrapper that closes a readiness channel when the runner registers its
   bus subscription — `StartProjections` blocks on `<-signal.ready` before returning. Fully
   deterministic. Notably, go-cqrs-lite's _own_ `example/user` still papers over this with
   `time.Sleep(runnerStartupDelay)`.

4. **Docs updated** — AGENTS.md + README.md version references bumped to v2.6.0; the
   read-your-writes consistency bullet now documents the deterministic projection startup.

5. **Lint clean** — 3 initial lint findings (exhaustruct, 2× wrapcheck) in the new
   `subscribeSignal` code resolved with idiomatic `//nolint` inline comments matching the
   existing codebase pattern for transparent delegation.

## g) Top #1 Question I Cannot Figure Out Myself 🤔

**Should the `subscribeSignal` pattern be pushed upstream to go-cqrs-lite, or is it
cqrs-htmx's responsibility to handle subscription-readiness?**

**Context:** When I replaced the `time.Sleep(50ms)` with `RunReplay`/`RunLive`, 5 tests
immediately failed — the live subscription hadn't been registered before the first event
was published. I fixed it with a local `subscribeSignal` wrapper that intercepts the first
`SubscribeAll` call and closes a readiness channel.

**The tension:**

- The upstream `projection.Runner.RunLive()` method does `subscribe + block` atomically in
  one method. There's no way to know _when_ the subscription is active without wrapping the
  subscriber.
- The upstream `example/user/handlers.go` has the **exact same race** and solves it with
  `time.Sleep(runnerStartupDelay)` — proving this isn't a cqrs-htmx-specific problem.
- A clean upstream fix would be either: (a) `RunLive` returns a `<-chan struct{}` that
  closes when subscribed, or (b) a separate `SubscribeLive()` method that returns after
  registering, leaving the caller to block separately.

**Why I can't decide alone:** This is a **library API design decision** that affects all
go-cqrs-lite consumers, not just cqrs-htmx. The right answer depends on how Lars wants the
upstream projection lifecycle API to evolve. My local fix works and is deterministic, but
every consumer currently reinvents this. Should I file an upstream feedback doc proposing
the API change, or is the `subscribeSignal` wrapper considered the consumer's responsibility?
