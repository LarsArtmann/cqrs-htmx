D Totally Fucked Up

CRITICAL DEBT

UserState.Roles vs User.Roles Split Brain

UserState.Roles was removed (correct). But User.Roles (the read model) still exists and is still populated by UserReadModel from UserRegisteredPayload.Roles and RolesUpdatedPayload.Roles. This means the read model still shows roles on the User, but the aggregate state does not. Consumers reading User.Roles will see stale data that doesn't reflect Membership-managed roles.

Impact: Any consumer using User.HasRole() or User.Roles will get incorrect results. Roles are now managed exclusively through Membership/Casbin, but the read model hasn't caught up.
CRITICAL DEBT

CasbinProjection UserRegistered Still Seeds Roles from Payload

CasbinProjection.Handle for eventUserRegistered still calls p.addRolesFor(subject, subject, d.Roles, "on register"). This means legacy UserRegisteredPayload.Roles still creates Casbin policies — but since UserState no longer tracks roles, these policies are invisible to the aggregate and can never be updated through the User stream. They should only come from the Membership stream now.

Impact: Double source of truth for roles at registration time. The Casbin policy is seeded from BOTH UserRegistered (legacy) and MemberAdded (new). If they diverge, the projection silently creates duplicates.
CRITICAL DEBT

Service.Register Still Passes Roles to RegisterUserCmd

service_register.go:81 still dispatches NewRegisterUserCmd(aggID, req.Email, req.DisplayName, []Role{RoleViewer, RoleUser}). These roles go into UserRegisteredPayload, which the CasbinProjection picks up and seeds as Casbin policies. But since UserState no longer has Roles, these roles exist only in the event payload and Casbin — not in any queryable state. This is a ghost system.

E What We Should Improve

1. Remove Roles from UserRegisteredPayload and CasbinProjection

The biggest architectural debt. The entire role-on-User pattern should be replaced by auto-creating a Membership at registration time (in the Service.Register method). Then UserRegisteredPayload becomes role-free, and CasbinProjection stops handling eventUserRegistered for role seeding.

2. Remove Roles from User Read Model

User.Roles field and User.HasRole() should be removed or deprecated. Consumers should use Authz.RolesForActor or MembershipReadModel.FindByActor instead.

3. Type Bot OwnerID as UserID

Change BotRegisteredPayload.OwnerID and BotState.OwnerID from string to UserID. This requires JSON serialization handling but prevents type confusion.

4. Tenant Suspend Should Revoke Sessions

SuspendTenant should cascade-revoke sessions for all members of the tenant, similar to how DeleteUser revokes sessions via revokeSessionsBestEffort.

5. Add Membership Service Wrapper Methods

Service.AddMember, Service.UpdateMemberRoles, Service.RemoveMember should wrap the command dispatch pattern, matching the Service.CreateTenant / Service.RegisterBot pattern.

6. Integration Tests for Cross-Aggregate Flows

Register user → Create tenant → Add member → Verify Casbin roles → Impersonate → Verify session. This is the critical path that currently has zero integration coverage.

7. Consider go-composable-business-types for Domain Types

The how-to-golang skill recommends go-composable-business-types/id.ID[Brand, V] for branded types. We currently use go-branded-id which provides similar functionality. Evaluate if migration adds value (e.g., built-in validation, URL-safe encoding).

G Top #1 Question I Cannot Figure Out

How should we handle the transition from User.Roles to Membership-managed roles without breaking existing consumers?

The problem: User.Roles is a public field on the read model that consumers may depend on. We've already removed Roles from UserState (the aggregate), but the read model (User struct) still has it. The CasbinProjection still seeds roles from UserRegistered events. We have three options:

  1. Break completely: Remove User.Roles entirely. Auto-create a Membership at registration. Consumers must use RolesForActor. This is a v3 breaking change.
  2. Deprecate gradually: Keep User.Roles but mark it deprecated. Have Service.Register dispatch both the old RegisterUserCmd (with roles for backward compat) AND a new AddMemberCmd. Eventually remove the old path.
  3. Bridge internally: Keep User.Roles on the read model but populate it from the Membership read model (not from the User event stream). This hides the migration from consumers but creates a read-model join.

My recommendation: Option 1 (break completely). This is already a v3 release with breaking API changes. The Membership aggregate is the single source of truth. But this is a product decision — it depends on whether you have existing consumers that read User.Roles and need a migration path.
