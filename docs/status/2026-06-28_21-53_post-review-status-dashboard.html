05What We Should Improve

adminui test coverage is dangerously thin

35 tests vs 747 in usermgmt. No integration test mounts the panel. A templ regression could ship undetected. The nix run .#coverage-gate doesn't cover adminui. This is the #1 quality risk in the repo right now.

Rate limiter split brain

Root uses token-bucket + heap LRU (ratelimit_middleware.go). usermgmt uses fixed-window per-IP (lockout.go + per-endpoint limiters). Two different algorithms, two config shapes, in one repo. Consumers see both.

ActorID type split brain

Root ActorID is string. usermgmt ActorID is a kind-discriminated struct ({Kind, UserID, TenantID, BotID}). Conversion is manual and stringly-typed. A shared type or typed conversion helpers would prevent bugs.

go mod tidy broken in submodules

Private go-cqrs-lite/event/v3/eventtest test deps prevent go mod tidy in usermgmt/adminui/integration_test. Manual go.mod editing works but is fragile. A vendor directory or GOPRIVATE proxy would fix this.

No benchmark baselines

No SSE replay benchmark exists. Consumers deploying to production don't know the limits of JournalSSEStore replay with 10K/100K events.

07Top #1 Question

Q2: Must writes survive closed tabs?

Q1 (where does decide() run?) is answered — ADR-0027: Queue-Only, the client never runs domain validation. That unblocks the protocol design.

Q2 remains: when a user closes the browser tab while offline commands are queued, should those commands survive? This determines the persistence architecture:

  • Tab-Scoped (SharedWorker or in-memory) — commands lost when tab closes. Simpler. Matches most web app expectations. The queue lives in a SharedWorker so navigating between pages doesn't lose pending commands, but closing the browser does.
  • Persisted (Service Worker + Background Sync + IndexedDB/OPFS) — commands survive tab close and browser restart. Synced when connectivity returns even if the app isn't open. Complex: requires Service Worker registration, Background Sync API (Chrome only), IndexedDB for queue persistence, and dealing with OPFS limitations in SW context (no SharedArrayBuffer).

I cannot decide this for you because it depends on your offline UX requirements: Do users expect to draft commands offline, close the laptop, and have them sync on reconnect? Or is "pending while tab is open" sufficient?

My recommendation: Tab-Scoped for MVP

Start with SharedWorker (survives page navigation, lost on tab close). This covers 90% of offline UX needs: user goes offline in a tunnel, queues commands, comes back online, commands sync. Upgrade to Service Worker + Background Sync only if users explicitly need "survives browser restart" persistence.

The library already provides everything needed for Tab-Scoped: the ACK protocol, the SSE broadcast, the honest UI states. The consumer just needs a JS command queue in a SharedWorker that flushes on reconnect.
