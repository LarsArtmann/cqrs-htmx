## d) TOTALLY FUCKED UP

### D1. Did not sync before starting (root cause — carried from previous session)

The entire rebase conflict saga was caused by creating tags on a diverged branch without syncing first. `git fetch && git status` should have been the FIRST action before touching CHANGELOG, scripts, or tags. This caused:

- 5 merge conflicts during rebase
- 9 orphaned tags that had to be deleted and recreated
- batch-release.sh fix lost and had to be re-applied
- ~1 hour of recovery work

### D2. batch-release.sh fix lost during rebase

The pseudo-version check fix (`remyoudompheng/bigfft` false positive) was committed BEFORE the rebase. The rebase replayed the commit but the fix was in a later commit that conflicted and got mangled. Had to re-apply the edit manually after the rebase completed. **Lesson:** script fixes that are part of the release flow should be in a separate commit that's less likely to conflict.

### D3. batch-release.sh creates dangling commits (architectural concern)

The script creates a temporary commit (`3a0dcf7`) with stripped go.mod replaces, tags it, then resets HEAD back. This means:

- The tagged commit is NOT reachable from any branch
- `git log master` doesn't show the release commit
- The only reference to `3a0dcf7` is via the tag objects

This differs from v4.6.0, which was tagged directly on a branch commit (`1708449`). While Go module resolution works fine with dangling tagged commits, it's confusing for repository history. **The batch-release.sh pattern is fragile** — it races with the auto-git daemon and produces a different git topology than manual tagging.

## e) WHAT WE SHOULD IMPROVE

### Process

1. **Sync-first protocol (STILL NOT IMPLEMENTED):** The release-checklist.sh STILL doesn't verify that HEAD is in sync with origin/master before allowing tag creation. This was identified in the previous session's self-critique but not fixed. **Highest priority.**
2. **batch-release.sh is incompatible with auto-git daemon:** The temp-commit-tag-reset pattern races with the daemon. Two specific failure modes observed: (a) daemon commits between script's temp commit and reset, (b) daemon pushes tags before the script finishes restoring files.
3. **Consider tagging on branch HEAD directly:** Instead of creating a dangling temp commit, modify the go.mod files, commit normally (letting the daemon handle it), tag HEAD, then restore. The v4.6.0 release proved this works.

### Technical

4. **The go.work replace directives should be documented as dev-only:** Root go.mod has NO replace directives (replaces are in go.work only). This is correct but non-obvious — batch-release.sh's strip phase is a no-op for root go.mod. The script should skip the strip phase for files that have no replaces.
5. **go.sum conflict resolution is fragile:** Stripping conflict markers with `sed` creates a union of both sides' checksums. This works but may leave stale entries. Should run `go mod tidy` after resolving.
