## d) TOTALLY FUCKED UP

### D1. Did not sync with origin before starting

**This is the root cause of everything that followed.** The local branch had diverged from origin/master (origin had 4 commits not in local; local had 11 commits not in origin). I should have run `git fetch && git rebase origin/master` (or `git sync`) BEFORE touching anything. Instead, I created tags on a diverged branch.

**Impact:** The `git sync` the user ran after my session hit merge conflicts because origin/master already contains the "deps: bump cqrs-htmx/v4 to v4.6.0" commits from the previous release attempt, and my local commits touch the same files.

### D2. Tags will be orphaned after rebase

The 9 tags point to `f0d7581` (and annotated tag objects). After the rebase replays all commits onto origin/master, `f0d7581` will become unreachable from HEAD. The tags will technically still point to valid git objects (they won't be garbage collected immediately), but they'll be **off the main branch line** — a release hygiene disaster.

**Fix:** Delete all 9 tags, complete the rebase, then re-run `batch-release.sh` on the synced HEAD.

### D3. batch-release.sh race condition with auto-git daemon

The `batch-release.sh` script does: strip replaces → temp commit → tag → `git reset --mixed HEAD~1` → restore files. But the auto-git daemon runs continuously and may commit BETWEEN the temp commit and the reset. This can cause the reset to undo the wrong commit. The script needs to either:

- Disable the auto-git daemon during execution, OR
- Use `git stash` / a worktree instead of commit-then-reset, OR
- Check that HEAD hasn't moved between commit and reset.

In this session it appears to have worked correctly (tags point to the right commit content), but it's fragile.

### D4. Misidentified tag state at session start

At the beginning, I saw local tags that pointed to dangling commits (from a previous partial release). I initially thought v4.6.0 was NOT tagged. It was only after force-fetching from remote that I discovered v4.6.0 was already published. I should have `git fetch --tags --force` as the FIRST action.

## e) WHAT WE SHOULD IMPROVE

### Process

1. **Sync-first protocol:** The release checklist should verify `git fetch && git status` shows "up to date" with origin before allowing tag creation. Add a hard gate: "HEAD must be in sync with origin/master."
2. **Auto-git daemon + batch-release.sh coordination:** The batch-release script's commit-tag-reset pattern is fundamentally incompatible with a concurrent auto-commit daemon. Needs a lock or a different mechanism.
3. **Coverage thresholds should be realistic:** loginpage (79.9%) and dashboardui (56.0%) were already below their thresholds at v4.6.0. The coverage gate was failing silently (or being marked EXPECTED when it shouldn't have been). Thresholds should reflect reality, not aspirations.
4. **batch-release.sh pseudo-version check was too broad:** Scanning ALL go.mod lines for pseudo-version patterns catches legitimate third-party deps. Should only scan for internal module paths. (Fixed this session.)

### Code/Config

5. **The coverage-gate runs with `GOWORK=off`** — this is correct for external-consumer simulation, but it means it CANNOT pass pre-tag (dependent modules reference unpublished root exports). The release-checklist should either: (a) skip coverage-gate pre-tag and run it post-tag, or (b) run coverage-gate with `GOWORK=on` pre-tag as a proxy.
6. **go-cqrs-lite replace directives in go.work are STILL required** — 13 of ~40 submodule tags have broken zero pseudo-versions. This is a go-cqrs-lite upstream problem that blocks clean external resolution.
