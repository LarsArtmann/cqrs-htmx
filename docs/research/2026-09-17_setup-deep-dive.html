00Summary

This audit reads every production file of the setup/v4 module (setup.go, config.go, bundle.go, mount.go, run.go, run_appkit.go, sse.go, doc.go — 1,614 LOC excluding tests) and compares what it wires against the capability surface of everything it already depends on: usermgmt, root cqrshtmx, dashboardui/adminui/loginpage, datastar, transport, go-cqrs-lite middleware, httputil, and go-appkit. Version claims were verified against pushed git tags on 2026-09-17.

The composition core is in excellent shape: the shared hub feeds both SSE and DataStar from one broadcast (ADR-0050), transport.ServeDomainEvents owns the SSE lifecycle, projection readiness gates /health, the OTel bundle threads bus spans without an OTel import, and the Service/ServiceConfig/flattened precedence is conflict-validated with escape hatches. Nothing is misused. What setup leaves on the table is reach: three capabilities that live one struct field away in dependencies setup already requires are invisible to its consumers.

The bottom line A setup consumer cannot turn on brute-force protection for the passwordless auth endpoints, cannot get metrics or build-info endpoints on either serve path, and can silently build SQLite-schema read models against a Postgres connection. All three fixes are small, additive, and respect the “never enforce defaults” library principle — they add opt-in seams, not opinions.

02Findings — Auth Layer

Missed Opportunity · High impact

usermgmt's auth-endpoint hardening is unreachable through setup

setup.go:57 (only CookieName threaded) · usermgmt/http.go:62-101 (the full HandlerConfig)

usermgmt.HandlerConfig carries six per-group rate limiters (WebAuthnRateLimit — whose own doc comment says “Use this to brute-force protection on the passwordless login/registration ceremonies” — plus Registration, Import, TOTP, Verification, OAuth), the session-cookie Secure override, SessionMaxAge, a handler Timeout, OAuth2SuccessURL/OAuth2ErrorURL (redirect-after-OAuth2 instead of JSON callbacks), and ImportExportAuthorizer. Setup constructs the AuthHandler internally with exactly one field: HandlerConfig{CookieName: cfg.CookieName}. The handler has no setters, and the documented escape hatch does not apply: Config.ServiceConfig is passed to usermgmt.NewService, which builds the service — the HTTP HandlerConfig is a different struct that only setup ever touches. The guide's “do not file expose-X requests; pass a ServiceConfig” policy is correct for every ServiceConfig capability and covers none of these.

Why it matters setup is the front door most consumers walk through. A passwordless stack’s ceremonies are its most abuse-exposed surface, the protection already exists one dependency down, and the composition root silently drops it — a setup consumer cannot enable it at all without abandoning Bundle.Mount (the auth routes are registered by Mount, so hand-building an AuthHandler means hand-mounting every panel too).
Recommendation Add one conflict-validated escape hatch, mirroring the ServiceConfig pattern — flattened CookieName stays the default; a set AuthHandlerConfig.CookieName must match it. 
// Config
// AuthHandlerConfig, when set, is passed to usermgmt.NewAuthHandler
// verbatim (rate limits, cookie Secure/MaxAge, handler timeout,
// OAuth2 redirect URLs). CookieName conflicts are rejected.
AuthHandlerConfig *usermgmt.HandlerConfig

// setup.go — replace the one-field literal
authCfg := usermgmt.HandlerConfig{CookieName: cfg.CookieName}
if cfg.AuthHandlerConfig != nil {
    authCfg = *cfg.AuthHandlerConfig
}
bundle.Auth = usermgmt.NewAuthHandler(svc, authCfg)
Consistency · Low risk

Auth mutations carry no CSRF while admin mutations do

mount.go:39-41 (RegisterRoutes, bare) vs mount.go:53-60 (admin wrapped in csrfMW)

POST /auth/register, the WebAuthn/TOTP/OAuth2 ceremonies, and /auth/logout are mounted without the CSRF middleware setup itself applies to admin form posts. Login-CSRF and logout-CSRF are low-severity vectors in a passwordless stack, and wiring CSRF here would require the login page to render the token — so this is likely deliberate, but nothing documents the decision, and the asymmetry surprised this audit. Decide and document (or wrap and teach loginpage the token).

03Findings — Persistence

Missed Opportunity · High impact

Flattened ReadModelDB silently means the SQLite dialect

config.go:126 · setup.go:124-136 (ReadModelDialect never set) · usermgmt/sql_readmodel_dialect.go:29-37 (“” → SQLite constructors)

The flattened path exposes ReadModelDB but not ReadModelDialect, and the empty string resolves to the SQLite constructor family. A consumer who follows the README and guide (“ReadModelDB: sqlDB — optional: enables SQL-backed read models”, no dialect caveat) with a Postgres or MySQL *sql.DB gets SQLite-dialect view stores: auto-migration emits SQLite DDL against a Postgres connection and fails — loudly, but far from the config mistake that caused it. The “pass a ServiceConfig” policy covers the knob (ServiceConfig.ReadModelDialect) and that design is sound; what is missing is fail-fast at the seam, and the driver is detectable.

Recommendation sql.DB.Driver() names the driver — validate at New: a non-SQLite driver on the flattened path is a rejection pointing straight at ServiceConfig.ReadModelDialect. No new knob, no policy change. 
func (c Config) validateReadModelDriver() error {
    if c.ReadModelDB == nil || c.ServiceConfig != nil {
        return nil
    }
    switch c.ReadModelDB.Driver().Name() { // "sqlite", "sqlite3"
    case "sqlite", "sqlite3":
        return nil
    }
    return errorfamily.NewRejection("setup.invalid_config",
        "flattened ReadModelDB uses the SQLite read-model dialect; for "+
            "postgres/pgx/mysql pass ServiceConfig.ReadModelDialect")
}

04Findings — Ops Surface

Missed Opportunity · High impact

go-appkit v0.5.0’s metrics and /version arrived today with no knob to reach them

setup/go.mod (go-appkit v0.4.0) · run_appkit.go:67-78 (ServiceConfig built without Metrics/Version) · remote tag v0.5.0 (2026-09-17)

v0.5.0 — published the day of this audit — adds ServiceConfig.Metrics (a dependency-free Prometheus text exposition at GET /metrics, Basic-Auth-mandatory-by-default) and ServiceConfig.Version + GET /version (JSON build-info battery, also labeling appkit_build_info). setup pins v0.4.0 and builds its ServiceConfig literal without either field, so RunWithAppkit consumers cannot enable them, and the RunHandler path has no metrics or build-info surface at all (root’s DebugHandler is similarly unmounted). For a module whose pitch is “the shortest path to a production-shaped server”, zero observability endpoints on the default path is the largest ops gap.

Recommendation Bump go-appkit to v0.5.0; thread Config.Metrics and Config.Version into the appkit ServiceConfig. For the httputil path, mount root’s cqrshtmx.DebugHandler behind an opt-in path (metrics on that path stay consumer-side via the go-cqrs-lite prometheus module, keeping root dependency-free).
Missed Opportunity · Medium impact

No request-logging knob — RunHandler serves with zero access logs

bundle.go:129-131 (Middleware is fixed) · root logging.go:204 (RequestLoggingSlog, unused by setup)

Root ships RequestLogging/RequestLoggingSlog; setup’s Bundle.Middleware() is hardwired to RecommendedSecurityMiddleware() and offers no composition point, so the httputil serve path produces no access log lines at all (the appkit path logs per-request INFO — the very line the adoption benchmark had to suppress). Consumers can wrap the returned handler manually, but nothing points them there; a Config.RequestLogging *slog.Logger (nil = current silence) would close the trap opt-in.

Missed Opportunity · Medium impact

Machine observability endpoints are unmountable via setup

event_catalog_handler.go:44 · usermgmt/es_event_catalog.go:13 (DefaultEventCatalog) · projection_status_handler.go:43 · usermgmt/es_projection_health.go:56 (Service satisfies the provider) · readiness.go:123 (DebugHandler)

The dashboard renders UI equivalents, but for scripts and monitors there is no setup path to mount EventCatalogHandler(usermgmt.DefaultEventCatalog()) (the Published-Language JSON, immutable + ETagged), ProjectionStatusHandler(service) (live JSON, per-request ETag), or DebugHandler (build info). Each is one mux.Handle away for a consumer — but setup is the composition root whose job is exactly this wiring, and it owns the only correctly-gated place to mount them (behind the session gate, like /sse).

Missed Opportunity · Medium impact

No liveness probe on the RunHandler path; /health cannot be disabled

mount.go:100-103 · config.go:294-296 (empty HealthPath is re-defaulted, no “-” opt-out)

/health is readiness-only (503 while draining — correct), but a Kubernetes consumer needs a separate always-200 liveness probe; the appkit path serves /health/live while the httputil path serves nothing equivalent. Relatedly, DataStarScriptPath supports “-” to opt out of a mount; HealthPath does not — an empty value is silently re-defaulted to /health, so consumers running their own health stack (the appkit path’s known /health dedup, ADR-001 item c) cannot turn setup’s off.

Missed Opportunity · Low impact

HTMX SSE extension script not served next to the SSE feed

htmx_extensions.go:62 (HTMXExtensionHandler) · mount.go:85-98 (DataStar SDK gets a script mount; HTMX gets none)

When SSEPath is set, DataStar consumers get the SDK served at /datastar.js automatically, but HTMX consumers using the sse extension against /sse must fetch sse.js from a CDN or self-host — an asymmetric treatment of the two protocols the hub otherwise treats as peers. An SSEScriptPath-style mount (“-” to opt out, mirroring DataStarScriptPath) closes it.

08Conclusion

setup is a well-built composition root that under-reaches rather than over-reaches: zero misused APIs, zero architectural violations, and every hard problem it touches (hub sharing, SSE lifecycle, readiness, shutdown, escape-hatch precedence) is delegated to the right owner. The gaps are all of one shape — a capability that exists in a direct dependency, loaded and paid for, with no Config seam to switch it on. Three of them matter (auth hardening, the SQL dialect footgun, metrics/version), and all three are additive opt-ins compatible with the next minor train. The stale README security paragraph found along the way was corrected in the same session; the actionable remainder is routed to TODO_LIST.
