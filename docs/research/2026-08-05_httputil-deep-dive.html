httputil — Adoption & Utilization Audit

How well does cqrs-htmx (a framework-agnostic Go library that wires go-cqrs-lite dispatch to net/http with first-class HTMX support) leverage its sibling HTTP middleware library github.com/larsartmann/httputil? The core migration is excellent — but testing tooling, production hardening, error classification, and consumer discoverability are largely untapped.

00Summary

cqrs-htmx depends on httputil v0.8.0 (the latest release) and fully re-exports the three concerns it migrated there — CSRF, keyed rate limiting, and Server-Timing — via clean type/var alias layers (csrf_reexport.go, ratelimit_reexport.go, server_timing_reexport.go). That migration is a model of how to extract shared middleware into a focused library. The gap is everywhere else: httputil ships 16 production-grade middlewares (CORS, Compression, ETag, MaxBodySize, Metrics, ClientIP, production Server), an HTTP-spec compliance test kit (httpspec), an error-classification registry, and a validated middleware stack — and cqrs-htmx taps almost none of it, neither internally nor by guiding consumers toward it.

The bottom line The CSRF / rate-limit / Server-Timing extraction is done right, but cqrs-htmx treats httputil as a 3-feature dependency when it is a 16-middleware + test-kit library. The highest-leverage moves are: (1) adopt httputil’s httpspec test kit internally to lock in compliance, (2) stop hand-rolling http.ListenAndServe in examples and use httputil’s production Server, (3) register httputil’s error classifications so stdlib HTTP errors classify through MapError, and (4) publish a consumer guide mapping every HTTP concern to its httputil middleware.

◆What’s already leveraged well

The current usage is concentrated in three re-export files plus a handful of direct calls. It is high quality — the aliases preserve the consumer API verbatim while moving the implementation (and transitive deps like justinas/nosurf) into httputil.

+
CSRF — fully migrated & re-exported csrf_reexport.go aliases 12 symbols (CSRFMiddleware, CSRFResponseHeaderMiddleware, CSRFTokenHXHeaders, ValidateCSRF, CSRFTestToken, ErrCSRFInvalid…) and 3 default consts. csrf_handler.go builds a per-handler CSRFProtect option on top of httputil.ValidateCSRF.
+
Keyed rate limiting — fully migrated & re-exported ratelimit_reexport.go exposes the O(log n) eviction KeyedRateLimiter, both KeyExtractor factories, and the retry/window/TTL defaults.
+
Server-Timing — migrated, re-exported, and wired into App server_timing_reexport.go + app.go:335 calls httputil.WrapServerTiming so the timing header flows through the dispatch pipeline.
+
Pagination & query parsing via httputil options_json.go (DecodePagination) and usermgmt/credential_http.go both call httputil.ParseUintQuery instead of reinventing uint query parsing.
+
Justified, richer re-implementations (not duplication) recovery.go, logging.go, and middleware.go (ContextEnrichment) are intentionally richer than httputil’s generic equivalents — they integrate errorfamily classification, dispatch-error capture, and domain IDs. These are correct divergences, kept on purpose.

01Findings

Ordered by impact. Each card cites the exact code location (or “not used anywhere”) and the httputil capability being missed. “Not re-exported” findings are intentionally consistent with cqrs-htmx’s duck-typing philosophy — the fix is discoverability (a guide), not necessarily re-export.

Missed Opportunity · High impact

httpspec compliance test kit unused — no spec regression guard

Not used anywhere. httputil provides httpspec.Run / httpspec.RunSerial (18 standard specs: index-reachable, unknown->404, HEAD/OPTIONS handled, TRACE/CONNECT rejected, error responses carry Content-Type, no version leak, X-Content-Type-Options present, no duplicate headers, long-URL handled).

httputil ships a ready-made HTTP-spec compliance test kit that asserts a handler behaves like a correct HTTP server. cqrs-htmx positions itself as the HTTP layer for CQRS apps, yet its own test suite never verifies that a recommended middleware stack produces a spec-compliant server. This is exactly where httputil’s testing tools deliver the most leverage for the least effort — a single test file locks in behavior that today silently regresses.

Recommendation Add httpspec_compliance_test.go that builds the recommended stack (SecurityHeaders + Recovery + a real index route) and runs httpspec.Run with WithIndexPath("/"). It both proves the defaults are compliant and documents the contract. 
// httpspec_compliance_test.go
func TestHTTPSpecCompliance(t *testing.T) {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /", func(w http.ResponseWriter, _ *http.Request) {
        w.Header().Set("Content-Type", "text/html")
        io.WriteString(w, "<h1>ok</h1>")
    })
    h := cqrshtmx.Chain(
        cqrshtmx.SecurityHeadersMiddleware,
        cqrshtmx.RecoveryMiddleware,
    )(mux)
    httpspec.Run(t, h, httpspec.WithIndexPath("/"))
}
Missed Opportunity · High impact

Examples serve with bare http.ListenAndServe — zero timeouts

examples/basic/main.go:239, examples/datastar-demo/main.go:31. Four other examples use &http.Server{} but still hand-fill timeouts instead of httputil’s validated DefaultServerConfig.

The classic Go footgun: http.ListenAndServe sets no ReadTimeout/WriteTimeout/IdleTimeout, leaving the server open to slowloris-style resource exhaustion. httputil provides NewServer(ServerConfig, handler) with a Validate()&rsquod DefaultServerConfig that sets sane timeouts and rejects negative values at construction. cqrs-htmx is a library that exists to help people ship HTTP apps — its canonical example teaching the unsafe pattern undercuts that mission.

Recommendation Replace bare ListenAndServe in examples with httputil.NewServer(httputil.DefaultServerConfig(), h). It demonstrates the library’s production path and removes the footgun. 
// Before
log.Fatal(http.ListenAndServe(addr, mux)) // no timeouts

// After
srv, err := httputil.NewServer(httputil.DefaultServerConfig(), mux)
if err != nil { log.Fatal(err) }
log.Fatal(srv.ListenAndServe())
Anti-pattern · Split brain

SecurityHeaders exists in BOTH repos with divergent field sets

cqrs-htmx/security.go (richer: PermissionsPolicy, Custom map, SecurityHeaderSkip sentinel) vs httputil/security.go (weaker: ContentTypeNosniff bool, no PermissionsPolicy, no Custom). CSRF / rate-limit / Server-Timing were migrated; SecurityHeaders was not.

The migration was incomplete. Three concerns moved cleanly into httputil and became single sources of truth; SecurityHeaders stayed behind as a richer hand-rolled copy while httputil grew a weaker parallel version. Two structs with the same intent and different fields is a maintenance hazard — a fix in one won’t reach the other. The right resolution is to promote cqrs-htmx’s richer config (PermissionsPolicy, Custom, SecurityHeaderSkip) into httputil, then re-export it like the other three.

Recommendation Port PermissionsPolicy, Custom map[string]string, and the "-" sentinel into httputil’s SecurityHeadersConfig, then add a security_reexport.go in cqrs-htmx and delete security.go. Single source of truth — matching the CSRF/rate-limit/ Server-Timing precedent.
Missed Opportunity · Medium impact

httputil error classifications never registered

errors.go:67 MapError falls back to errorfamily.Classify(err).HTTPStatus(). httputil.RegisterErrorClassifications() is never called anywhere in cqrs-htmx (grep returns nothing). httputil has no init() that auto-registers.

cqrs-htmx is errorfamily-centric: every error flows through MapError, which classifies via errorfamily.Classify. httputil registers classifications for stdlib sentinels (http.ErrNotSupported, http.ErrAbortHandler, …) and templates for its own codes (http.write_failed, http.compress_write_failed, http.etag_write_failed). Because cqrs-htmx never calls the registrar, any consumer who layers httputil Compression/ETag middleware on top gets unclassified write errors (no what/why/fix template) if they reach the handler pipeline.

Recommendation Call httputil.RegisterErrorClassifications() once during New()/MustNew() (idempotent). It completes the errorfamily picture so every HTTP-layer error classifies consistently through MapError.
Missed Opportunity · Medium impact

No consumer guide to httputil’s broader middleware catalog

doc.go mentions only the 3 migrated concerns. No guide maps CORS, Compression, MaxBodySize, ClientIP, Metrics, ETag, or production Server for consumers. Consistent with duck-typing (consumers import what they need) — but they can’t import what they don’t know exists.

httputil has 16 middlewares. A cqrs-htmx consumer building a browser-facing CQRS app almost always wants CORS (browser API access), Compression (htmx.js + JSON payloads), MaxBodySize (protect the JSON decoders cqrs-htmx exposes), and ClientIP (correct rate limiting behind a proxy). None of this is surfaced. The duck-typing philosophy is sound; the discoverability is not. A single guide closes the gap without bloating the API.

Recommendation Add docs/guides/leveraging-httputil.md with a concern→middleware table and copy-paste recipes (CORS, Compression, MaxBodySize, ClientIP, NewServer, Metrics, ETag, MiddlewareStack, health readiness). Add a pointer in doc.go.
Missed Opportunity · Medium impact

JSON/form decoders have no body-size guard

options_json.go (RenderJSON), the DecodeJSON/DecodeForm family, and usermgmt/credential_http.go all decode request bodies. cqrs-htmx defines ErrRequestTooLarge (413) but never enforces a size limit. httputil.MaxBodySize(int64) is not referenced anywhere.

cqrs-htmx hands consumers unbounded json.NewDecoder(r.Body) decoders and even declares an ErrRequestTooLarge sentinel — but nothing wires the two together. httputil’s MaxBodySize middleware is the missing piece: it rejects oversized bodies before decoding, mapping cleanly onto the 413 path cqrs-htmx already anticipates.

Recommendation Document httputil.MaxBodySize in the new guide as the recommended guard for mutation endpoints, and show it composing inside cqrshtmx.Chain.
Partially Used · Low impact

Chain logic duplicated; cqrs-htmx’s variant is unvalidated

middleware.go:79 re-implements httputil.Chain with a curried signature (Chain(mw...) func(http.Handler) http.Handler vs httputil’s Chain(handler, mw...) http.Handler). Neither enforces ordering. httputil’s MiddlewareStack (stack.go) validates “Recovery outermost” and rejects duplicate names.

Two Chain functions with the same name and different signatures is a known papercut (the project’s own skill notes “pick one and use consistently”). The deeper miss is that neither offers ordering validation. httputil’s MiddlewareStack catches “Recovery not first” at build time — a real correctness guard cqrs-htmx could surface.

Recommendation Low priority. Either document httputil’s MiddlewareStack as the validated alternative, or have cqrshtmx.Chain delegate to it internally.
Partially Used · Low impact

Health has liveness but no readiness split

app.go:425 App.HealthHandler() returns 200/503 based on dispatcher availability (effectively readiness). httputil’s LiveHandler, ReadyHandlerWithProbe, and RegisterHealth(mux) (mounts /healthz, /livez, /readyz) are unused.

Kubernetes-style orchestration wants separate liveness (is the process up?) and readiness (are deps ready?). cqrs-htmx exposes one combined handler; httputil offers the split plus a one-call RegisterHealth that mounts the conventional three endpoints. Complementary, not conflicting.

Recommendation Document httputil’s RegisterHealth alongside app.HealthHandler() in the guide for consumers running under orchestrators.
Partially Used · Low impact

Dispatch-level timeout exists; request-level timeout is undocumented

Config.Timeout (timeout_test.go) sets a deadline on the dispatch context. httputil’s Timeout(duration) wraps the whole HTTP handler and is not referenced.

These are complementary layers, not duplicates: Config.Timeout bounds the CQRS dispatch; httputil.Timeout bounds the entire request (including decode, render, middleware). Both have value; only one is surfaced.

Recommendation Mention httputil’s request-level Timeout in the guide, noting the distinction from Config.Timeout.

03Version currency

cqrs-htmx is on httputil v0.8.0, which is the latest published tag. No version gap. The v0.8.0 release is precisely the one that introduced CSRF, Server-Timing, and keyed rate limiting — the three concerns cqrs-htmx migrated — so the dependency is current and the migration target is the right one.

On the latest release v0.8.0 == latest tag. httputil’s own roadmap lists v0.9.0 (observability: OTel tracing, Prometheus metrics recorder) and v1.0 (API freeze, TokenBucketLimiter removal). Watch v0.9.0’s metrics recorder — it pairs directly with the unused Metrics middleware noted in this report.

04Conclusion

cqrs-htmx leverages httputil superbly for the three concerns it chose to migrate and correctly keeps richer, domain-aware re-implementations (Recovery, Logging, context enrichment) where httputil’s generic versions would lose value. The untapped surface is httputil’s testing and production tooling — the httpspec compliance kit, the production Server, the error classification registry — plus consumer discoverability for the remaining 13 middlewares. The single highest-leverage next step is adopting httpspec.Run in the test suite: it turns httputil from a runtime dependency into a correctness partner.
