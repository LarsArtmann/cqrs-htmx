00Summary

This audit answers a narrow question: does dashboardui/ use github.com/larsartmann/templ-components superbly? The evidence says it is close to a model consumer. All five required module paths (core, errorpage, htmx, icons, utils — spanning the seven import packages display, forms, feedback, htmx, errorpage, icons, utils) sit at the newest released tag; ~90 distinct library identifiers appear across 12 handwritten Go files plus 10 generated *_templ.go files; table sorting, polling regions, toasts, global HTMX error handling, and family-aware error pages all route through library components rather than hand-rolled equivalents; and the compiled Tailwind bundle gate is green (76,984 bytes, minified, canary utilities present).

The remaining surface divides into three small partial adoptions (hidden CSRF inputs, dark-mode toggle, version slider), one optional candidate (sidebar), and a set of deliberate divergences (page shell, cursor pagination) that are justified by the dashboard's HTMX-boost navigation model — not oversights. No misuses were found.

Series context (added same day, on review): this is a follow-up, not a first episode. The predecessor 2026-09-17 dashboardui audit scored this module 14/100 — one component imported, everything hand-rolled in strings.Builder — six days before the full-templ migration that this audit's 85/100 measures the result of. The companion adminui audit (68/100) covers the sibling consumer. The 2026-09-20 theme-toggle strategy spike predates this report's ThemeToggle finding. The score trajectory 14 → 85 is the headline this report originally buried.

The bottom line This is superb usage with a short tail. Two cheap moves — swapping 7 hand-rolled hidden CSRF inputs for htmx.CSRFToken, and landing the already-planned ThemeScript/ThemeToggle adoption — would lift the score to roughly 95 and leave only defensible divergences behind.

The baseline: how the library is actually used today. Every claim below was verified against the codebase on 2026-09-23.

+

01Findings

Ordered by impact. Two partial adoptions, two optional candidates, and one fully-leveraged confirmation. Deliberate divergences (page shell, cursor pagination, raw GET filter form) are documented at the end.

Partially used · trivial to fix

7 hand-rolled hidden CSRF inputs — htmx.CSRFToken exists for exactly this

dlq.templ:62,74,109,151 · projections.templ:78,115 · snapshots.templ:56

Every mutating inline form re-implements the same line: <input type="hidden" name="_csrf" value={ p.CSRFToken }/>. The library ships htmx.CSRFToken(token string) — a hidden CSRF input component — as the canonical spelling. The raw <form> elements themselves are fine to keep: these are bare inline action forms with data-confirm, and forms.Form's labeled field-group wrapper does not fit an inline form. The hidden input, however, is a 1:1 swap that centralizes the attribute spelling in the library. 

// Before (×7)
<input type="hidden" name="_csrf" value={ p.CSRFToken }/>

// After
@htmx.CSRFToken(p.CSRFToken)
Recommendation Mechanical replacement across the four files; zero behavior change; future CSRF attribute changes then flow from one library upgrade instead of seven edits. (The events filter form is a GET with hx-get and correctly needs no token — leave it alone.)
Partially used · already planned

Dark mode is OS-follow only — ThemeScript + ThemeToggle not adopted

tailwind.css:18-21 · layout.templ (head) · library: layout.ThemeScript, layout.ThemeToggle

The dashboard respects prefers-color-scheme through its CSS token layer, but users cannot override it. The stylesheet's own comment declares the intent: "class-based strategy (@custom-variant) lands with the ThemeToggle adoption." The library provides the complete pair — ThemeScript(nonce) (FOUC-preventing head script) and ThemeToggle(ariaLabel, nonce) (sun/moon button) — and sibling module adminui already ships a user-controllable theme toggle, so the pattern is proven in this repo. Because all library components carry dark: variants, adopting the class strategy also future-proofs any newly adopted component's dark surfaces.

Recommendation Add @custom-variant dark (&:where(.dark, .dark *)) to tailwind.css, drop @layout.ThemeScript(p.Nonce) into the hand-rolled <head>, and place @layout.ThemeToggle("Toggle theme", p.Nonce) in the header. Rebuild the CSS bundle in the same change (repo rule).
Partially used · verify visual fit first

Time-travel version slider is hand-rolled — forms.Slider covers most of it

timetravel.templ:84-95 · library: forms.Slider (Min/Max/Value/Step/ShowValue, BaseProps.Attrs)

The version scrubber is a raw <input type="range"> with custom data-nav-base/data-slider-display hooks and dynamic aria-valuetext. The library's forms.Slider supports min/max/value/step, a value display, and arbitrary data-* attributes through BaseProps.Attrs — so the wiring ports. The honest caveat: forms.Slider renders a labeled field-group wrapper, while the dashboard wants an unlabeled, compact control, and the custom aria-valuetext needs the Attrs escape hatch. This is an evaluation candidate, not a clear win.

Recommendation Prototype forms.Slider with BaseProps{Attrs: templ.Attributes{...}} carrying the two data hooks; adopt only if the rendered wrapper fits the panel layout. Otherwise keep the raw input — it is a legitimate custom control.
Optional candidate · visual continuity caveat

Sidebar is hand-rolled — navigation.SidebarNav covers its anatomy

layout.templ (templ sidebar) · library: navigation.SidebarNav (brand, icon+label items, footer slot)

The aside implements brand (initials badge + name), icon+label nav items with active-state classes, a logout link, and a footer — exactly the surface SidebarNav models. Adoption would delete the bespoke nav-link CSS in favor of library Tailwind classes (already present in the scanned bundle). The caveat is real, though: the current sidebar is styled by the dashboard's own token stylesheet for visual continuity with the accent-color theming, and the library's AppShell cannot host the boost-based navigation model (see below). Treat as optional polish.

Fully leveraged where it counts · divergence is deliberate

The hand-rolled page shell is justified — layout.AppShell cannot express it

layout.templ (templ layout) · library: layout.AppShell (sidebar + header + main grid)

The dashboard shell needs four things AppShell's props surface does not offer: an hx-boost wrapper targeting #main-content with hx-select title extraction, an HTMX partial mode that emits only <title> + <main>, a skip-link, and a per-instance accent CSS variable. Forcing the shell into AppShell would mean restructuring the dashboard's entire navigation model for zero user-visible gain. Likewise, self-hosted assets (/-/dashboard.css, /-/dashboard-tw.css, /-/htmx.js) and noindex make layout.Base's CDN/SEO surface a non-fit for an embedded admin dashboard. Cursor-based prev/next pagination with a history stack (pagination.go) has no page-number equivalent in the library — Pagination is page-number-based and LoadMore is a different UX. All three divergences are correct calls, and the library is used everywhere they are not required.

04Conclusion

dashboardui's relationship to templ-components is what the library's own consumer guide asks for: check the catalogue before hand-rolling, wrap with pinned defaults, keep DOM hooks stable, rebuild the bundle with every bump. The audit found ~90 library identifiers in active use, zero anti-patterns, and a zero-version gap. The two findings worth acting on are small and cheap; the divergences that remain are load-bearing (HTMX-boost shell, cursor pagination) or cosmetic (slider, sidebar). Answer to the opening question: yes — this is superb usage, one theme toggle and seven hidden inputs away from textbook.

07Component evaluations (same-day batch)

Library component Verdict Reasoning
forms.FilterInput/FilterDropdown Reject for the events bar The events filter is a 3-field AND query (type + streamType + streamID) submitted together via one GET form. Both library components are single-field <search> forms with per-field auto-submit/debounce; composing three would split one query across three forms (cross-form hx-include plumbing fights htmx form semantics). The bar is already library-composed (forms.Input). FilterDropdown remains viable for a future single-select filter.
forms.Slider (time-travel scrubber) Reject SliderProps renders a labeled wrapper (label + value bubble + help text); the scrubber lives in a compact row with .version-links and an adjacent version display, so the wrapper is redundant chrome. The two data hooks ride BaseProps.Attrs, but the form-factor mismatch buys nothing for a 3-line input.
navigation.SidebarNav Keep custom (standing criteria) Structure fits (brand/icon items/footer), but adoption needs the adminui-class theming work: @theme gray remap + CSP-dropped --tc-sidebar-w inline style require scope pin-backs, and the library has no dark-token shell matching the custom sidebar variables. The TODO_LIST P2 revisit criteria (dark-token shell, zero-JS drawer, adminui production proof) are unchanged and still unmet.
display.Card/Grid vs .panel Keep .panel 4 usages across 2 files, styled by dashboardCSS tokens (border/radius/padding vars) that resolve correctly in both themes. A swap trades zero user-visible gain for a re-verification pass over every dark surface plus a CSS bundle rebuild — regression surface without capability gain. Revisit only if panels need component features (header actions, footers).
display.DataTable Reject DataTable is data-driven (Columns []DataTableColumn/Rows []TableRow, URL-appended sort params). dashboardui tables embed inline templ cells — copy buttons, badges, per-row action forms — that would need re-expression as data, losing templ's escape guarantees, for zero capability gain: sortable headers already shipped via Table+TypedHeaders+sortState.
display.RelativeTime Adopt-candidate (narrow) Strictly better semantics than the relativeTime() string helper (<time datetime> + hover title + AutoRefresh + htmx:afterSettle). Fits server-rendered timestamps (snapshot detail "Created"); does NOT fit the live SSE rows (JS-injected via dashboard.js). Narrow swap queued as follow-up, not emergency.
Bare empty-state sweep Clean All "No X" surfaces route through emptyStatePanel (display.EmptyState) including the stream-listing emptyTitle params; zero bare text blocks remain.
htmx.ConfirmDelete Reject dashboardui's CSP-safe pattern is one delegated submit listener (layout.go dashboardJS) + data-confirm attributes on N forms with native confirm(). ConfirmDelete components pair per-form; adopting means touching every destructive form to gain nothing over the existing listener.
display.ListNote for "Showing X–Y of Z" Blocked on upstream ListNote speaks N-of-M truncation or N-items counts, not X–Y ranges; the range-variant upstream ask is already filed (TODO_LIST P3). Hand-roll stays until the variant ships.
errorpage.ErrorDetail No fit The HTMX swap path renders the bare family-aware ErrorPage fragment — already styled and correct for a swapped region. ErrorDetail targets inline error slots inside page content, which dashboard pages don't have.
display.Scrollback No current fit Scrollback is a terminal-style LOG stream (timestamp + tone tags per line). The payload viewer is a single JSON blob (<pre class="code-block"> + download); the live feed renders as a table. Revisit if a raw-log viewer page ships.
