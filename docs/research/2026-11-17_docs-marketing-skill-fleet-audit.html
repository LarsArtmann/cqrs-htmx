00Summary

The presentation engine works. Eleven of the twenty consumer audits end in a correct refusal to adopt (headless CLIs, single-operator tools, no go-cqrs-lite), and those reviews quote the README fit-test line as the deciding artifact. The AI skill is not marketing collateral — it is the de-facto utilization rubric: consumer audits grade their own endpoints against its sections by name, and its vocabulary (Path 0/A/B/C) has migrated into consumers' own AGENTS and STACK docs. Of the nine adopters, eight run the library at 75–100/100 utilization (the ninth, PapDashboard, is a deliberate single-symbol consumer at 6/100).

The highest-leverage improvements are not new features. They are corrections to signals the fleet is already reading, sometimes wrongly: two consumer audits recorded this MIT library as proprietary; a security patch sits stranded behind a stale nested-module tag; the library's largest adoption tax (dependency weight) is nowhere documented; and four integration recipes had to be invented by consumers because the skill does not carry them.

The bottom line Keep the positioning honest — it is the most-cited asset the library has — and spend the next window on three corrections (license disambiguation, the oauth2 security re-tag, the header-constant discoverability erratum) and two additions (the dependency-footprint table, the four invented skill recipes). Everything else in this report is second-order.

01Findings

Ordered by impact. Severity classes: critical = wrong or stranded signals consumers act on today; important = recurring friction every audit re-derives; nice = leverage waiting to be claimed.

Critical · consumers are deciding on a wrong premise

F1 — License split-brain: the fleet records this MIT library as proprietary

LICENSE (MIT, line 1) · README.md:6 badge · cited wrong in: go-taskqueue review, business-networking review

go-taskqueue/docs/review/libs/cqrs-htmx.md keeps the library out partly on a “License/stance note: PROPRIETARY (same author/policy as go-cqrs-lite)… cqrs-htmx has no such instruction here.” business-networking claims adoption “would add… a proprietary licence.” Both are factually wrong — the LICENSE is MIT — and the error pattern-matches the sibling library, whose proprietary status is real and does gate some consumers. The license signal is being inherited across the family instead of read per library, and it has already contaminated one keep-out verdict and one “to the max” cost estimate.

Fix Disambiguate per library in every family-facing surface: the README first screen already carries the MIT badge — add one line where the family is discussed (“MIT. Note: some sibling LarsArtmann libraries are proprietary; each repo's LICENSE is authoritative”), and mirror the note in the how-to-golang / stack-selection policy tables consumers actually consult. Write errata on the two consumer reviews (the fleet's erratum culture expects corrections in place, not rewrites).
Critical · a security patch is unreachable by its consumers

F2 — The go-jose DoS patch is stranded behind a stale oauth2 sub-tag

commit 7fd1db43 (2026-10-28) · latest usermgmt/oauth2/* tag: v4.13.0 (2026-10-11) — verified 2026-11-17 via git tag -l 'usermgmt/oauth2/*'

The JWK RSA-key DoS patch (go-jose v4.1.5 → v4.1.6) landed on the root train, but the oauth2 nested module has not been re-tagged since — and nested-module importers cannot consume root-tag-only releases (dnsblockd's review names this exact mechanism as the “templ-components v1.8.3 class”). dnsblockd, the standalone oauth2 consumer, has now documented the exposure in its own review — dependency resolved to v4.1.5, patch uncovered — with the practical severity downgraded only because its IdP is operator-configured. The stranded state is still live three weeks later.

Fix Cut usermgmt/oauth2/v4.13.1 (and sweep webauthn/totp if their closures carry the same bump) and publish the consumer sweep recipe in the changelog entry. Then add the release rule: a security-relevant dependency bump inside a nested module's closure triggers a same-window nested re-tag. Consumers should never have to file the release request themselves.
Critical · an audit mis-verified a shipped surface

F3 — The Header* constants exist, yet a fleet audit concluded they don't

htmx/htmx.go:27-28 (HeaderRetarget, HeaderReswap) · added e1bc0095, 2026-11-04 · present in v4.18.1 — the exact tag audiblesync pins

audiblesync's review states: “the htmx subpackage exposes no constants for them (verified via go doc)” and hand-rolls the raw strings "HX-Retarget"/"HX-Reswap" in its error contract. The constants exist in the tag the audit pins. Whether the cause was a stale module cache or the Header prefix hiding them from a searcher looking for Retarget, the outcome is the same: a careful fleet audit ran a verification and got a false negative on a shipped API — and encoded the raw-string workaround as its documented contract.

Fix Three layers: (1) skill — add htmx.HeaderRetarget/ HeaderReswap to the “Discoverability notes” section and cross-link them from the Response-builder Retarget() bullet; (2) erratum on the audiblesync review citing htmx/htmx.go:27-28; (3) consider the discoverability lesson — the constants' names are the only API element in the package that does not start with what a consumer searches for.
Important · the #1 recorded non-adoption tax is undocumented

F4 — Dependency weight decides adoptions, and every audit re-derives it by hand

Six reviews derive it manually: PapDashboard, dnsblockd, google-domain-detector, io-surface, invoices, Cyberdom

The recurring computation: PapDashboard — “1 symbol costs the binary go-sse + go-etag + go-idempotency compilation units”; dnsblockd — re-implemented RenderTemplComponent locally to avoid dragging the “11-repo closure” into a hermetic flake; google-domain-detector — “dependency explosion for a hermetic nix single-binary CLI”; io-surface — “four rejections compounding into one”; invoices — “ADD ~7 direct deps, a toolchain bump”; Cyberdom — the vendorHash recompute dance. The README's module table says what each module provides but never what it costs. For this fleet — nix-heavy, hermetic-build-sensitive — the closure footprint is a first-class adoption criterion, and the library makes every consumer measure it themselves.

Fix Publish a per-module dependency-footprint table in the README (direct requires count, closure size, Go floor per module), linked from “The modules” section. Regenerate it in the release checklist so it cannot rot — the same single-source discipline as the coverage thresholds.
Important · two near-adopters stalled on the same buried fact

F5 — dashboardui's identity-free mounting is true but nearly undiscoverable

dashboardui/go.mod (zero usermgmt requires — verified 2026-11-17) · stated in one skill table row · absent from dashboardui/README.md Integration Modes

The index audit treats dashboardui-only adoption as “gated: API-key-only mounting UNVERIFIED — treat as gated”; CV's review parks dashboardui as its one real future candidate. The decisive fact — dashboardui depends on root + go-cqrs-lite only, no usermgmt — exists in exactly one place: the skill's module table (“verified against dashboardui/go.mod 2026-10-25”). The consumer-facing document (dashboardui README, Integration Modes section) does not lead with it, so two separate audits hedged on the same question within one week.

Fix dashboardui/README.md § Integration Modes gets an explicit “Runs without usermgmt” receipt (go.mod citation) plus a headless/API-key mounting example. The skill row stays as the pointer; the README becomes the proof.
Important · every consumer audit re-explains the tag mechanics

F6 — Per-module release trains need a consumer-facing doc

dnsblockd §2, PapDashboard §1, journal, browser-history §2 — each spends paragraphs explaining trains

Consumers repeatedly reconstruct the release model mid-audit: dnsblockd explains that a flake input must ride “the tag whose commit carries the sub-module tag” and that “root-tag-only releases can't be consumed by nested-module importers”; PapDashboard notes “core tags vs package tags move separately”; browser-history documents being four minors behind loginpage/adminui (masked in dev by go.work replaces); journal missed the htmx 2.0.11 asset release for two minors before catching it. The per-module train design is deliberate and correct — but it is explained in maintainer docs, not consumer docs, so every audit pays the comprehension cost again.

Fix Extend README § Versioning & migrations with a consumer-facing train table: which nested tags map to which root tag, the flake-input rule for nested-module importers, and the escalation path when a nested train lags a security patch (see F2). Link it from each nested module's README.
Important · changelog receipts outran the tags once already

F7 — Changelog claims need per-tag diff verification

dnsblockd review errata (2026-11-08) — the receipt for this finding

dnsblockd's refresh found that v4.13.0's changelog receipts documented three features (ClientType public clients, preferred_username, FinishLoginWithToken) that were already present in v4.12.0 — verified by reading the tagged provider.go — and that its earlier edition had cited APIs (“BeginLoginWithNonce”) that do not exist at any tag. A consumer audit treating the changelog as version truth got burned twice by the same document class. Consumers plan bumps and security postures from these receipts; a receipts-vs-tree mismatch costs them a verification round trip per claim.

Fix Add a receipt rule to the release checklist: every changelog entry naming a symbol must be diff-verified against the tagged tree at tag time (the release-train gate can carry the check). Ship the dnsblockd-class erratum practice upstream: when a receipt is found overstated, correct the changelog of the next train with a dated note.
Important · four integration recipes were invented downstream

F8 — The skill is missing the recipes consumers had to derive themselves

.agents/skills/cqrs-htmx/SKILL.md (764 lines) — verified absent by grep this session

The skill's decision trees are the fleet's rubric — which is exactly why its gaps become every consumer's invention: (1) standalone oauth2 — dnsblockd built the lazy-provider-retry + FinishLoginWithToken nonce pattern with no Path in the skill covering “oauth2 module without usermgmt”; (2) the HTMX flash error contract — audiblesync hand-designed 200 + HX-Retarget + HX-Reswap retarget to a flash partial (the skill documents Retarget() but no error-path recipe); (3) dashboardui headless mounting — index's “API-key-only mounting UNVERIFIED” question; (4) metaengine facts → dashboardui — invoices and CV both park event-store observability because systemadapter covers the identity domain only. Each of these is a consumer that invented a pattern the library wants adopted uniformly.

Fix Add a “Standalone module recipes” skill section with the four patterns, each crediting the consumer that proved it (dnsblockd, audiblesync, index, invoices). Keep the existing path names and section titles untouched — consumers cite them verbatim; this is additive.
Nice to have · the API-side completion of F3

F9 — A first-class “error → HTMX flash” helper

candidate: httperr package · demand signal: audiblesync's dispatchError/flash contract (handlers.go:221-251)

audiblesync's bespoke contract — HTMX clients get 200 + retarget to a flash partial, plain clients get the real status — is the shape at least two other HTMX consumers will re-derive (it is the standard HTMX error UX). Once the F3 discoverability fix lands, a httperr.FlashErrorHandler (or a documented Response-builder recipe) turns that invention into a paved road. Candidate for the v4 line's next minor; not urgent.

Nice to have · converts two parked near-adopters

F10 — The metaengine-facts → dashboardui bridge story

demand signal: invoices review recommendation 3 · CV review “dashboardui post-S5” park

Two consumers independently want dashboardui's event-store observability over a metaengine journal without the identity stack, and both stop at the same missing piece: a documented bridge from metaengine facts to the dashboard's domain-event surface (invoices proposes pricing “a thin bridge”; CV parks behind its S5 cutover). A guide — or an examples/ spike — would convert both from parked to adoptable, and it reuses F5's README receipt as its front door.
