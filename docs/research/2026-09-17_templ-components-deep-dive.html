Is adminui using templ-components to the max?

A component-by-component audit of adminui/ against the full capability surface of github.com/larsartmann/templ-components v1.17.0. Verdict: deep where it adopted, narrow where it didn’t — 19 components used deeply and cleverly themed, but three whole packages sit at zero adoption and five hand-rolled patterns duplicate components that exist today.

Scope: adminui/ (7 templ files, ~800 LOC templ) Library: templ-components v1.17.0 × 4 modules Version currency: current (v1.17.0 = latest release)

01Summary verdict

Adoption score: 68/100. Within the components adminui has adopted, usage is genuinely deep: advanced options are exercised (GridColsAutoFit + MinColWidth, Table.Body row slots, DefinitionItem.DetailComponent, Avatar shape overrides, BaseProps.Attrs for HTMX wiring), and the theme-bridge CSS pattern that makes every library component follow adminui’s design tokens in both light and dark mode is the single most sophisticated adoption technique in the repo. This is not a surface-level consumer.

But “to the max” fails on breadth and duplication. Three of the nine consumer-relevant packages — navigation, errorpage, layout — have zero imports, and the gaps are not cosmetic: users/tenants/audit lists are hard-truncated at 50 rows with no way to see the rest, twelve handlers answer failures with bare http.Error (two leaking raw err.Error() text), and six page headers plus a search form are hand-rolled against components built for exactly those jobs. Two documented custom-vs-library decisions (the hand-rolled app shell, the Card+Table border fix) are now solvable with library features that shipped after the decision was written down.

Bottom line. Keep every wrapper that exists today — they are good architecture. Spend one focused sprint on the six quick wins (Flush, icons, PageHeader, FilterInput, Breadcrumbs, StatusBadge upstream patch) and one on the two structural gaps (Pagination, error pages). Together they delete ~150 lines of hand-rolled UI code, make >50-row datasets reachable, and close the raw-error leak. The app-shell migration is now feasible but remains optional.

03What is fully leveraged

✓
The theme-bridge (best-in-repo pattern). tailwind.css:74–92 remaps Tailwind’s --color-gray-*/--color-blue-600 onto adminui CSS custom properties that flip under prefers-color-scheme (tailwind.css:54–69). Every library component (bg-gray-100, text-red-600…) therefore follows adminui’s palette in both modes with zero component changes, and the .bg-white bridge (tailwind.css:106–108) pins Card/Table surfaces to --surface. This is the documented theme-bridge recipe, applied deliberately.
✓
Advanced display props, not just the happy path. GridColsAutoFit + MinColWidth (dashboard.templ:12–15), Table.Body custom-row slots on all six tables, Card.Header slot for the danger zone (users.templ:153–155), DefinitionItem.DetailComponent (users.templ:130–136), Avatar square shape + size override (users.templ:108), Button icon/variant/size matrix everywhere.
✓
Typed mapping shims instead of stringly calls. badge()/roleBadge() route domain strings through typed display.BadgeType mappings (util.go:23–55), and icons.go:12–18 pins nav icons to typed icons.Name constants. Typos degrade to neutral/question fallbacks instead of breaking renders.
✓
Toast + global error pipeline wired correctly. feedback.ToastContainer is bridged to a typed adminui:toast HX-Trigger event (render.go:44–60, admin.js:33–46) and htmx.GlobalErrorHandling covers 5xx retry, network errors, and session expiry (layout.templ:99). Server and client halves are consistent.
✓
Cap + ListNote integration. The generic capList[T] helper (util.go:82–90) feeds display.ListNote so truncation is at least honest (“showing N of M”) — the pattern is right, it just stops one step short of Pagination (finding F3).

05Findings (gap analysis)

Each finding states what the library offers, what adminui does instead (with file:line evidence), and what improves by adopting it. Ordered by severity within tiers; the cross-tier priority ranking is in §07.

Missed Opportunity · functional gap

F3 — Lists are hard-truncated at 50 rows with no pagination

config.go:26 (MaxListRows) · util.go:82–90 (capList) · users.templ:59, tenants.templ:37, audit list — vs navigation/pagination.templ:180, loadmore.templ, endoflist

Library offers: navigation.Pagination (page numbers, ellipsis, prev/next, BaseURL+QueryParam, container-aware), LoadMore (cursor, optional infinite scroll), and EndOfList. The handler already computes the unfiltered total (capList returns it) — the hardest input already exists.

Project does instead: slices to MaxListRows (50) and renders a note. Rows 51+ are unreachable from the UI — an admin cannot manage user 51 of 4,000, on every list page.

Impact: restores access to the entire dataset; turns the honest truncation notice into real navigation. Effort: parse a page query param in the three list handlers, compute TotalPages, add one component call per page. 

@navigation.Pagination(navigation.PaginationProps{
    CurrentPage: uint(d.Page),
    TotalPages:  uint((d.Total + MaxListRows - 1) / MaxListRows),
    BaseURL:     d.BasePath + "/users",
})
Missed Opportunity · error UX + leak

F10 — Bare http.Error everywhere; errorpage package at zero

handler_users.go:45,76,104,109 · handler_tenants.go:25,35,45,78,89,100 · handler_members.go:92,161 · render.go:25 — vs errorpage/handler.go:116 (WriteError)

Library offers: the errorpage package: WriteError(w, r, err, nonce) renders family-aware error pages from go-error-family errors (which adminui’s own errors are — util.go:15–20), NotFound404, ErrorAlert for inline/HTMX contexts, and prebuilt family constructors.

Project does instead: twelve http.Error calls with ad-hoc strings. Two sites print raw err.Error() into the response (handler_tenants.go:45,78 — internal error text surfaced to the browser). Under HTMX, these plain-text responses get swapped straight into the page body, unstyled.

Impact: themed, consistent failure UX; stops leaking internal error strings; HTMX-aware error fragments via ErrorAlert. Pairs with the already-adopted GlobalErrorHandling client pipeline.

Partially Used · quick win

F1 — Table.Flush ignored; global !important CSS hack instead

tailwind.css:114–117 (border: 0 !important hack) · vs display/table.templ:163–167 (Flush: “suppresses the wrapper div’s border and rounded corners”)

Library offers: TableProps.Flush, built exactly for nesting a table flush inside a card.

Project does instead: a global selector .overflow-hidden > .overflow-x-auto that strips borders from any such pairing with !important — a latent foot-gun that reaches beyond the five Card+Table nestings it was written for, and a comment documented as a workaround for the library.

Impact: delete the global hack, set Flush: true on the five Card+Table nestings (dashboard recent activity dashboard.templ:26, audit audit.templ:15, tenant roles users.templ:141, external accounts users.templ:196, members members.templ:14), and the styling intent lives at the call site instead of a page-wide override.

Partially Used · quick win

F5 — Hand-rolled iconSVG + templ.Raw instead of icons.Icon

icons.go:23–32 · components.templ:9–11 — vs icons/icon_templ.go:21 (Icon), :120 (IconWithStrokeWidth)

Library offers: icons.IconWithStrokeWidth(name, class, strokeWidth) — emits the identical shape adminui’s wrapper builds by hand: viewBox 0 0 24 24, fill="none", stroke="currentColor", round caps/joins, aria-hidden, plus a Question-fallback for unknown names. Typed, escaping-safe, and RTL/animated variants exist.

Project does instead: a 10-line Go string builder producing raw SVG markup rendered through templ.Raw — the one API in templ that bypasses templ’s output escaping. The only adminui-specific value is stroke-width 1.8 (library default 1.5), which IconWithStrokeWidth takes as a parameter.

Impact: delete iconSVG() and the templ.Raw escape hatch; the icon(name) shim becomes a one-line delegation. Zero visual change at stroke-width 1.8. 

templ icon(name string) {
    @icons.IconWithStrokeWidth(icons.Name(name), "h-[18px] w-[18px]", 1.8)
}
Missed Opportunity · quick win

F2 — Six hand-rolled page headers; PageHeader unused

users.templ:19–21 · tenants.templ:16–18 · tenants.templ:68–71 · tenants.templ:103–114 · audit.templ:7–9 · members.templ:86–95 — vs display/page_header.templ:33

Library offers: display.PageHeader — title, subtitle, breadcrumb slot above, and an Action slot on the right.

Project does instead: every page repeats <div class="mb-5 flex flex-wrap items-center ..."><h1 class="text-xl font-semibold">…, then fights to position the “New tenant” button and status badges inside that flex row by hand.

Impact: one consistent header primitive; the “New tenant” button and tenant status badge move into the Action slot they were designed for; subtitle support comes free.

Missed Opportunity · quick win

F4 — User search form hand-rolls what forms.FilterInput is

users.templ:22–43 (hx-trigger=“submit, keyup changed delay:350ms from:find input[name=q]”) — vs forms/filter_input.templ:91

Library offers: forms.FilterInput — a debounced, wired search input inside a semantic <search> landmark with a no-JS GET fallback, ARIA labeling, and value preservation across server re-renders. DebounceMS: 350 + Wire: &wire.Action{URL: …, Target: "#users-table"} reproduces the exact behavior without the raw htmx trigger DSL.

Project does instead: a hand-written form with an inline hx-trigger from:find selector expression and a manually positioned search icon.

Impact: ~20 lines of trigger DSL replaced by one typed prop struct; a11y (<search> landmark, aria-label) and no-JS fallback gained. One small gap: FilterInput renders no built-in icon (padding is reserved), so the icon either moves or is accepted as a minor visual change.

Partially Used · upstream patch

F6 — display.StatusBadge map lacks adminui’s statuses

display/badge.templ:142–151 (statusToBadgeMap) · tenants.templ:51–57,105–111 · components.templ:63–77

Library offers: StatusBadge(status) auto-maps ~20 status strings with a status dot. But the map has no entries for suspended, deleted, verified, enabled — precisely the states adminui renders — so everything would fall back to neutral gray, which is why adminui keeps badge()/stateBadge() wrappers.

Fix: a four-line upstream contribution ("suspended": BadgeWarning, "deleted": BadgeError, "verified": BadgeSuccess) — consistent with existing entries like "degraded": BadgeWarning — collapses the three-site suspended/deleted/active if-else chains in tenants.templ into one StatusBadge call and shrinks the wrapper layer.

Missed Opportunity

F8 — Zero loading states in the whole panel

no Spinner/Skeleton/LoadingButton/PolledRegion imports — vs feedback/loading.templ, htmx/polled_region.go

Every HTMX swap (search, role change, member add/remove, delete) replaces content with no visual transition: no htmx.LoadingButton submit states, no feedback.Spinner/hx-indicator on tables, no skeletons.

The biggest specific win: the dashboard stats grid is a static snapshot. htmx.PolledRegion (URL + Every, aria-live, optional updated-at stamp) would make the stats panel self-refreshing with one component — the panel already has the SSE story for mutations, but stats never update after load.

Deliberate decision · now partially unblocked

F9 — Hand-rolled app shell; AppShell blocker solved upstream since it was written

layout.templ:27–97 (~70 LOC) · admin.js:17–29 (mobile toggle) · AGENTS.md: “AppShell’s lg: breakpoint … don’t match” — vs layout/appshell_types.go:116–151 (Breakpoint MD/LG/XL, SidebarWidth, MobileNav slot)

The AGENTS.md adoption table marks layout.AppShell and navigation.SidebarNav “custom” because the library’s fixed lg: breakpoint and standard classes don’t match the deeply themed layout. Research finding: upstream shipped typed AppShellProps.Breakpoint (MD/LG/XL) and SidebarWidth exactly for this. SidebarNav has Brand/Header/Footer slots and CurrentPath auto-activation — covering the adminui sidebar’s feature set (the active-state inline style would map to library classes or a small BaseProps.Class addition).

Remaining genuinely custom needs: the --sidebar-bg/--surface CSS-var theming (expressible via BaseProps/Class), the sync-bar in the header (fits AppShell’s Header slot — any templ component), and the translucent backdrop-blur. Feasible today at medium effort for ~95 deleted lines (templ + JS + scrim), but the hand-rolled version works and is paid for. Recommendation: keep for now, delete the stale blocker rationale from AGENTS.md, and re-evaluate at the next layout change.

Partially Used

F7 — forms.Form/CSRFToken bypassed for raw <form> elements

tenants.templ:74 · members.templ:27,57 · users.templ:23 — vs forms/form.templ:146–176 (CSRFToken, Layout=Inline, Validate, Wire)

Four hand-rolled <form hx-post> elements. CSRF works today via the admin.js meta-tag header injection (admin.js:10–15) — functional, but imperative. forms.Form makes the token declarative per-form (CSRFToken hidden input), gives Layout: Inline for the add-member row (replacing the manual flex classes), and Validate for pre-submit HTML5 constraint checks. Medium value: adopt opportunistically when touching these forms, not as a dedicated change.

Missed Opportunity · easy

F11 — Hand-rolled “← Back” links; Breadcrumbs unused

users.templ:105 · tenants.templ:69,104 — vs navigation/breadcrumbs.templ (Items, JSONLD, CurrentPath auto-activation)

Three one-link back rows duplicated by hand. navigation.Breadcrumbs gives the trail, separator, active detection, and optional JSON-LD — and composes into PageHeader.Breadcrumb (F2), so fixing F2 naturally pulls this in.

06Evaluated and rejected

Components that look like matches but are not (keep the current code)

htmx.ConfirmDelete — renders a plain red text-link button with hx-confirm. Adminui’s destructive actions are full display.Buttons with icons plus the CSP-safe data-confirm + htmx:confirm listener (admin.js:48–56), which the dashboardui CSP work standardized. Adopting ConfirmDelete would downgrade the controls.

layout.ThemeToggle/ThemeScript — adminui’s dark mode is token-remapping under prefers-color-scheme; a manual toggle would need a class-strategy variant and add UI chrome for little gain in an admin panel. Not applicable by design.

layout.Base/Minimal — adminui owns its <head> deliberately (CSRF meta tag, self-hosted htmx.js from the root module, per-brand accent injection). Correct for a mountable panel.

Charts, Kanban, Calendar, wire/Datastar — no matching use case in a user-management panel (utils/wire’s dual-transport is HTMX-only here; charts belong to dashboardui’s domain).

Verification protocol (for each step)

1

Render parity first

adminui has golden-style render tests (seed_render_test.go, layout_render_test.go). Capture current HTML for each touched page before the swap; expect byte-identical output for F1/F5 (stroke-width 1.8 parity) and intentional diffs for F2/F3/F4.

2

Tailwind rescan + style parity

The compiled admin-tw.css is produced by the nix build-adminui-css app, which scans library *.templ files. After adopting navigation/errorpage classes, rebuild CSS and confirm the new classes (pagination, breadcrumb) survived the scan — and that removing the Flush hack doesn’t double-border the five nested tables.

3

Module gates

Per repo convention: GOEXPERIMENT=jsonv2 go test ./... -count=1 -race in adminui, nix run .#lint (0-issue bar), and nix run .#check-modules if go.mod changes (upstream StatusBadge patch bumps the family train).
