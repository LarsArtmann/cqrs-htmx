03DON'T — Research-Confirmed Dead Ends

Rejected

Extract openapi/ as standalone repo

openapi/ sub-package (577 LOC, zero deps)

The Go OpenAPI library space is saturated. swaggo/swag (12.9k stars), go-swagger (10k), oapi-codegen (8.5k), huma (4.3k), kin-openapi (3.3k), fuego (1.7k). The closest competitor to a manual builder (swaggest/openapi-go) has only 115 importers. The market is moving toward reflection-from-types (Huma, Fuego), away from manual builders entirely.

Verdict: Keep in cqrs-htmx. It's small, self-contained, zero-dep, serves WithOpenAPI. Nobody outside cqrs-htmx is asking for it.
Rejected

Adopt Huma-style reflection for OpenAPI generation

Fundamentally incompatible architecture

Huma's Register[I, O](api, op, func(ctx, *I) (*O, error)) assumes the HTTP input type IS the thing you document. cqrs-htmx's mapper closures (DecodeJSONWithRequest(func(r, body) → command)) deliberately decouple HTTP request structs from CQRS command structs. The reflection system cannot see through the closure boundary.

Verdict: Reflection is the better idea for greenfield frameworks. But cqrs-htmx's architectural boundary (mapper closures) is incompatible with it. Not a bolt-on.
Rejected

Extract SSE/WS building blocks

Thin wrappers over go-sse (already extracted as a separate repo). The value-add (AfterDispatchHook integration) is cqrs-htmx-specific. Not enough standalone value.

Rejected

Extract HTMX serving / offline sync

04Huma Deep Dive — Is Reflection-From-Types Better?

Research into danielgtaylor/huma (v2, 4.3k stars) prompted the question: is the code-first reflection approach better than cqrs-htmx's manual builder?

How Huma Works (verified from source)

Huma uses runtime reflection on Go struct type parameters at handler registration time. The universal signature: func(ctx, *I) (*O, error). Struct tags (path:, query:, header:, maxLength:, enum:, etc.) serve as dual-purpose annotations — each tag generates both an OpenAPI schema field AND a runtime validation rule.

What Huma Proved Wrong in Earlier Claims

Earlier (wrong) claimReality
"huma owns the router"Router-agnostic: 9 official adapters (net/http, Chi, Gin, Echo, Fiber, gorilla/mux, httprouter, bunrouter, Flow)
"every endpoint is JSON-in/JSON-out"Supports multipart forms, SSE (first-class), streaming responses, HTML/HTMX
"reflection can't work without owning the router"Reflection happens on type params at registration, independent of routing

Why It Still Doesn't Work for cqrs-htmx

Huma's Register[I, O] assumes I (HTTP input) IS the documented type. cqrs-htmx's app.Command("Type", DecodeJSON(mapper)) deliberately separates HTTP request structs from CQRS command structs via closure mappers. The documented type and the dispatched command are intentionally different types — that's the CQRS architectural boundary.
