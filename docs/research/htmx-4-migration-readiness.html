Executive Summary

HTMX 4.0 is a major rewrite that skips v3 entirely. It introduces 9 breaking changes, a new extension system, and a new config notation (HCON). This audit maps each change to our codebase and assesses migration risk.

Safe ✓

Header names unchanged. No htmx event names in Go code. No queue: modifier usage. No hx-disable attribute. OOB swap still works (order change is cosmetic).

Needs Attention

Error responses now get swapped into the DOM by default. CSRF may behave differently with fetch() transport. nosurf compatibility unverified. OOB swap order reversed.

Already Prepared

HTMXScriptHandlerWith() lets consumers serve htmx 4.0 JS without forking. HTMXCDNScriptTag() provides CDN loading. The library is transport-agnostic at the API level.

Bottom line: The Go library code is ~90% compatible with htmx 4.0. The remaining 10% is CSRF transport behavior (needs browser testing) and error response design (needs a consumer decision). No Go code changes are strictly required — the migration is primarily a consumer-side concern.

Breaking Changes — Codebase Impact

Each of the 9 breaking changes from the htmx 4.0 migration guide, mapped to specific code in cqrs-htmx.

Critical 1. fetch() transport replaces XMLHttpRequest

htmx 4.0 uses the Fetch API instead of XMLHttpRequest for all requests. This is an irreversible architectural change that affects cookie handling, credentials, and cross-origin behavior.

Affected code: csrf_middleware.go — setPlaintextHTTPOrigin() sets Sec-Fetch-Site: same-origin. With fetch(), the browser sets this header natively. Our manual injection may conflict or become redundant. Needs browser testing.

Risk: Cookie-based CSRF tokens may not be sent by default with fetch() unless credentials: 'same-origin' (or 'include') is set. htmx 4.0's default is unknown — must verify.
High 2. Error responses (4xx/5xx) now swap into the DOM

In htmx 2.x, error responses are silently ignored (no swap). In htmx 4.0, they are swapped into the target element by default. This means our error handler's response body will appear in the consumer's UI.

Affected code: errors.go:99-130 — DefaultErrorHandlerWithRedirect writes plain text error messages via io.WriteString(w, err.Error()). In v4, this text would be swapped into the DOM target.

Mitigation: Auth errors are already safe — they use HX-Redirect which htmx follows regardless of status code. For other errors, consumers should either: (a) render HTML error partials, (b) set HX-Retarget to redirect errors to an error container, or (c) use the hx-status attribute to control swap behavior.
Low 3. Explicit inheritance with :inherited

Attributes like hx-headers, hx-vals, and hx-confirm no longer inherit from parent elements by default. You must add :inherited to opt in.

Affected code: csrf_helpers.go:47-65 — CSRFTokenHXHeaders() generates hx-headers attributes. If consumers place these on a parent element (e.g., <body>), the token will no longer be inherited by child elements in v4.

Mitigation: Document that consumers using v4 should add :inherited or place hx-headers on the specific elements making requests.
Low 4. hx-delete no longer includes form data

DELETE requests triggered by hx-delete no longer automatically include form field values in the request body.

Affected code: None. The library's form decoder (decoder.go) handles request bodies generically. If consumers send DELETE with form data, they'll need hx-vals in v4.
No Impact 5. No localStorage history (sessionStorage only)

htmx 4.0 uses sessionStorage instead of localStorage for history persistence. This means history is lost when the tab closes.

Affected code: None. This is a client-side-only change with no server-side impact.
Low 6. OOB swap order reversed

Out-of-band swaps now happen after the main swap, instead of before.

Affected code: ws.go:124-131 — WSOOBHTML() wraps HTML with hx-swap-oob attributes. The attribute still works; only the execution order changes. Consumers relying on OOB content being present before the main swap needs may see a difference.
No Impact 7. queue: modifier removed

The queue:last, queue:first, queue:all modifiers on hx-trigger are removed. Use hx-sync instead.

Affected code: None. The library never generates hx-trigger attributes with queue: modifiers.
No Impact 8. Default timeout increased to 60s

The default request timeout changed from no limit to 60 seconds.

Affected code: app.go — Config.Timeout wraps the dispatch call. Server-side timeout is independent of client-side timeout. No change needed.
No Impact 9. Extension loading via script include

Extensions are now loaded by including their script tag, not via htmx.defineExtension().

Affected code: None. The library has no extension loading code. Consumers manage their own client-side extensions.

CSRF Transport Risk Analysis

The switch from XMLHttpRequest to fetch() is the single most impactful change for CSRF. This is a deep-dive into the specific code paths affected.

Current CSRF Architecture

Our CSRF implementation uses justinas/nosurf v1.2.0, which works at the HTTP middleware level — it reads the CSRF token from either a form field (csrf_token) or a request header (X-CSRF-Token). nosurf does NOT depend on XMLHttpRequest — it reads standard HTTP headers and form bodies.

The good news: nosurf operates on server-side HTTP, not client-side transport. The switch from XMLHttpRequest to fetch() does NOT change what nosurf sees on the server. The token still arrives via form field or X-CSRF-Token header regardless of transport.

Potential Issues

High

Cookie credentials behavior

fetch() does not send cookies by default unless credentials: 'same-origin' (or 'include') is set. htmx 2.x (via XMLHttpRequest) always sent same-origin cookies. If htmx 4.0's fetch() calls don't set credentials, the CSRF cookie won't be sent, and nosurf won't find it.

Mitigation: nosurf's default reads the token from the form field or header, NOT from the cookie. The cookie is only used for token storage on the client. As long as consumers include the token via hx-headers (our CSRFTokenHXHeaders() helper) or a hidden form field (CSRFTokenFormField()), CSRF will work regardless of cookie behavior.
Medium

Sec-Fetch-Site header injection

csrf_middleware.go:98-108 — setPlaintextHTTPOrigin() manually sets the Sec-Fetch-Site: same-origin header for plain HTTP requests from trusted proxies. With fetch(), the browser sets this header natively. Our injection may:

  • Become redundant (browser already sets it correctly)
  • Conflict if htmx sets its own Sec-Fetch-* headers
  • Still be needed for nosurf's origin check (nosurf uses it for safe-method bypass)
Action: Browser-test whether fetch() sends Sec-Fetch-Site correctly for same-origin requests. If yes, the manual injection can be simplified to a no-op for htmx 4.0 consumers. If no, the existing code is a valid polyfill.
Low

Cross-origin requests

With fetch(), CORS preflight (OPTIONS) behavior may differ. Consumers using htmx for cross-origin requests (rare) should verify CORS headers. The library itself doesn't set CORS headers — it's the consumer's responsibility.

CSRF Token Delivery Paths

The library provides three ways for consumers to deliver CSRF tokens to htmx:

Method Helper Function v2 Compatible v4 Compatible Notes
hx-headers attribute CSRFTokenHXHeaders() ✓ Yes ⚠ Needs :inherited v4: inheritance changed, place on request element
Hidden form field CSRFTokenFormField() ✓ Yes ✓ Yes Transport-agnostic, always works
Meta tag + JS injection CSRFTokenHTMLMeta() ✓ Yes ✓ Yes Consumer's JS reads meta, sets header
Response header resp.CSRFToken(token) ✓ Yes ✓ Yes Sets X-CSRF-Token on response
Recommendation: The hidden form field approach (CSRFTokenFormField()) is the most robust — it works identically in v2 and v4, is immune to transport changes, and doesn't depend on attribute inheritance. Document this as the recommended approach for v4 consumers.

Error Response Swap Behavior

htmx 4.0 swaps error response bodies (4xx/5xx) into the target element by default. This is the second-biggest migration concern after CSRF.

Current Error Handling

// errors.go — DefaultErrorHandlerWithRedirect func DefaultErrorHandlerWithRedirect(loginRedirect string) ErrorHandler { return func(w http.ResponseWriter, r *http.Request, err error) { status := MapError(err) // Auth errors → HX-Redirect (works in v2 and v4) if isAuthError(err) && IsHTMXRequest(r) { writeHTMXAuthRedirect(w, loginRedirect) return } // Other errors → plain text body w.WriteHeader(status) io.WriteString(w, err.Error()) } }

Impact in v2 vs v4

htmx 2.x

Error responses (4xx/5xx) are silently ignored. The response body is never swapped. Only HX-Redirect and HX-Refresh headers are processed on error responses.

Result: io.WriteString(w, err.Error()) produces a response that htmx ignores. The consumer sees no visible change.

htmx 4.0

Error responses are swapped into the target by default. The plain text error message will appear inside whatever DOM element was the hx-target.

Result: Consumers will see raw error text like "validation failed: email is required" rendered inside their UI. This may be undesirable.

Migration Options

Option A: HTML Partials

Change error handlers to render HTML partials instead of plain text. Most flexible, but requires the library to know about HTML templates.

Library change

Option B: HX-Retarget

Set HX-Retarget on error responses to redirect them to a dedicated error container (e.g., #error-toast).

Consumer config

Option C: hx-status

Use htmx 4.0's new hx-status attribute to control swap behavior per response status code.

Consumer config
Library principle: The library should NOT impose an error rendering strategy. The existing ErrorHandler interface already lets consumers provide custom error handlers. For v4, consumers who want HTML error partials should implement their own ErrorHandler. No library change is needed — this is a documentation concern.

Already Prepared

Changes we've already made to prepare for htmx 4.0.

Done ✓ Pluggable HTMX Script Serving

htmx_serve.go — Added HTMXScriptHandlerWith(js []byte, version string) that lets consumers serve any htmx JS build (including v4 betas) with proper Content-Type, ETag, and Cache-Control headers. HTMXScriptHandler() now delegates to this.

Usage:
// Serve htmx 4.0 beta from Go binary customJS, _ := os.ReadFile("htmx-4.0.0-beta4.min.js") mux.Handle("/static/htmx.js", cqrshtmx.HTMXScriptHandlerWith(customJS, "4.0.0-beta4"))
Done ✓ CDN Script Tag Helper

htmx_serve.go — Added HTMXCDNScriptTag(version string) for consumers who prefer CDN loading over self-hosting. Empty version uses the embedded library version.

Usage:
// CDN with explicit version tag := cqrshtmx.HTMXCDNScriptTag("4.0.0") // => <script src="https://unpkg.com/htmx.org@4.0.0"></script>
Done ✓ Version Single-Source-of-Truth

htmx_embed.go — Extracted htmxVersion = "2.0.9" as a package-level const. Previously the version string was duplicated in 3 places (HTMXVersion, ETag, If-None-Match check). Now a single constant drives all three.

Done ✓ Transport-Agnostic Design

The library's entire API operates on net/http types — http.ResponseWriter, *http.Request, headers, and bodies. It has zero coupling to XMLHttpRequest, fetch(), or any client-side transport. The server sees standard HTTP regardless of what the client uses.

  • Test CSRF token delivery (verify X-CSRF-Token arrives via fetch())
  • Verify OOB swap order if relying on pre-main-swap OOB content
  • Update htmx:* event listeners (if any in client-side JS)
  • Load extensions via <script> tags instead of defineExtension

Recommendation

Should cqrs-htmx adopt htmx 4.0 now, wait, or prepare?

Do NOT adopt htmx 4.0 yet. As of this audit, htmx 4.0 is in beta (4.0.0-beta4 on npm next tag). The library principle dictates that consumers inherit the risk of our dependencies. Shipping a beta HTMX version embedded in a library would expose every consumer to potential breaking changes between beta releases.

Short Term (Now)

  • Keep embedded htmx at v2.0.9 (stable)
  • Document the pluggable API for early adopters
  • Point consumers to HTMXScriptHandlerWith() if they want v4
  • Monitor htmx 4.0 release candidates

Medium Term (Post-v4-Stable)

  • Upgrade embedded JS to v4 stable once released
  • Run full CSRF browser test suite against v4
  • Update documentation with v4-specific guidance
  • Bump major version (v3.0.0) for the embedded JS change
The library is ready. Consumers who want to try htmx 4.0 today can do so via HTMXScriptHandlerWith(customJS, "4.0.0-beta4") without any library changes. The server-side API is fully compatible. The only risks are client-side: CSRF cookie behavior and error response rendering. Both are consumer-side concerns that the library correctly leaves to the application.
