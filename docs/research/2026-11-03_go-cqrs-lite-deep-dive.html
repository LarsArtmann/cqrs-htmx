00Summary

This is the third utilization audit of go-cqrs-lite against this workspace. The first (2026-06-14, v2 era) scored 42% and its eleven gaps are all closed today. The second (2026-07-30) produced docs/guides/leveraging-go-cqrs-lite.md, the capability map that still anchors consumer docs. Since then the upstream library pivoted — ADR-0123 makes system.New + metaengine the only sanctioned composition for new apps, and the v1 read-model tiers this workspace's SQL read models ride on are now deprecated-with-v5-removal. This audit re-measures adoption against that moved goalpost: 47 capability rows graded, 37 applicable, 22 fully leveraged — 73/100, high band. Version currency is perfect: all 15 pinned module trains sit at their latest tags (verified 2026-11-03), and the cqrs-upgrade scanner is already an operational habit here (ADR-0051 was written from its output).

The bottom line Adoption is high and disciplined, with zero anti-patterns and every prior audit gap closed. The one strategic exposure is already decided, not discovered: the default usermgmt composition rides stack/SQLViewStore surfaces that upstream deletes at v5, and ADR-0051 gates the metaengine migration on a recorded criterion (secondary-index semantics + declarative hydration). The five missed opportunities are cheap: derive the event catalog instead of hand-maintaining it, decide (or adopt) CBOR for byte-heavy payloads, wire command lifecycle streams, and stop hand-rolling replay-seam dedup that dedup.Ring already provides.

Missed Opportunity · Medium-high impact · low effort

The event catalog is hand-maintained while upstream can derive it — with a drift gate

usermgmt/es_event_catalog.go:13-25 · 24 events registered by hand, field lists marked illustrative

usermgmt.DefaultEventCatalog() hand-builds every event entry — schema versions, descriptions, and field lists that the file's own //nolint:exhaustruct // field lists are illustrative comment admits can drift from the real payloads. Upstream's systemcatalog module derives the same catalog from declared + runtime truth: FromDomainConfig(ctx, domain) boots an ephemeral memory system, reflects payload schemas from the registrations, stamps versions from DomainConfig.Schema, and pairs with catalog.AssertInventory as a compile-time drift gate. The bridge module already declares everything the derivation needs — systemadapter.DomainConfig() sets Schema: EventSchemas() and a ProjectionTypeDecoder (domain_config.go:66-67) — so the inputs exist and are equivalence-tested; only the catalog consumer path is hand-rolled.

Recommendation Derive the identity catalog from the declared domain instead of maintaining it by hand, and keep the curated layer (descriptions, owners) as overrides. 
// systemadapter (or a thin usermgmt wrapper): derive, then curate.
cat, err := systemcatalog.FromDomainConfig(ctx,
    systemadapter.DomainConfig(),
    systemcatalog.WithServiceID("cqrs-htmx-identity"),
    systemcatalog.WithMessageOverrides(map[string]systemcatalog.MessageConfig{
        "user.registered": {Title: "User Registered"},
    }),
)
// gate: catalog.AssertInventory(cat, expected) pins the 24-event inventory
// so a new payload field or event type cannot land undocumented.
Missed Opportunity · Medium impact · decision first, then low effort

Byte-heavy payloads ride JSON — CBOR is ~35% smaller and events are self-describing

identity-model/events.go:45,53,67,135 · CredentialRemoved/CredentialUsed/TOTPEnabled/BotRegistered payloads ([]byte fields)

cqrs-lint flags four payload types carrying []byte fields through the JSON codec (P009 ×4, plus F008 at the package level): JSON base64-inflates binary data by 33%, and these are exactly the binary fields — WebAuthn credential IDs/public keys, TOTP secrets, bot token hashes. Upstream stamps the encoding per event, so mixed JSON+CBOR journals decode correctly, and codec.TranscodeToJSON exists for browser seams. The honest counterweights: JSON journals are human-debuggable, the SSE envelope bytes are golden-pinned, and the FAQ records a CBOR time.Time quantization caveat (~165 ns single-hop) — none of which apply to pure-[]byte payloads. No ADR records this decision either way; today it is an accident of defaults.

Recommendation Write the decision down first (one ADR paragraph), then adopt CBOR for the four binary payloads only — self-describing events make this a per-event choice, not a migration. 
// Binary payloads opt into CBOR; every other payload stays JSON.
opts := []event.Option{
    event.WithCodec(codec.CBORCodec{}), // stamped per event
    event.WithSchemaVersion(1),
}
// Journals stay mixed-safe: Record.Encoding says which codec produced
// each payload; DecodePayloadAuto honors it on every read path.
Partially Used · Strategic · direction decided (ADR-0051), execution gated

system.New is bridged and equivalence-tested — but not the default composition

systemadapter/ (12 files) · opt-in; usermgmt NewService/NewEventSourcedSetup still compose decider+stack directly

Upstream's ADR-0123 makes system.New + metaengine the only sanctioned composition for new apps, and the module was promoted from experimental to the production composition root on 2026-11-03 — the day of this audit. This workspace's answer is systemadapter: DomainConfig (4 deciders, 21 commands, 25-event TypeDecoder), engine presets (memory/sqlite/split-sqlite, presets.go:29-70), and declarative projections whose equivalence with the legacy path is pinned by tests (TestDeclarative_EquivalenceWithProjectionLayer). It is nonetheless an opt-in side door: the default composition path (NewService, NewEventSourcedSetup, the SQL setup templates) still wires decider repositories by hand. ADR-0051 records why — the stack presets' value IS the wiring, and cluster 1 (the SQL read models) stays until metaengine expresses secondary-index lookups declaratively. The criterion is written; this finding tracks its execution.

Recommendation No new code today. When the cluster-1 criterion fires (FilterOnField-class keyed access + declarative hydration), migrate the read models and promote systemadapter.RecommendedSQLiteDeployment to the default SQL path — the equivalence tests are already the migration proof.
Partially Used · managed v5 exposure · 68 gated findings

SQL read models ride the v5-removed SQLViewStore surface — gated, with a written criterion

usermgmt/sql_readmodel_extra.go:31,101 · kv.ViewQuerier conditions · ADR-0051 cluster 1

The four SQL read models are built on storage.SQLViewStore/kv view queries — 68 of the 78 v5-removed-API findings cqrs-upgrade reported on 2026-09-20. ADR-0051 dispositioned them deliberately: they compile and test green on v4 trains, and migration to metaengine planned tables waits until the planner covers secondary-index semantics (FindByEmail-style keyed access) and a declarative equivalent of the hydration contract. The risk is real but priced: the v5 cut turns each use into a compile error, and the inventory lives in docs/guides/v5-removal-inventory.md. The adjacent seam is also the partial: kv.Cache read-side caching was evaluated (ROADMAP, 2026-07-30) with precise guidance (cache FindByID, never FindByEmail) but never wired.

Recommendation Keep the gate; add the kv.Cache write-through for FindByID paths now (it is v5-neutral and orthogonal), and re-run cqrs-upgrade --dry-run --workspace on every sweep so the 68-finding count only ever shrink.
Partially Used · hand-rolled duplication at the SSE replay seam

Replay-seam dedup is a raw map while dedup.Ring sits bench-only

transport/serve.go:185-190,281,543 · dedup/v4 imported only by usermgmt/es_dedup_benchmark_test.go:29

The SSE replay/live seam deduplicates by recording returned event IDs in replayed map[string]struct{} — unbounded, hand-rolled, and flagged by cqrs-lint C035 as an unguarded map on the two structs that carry it (replayAdjustedStore, filteredReplayStore). Upstream ships exactly this primitive: dedup.Ring, a bounded O(1) fixed-capacity ID filter documented for stream boundaries. The workspace's only use of the module is a benchmark that measures the Ring it never wires into the seam that needs it. 

// Before (serve.go): unbounded map, C035-flagged struct
replayed map[string]struct{}

// After: bounded, purpose-built, drops oldest beyond capacity
seen := dedup.NewRing[string](dedup.DefaultCapacity)
if seen.Has(id) { continue }
Recommendation Replace the seam map with dedup.Ring (per-connection lifetime bounds it naturally), which also retires both C035 warnings rather than suppressing them.

Errata (2026-11-03, post-publish): the snippet originally read seen.Seen(id) — the v4.3.0 API is Has/Add (verified at the pinned tag). Corrected in place; also note systemcatalog (finding 1) has no published v4 tag yet — the drift-gate half is buildable today on pinned catalog/v4 v4.11.0 (SchemaFromType[T] + AssertInventory); the module itself waits on an upstream tag.

Missed Opportunity · Low-medium impact · optional wiring

Command lifecycle streams absent — dashboards audit records, not fates

not imported anywhere · dashboardui reads command/query stores (system_bridge.go:23-58)

Upstream's commandlifecycle records every command's fate as events — Received/Rejected/Failed/Retried/DeadLettered/ Completed — with ready projections (DeadLetterQueue, RetryCount, FailureLog, ProcessingTime, CommandsByActor). dashboardui's audit views read raw command/query records from the stores; they can show what was dispatched, never what happened to the retries and dead letters the middleware guide teaches consumers to enable. With retry/recovery middleware a documented default recommendation, the lifecycle stream is the observability half of that advice.

Recommendation Offer lifecycle recording as an opt-in ServiceConfig/CommandMiddleware wiring (the module's outer+attempt middleware pair slots into the existing seam), and surface FailureLog/RetryCount in dashboardui beside the store views.
Partially Used · durability default

Projection DLQ defaults to memory — poison events evaporate on restart

usermgmt/es_projection_setup.go:118 · projectionhost.NewMemoryDeadLetterStore(), retries 0

The default projection host parks poison messages in an in-memory DLQ. A restart drops them silently — the events that most need human attention are the least durable in the system. Upstream ships projectionhost.SQLiteDeadLetterStore (plus DeadLetterStoreAdmin with Count/ListPaged/PurgeBefore), and the declarative path documents WithDeadLetterStore as the seam (declarative-projections.md §91-110). Neither is wired as the default for SQL deployments, where a file-backed DLQ is one constructor away.

Recommendation For the SQL setups (sqlite/postgres/mysql), default the DLQ to the SQLite store; keep memory for the in-memory deployment where everything else is equally ephemeral.
Partially Used · throughput knob left at default

Checkpoint batching options unused — every event writes a checkpoint

usermgmt/es_projection_setup.go:115-122 · no WithCheckpointEvery/WithCheckpointInterval anywhere in the tree

projectionhost defaults to save-per-event checkpoints — the most durable, the most write-amplified. Upstream added WithCheckpointEvery(n) / WithCheckpointInterval(d) for high-throughput projections (batch the saves; crash replays at most n events — the folds are idempotent by construction here, so the trade is free correctness-wise). The options are simply never used, and there is no seam to tune them from ServiceConfig.

Recommendation Expose ProjectionHostOptions on the setup paths (the systemadapter side already has WithHostOptions, options.go:49) and document the batching tradeoff for replay-heavy deployments.
Partially Used · forward-looking

Engine breadth unexposed — presets stop at memory/sqlite/split

systemadapter/presets.go:29-70 · RecommendedMemoryDeployment / RecommendedSQLiteDeployment / RecommendedSplitSQLiteDeployment

metaengine has first-class engines for pebble (~7× faster point reads than SQLite on MapGet), bbolt, badger, postgres, duckdb, turso (embedded encryption, materialized views), bigtable (native as-of reads), and dgraph. The bridge module presets three deployments. That is the right scope today — the default path does not route through metaengine yet — but it means the marketing claim "any engine, one DeploymentConfig" is one preset function away from being demoable per engine.

Partially Used · v5 hygiene tail

Small v5-prep items: deprecated CausationID reads, snapshot shape-version stamping

dashboardui/detail_items.go:166,187,269 · meta.CausationID; usermgmt/snapshot.go (no WithSnapshotStateVersion)

Two cheap hardenings: (1) dashboardui still reads meta.CausationID — the implied-kind field upstream replaced with structural record.Cause{Kind,ID} and deletes at v5; three display sites, a mechanical rename. (2) decider.WithSnapshotStateVersion[State](n) stamps saved snapshots with the state-shape version and discards stale shapes on load — free insurance for the day a fold changes state shape and old snapshots would otherwise hydrate garbage.

Recommendation Fold both into the next family sweep: Cause reads in dashboardui (3 lines), shape-version stamping in repositoryOptions (1 option line).
Missed Opportunity · documentation · trivial effort

Guide gaps: flightrecorder and otel/otlp deserve a paragraph; test helpers deserve adoption

docs/guides/leveraging-go-cqrs-lite.md (no matches for flightrecorder/SetupOTLP) · testutil/idtest/querytest imported nowhere

The capability map documents 58 modules but predates three conveniences: go-flightrecorder (zero-dep runtime/trace capture with CQRS middleware triggers — the "capture execution traces on slow commands or errors" story), otel/otlp.SetupOTLP (one-call OTLP/HTTP exporters, no gRPC dep — the guide only mentions an exporter in a code comment at line 191), and the test helpers (testutil.MustNewCmd, id/idtest, query/querytest) that replace hand-rolled test constructors with tb.Fatalf-on-error variants.

Recommendation Three short additions to the guide's §2/§6, and adopt the test helpers as new tests are written (no migration needed).
