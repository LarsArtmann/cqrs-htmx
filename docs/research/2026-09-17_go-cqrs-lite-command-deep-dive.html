00Summary

cqrs-htmx uses commands everywhere it should structurally: all 20 identity-domain commands are registered via command.RegisterTyped, every command struct embeds *command.BasicCommand, the HTTP↔CQRS bridge enriches and dispatches through the dispatcher in both typed and untyped form, and errors flow through the dispatcher's error-family wrapping into MapError. Six of the 27 modules use commands directly; the rest are UI, transport, or strategy modules for which that is architecturally correct.

The gaps are systemic rather than mechanical. The library's own most-used command pipeline — usermgmt's 20-command internal dispatcher — ships with zero middleware and no config hook for consumers to add any. The upstream audit-trail chain (CommandActorContext → ActorEnricher) has zero call sites in this repo, so every event the library's own domain emits is anonymous. Command idempotency and command persistence are entirely unadopted, which leaves the dashboard's command audit view dead for the default stack.

The bottom line The library documents and exports everything needed for a complete audit trail — CommandOptionsFromContext, WithActor, CommandActorContext, ActorEnricher — yet none of it is wired end-to-end in its own domain: commands are constructed without metadata and repositories are built without an enricher. Fixing the two wiring points (findings 1 and 2) is roughly a dozen lines and would activate the audit story the project already sells.

03Findings

Ordered by impact. Every claim is cited to source.

Missed Opportunity · High impact

The audit-trail chain is unwired — every event from the library's own domain is anonymous

usermgmt/snapshot.go:88-91 (repositoryOptions) · identity-model/commands.go (constructors take no metadata) · zero call sites of middleware.CommandActorContext / event.ActorEnricher repo-wide

go-cqrs-lite documents a precise two-link chain for attributing events to actors: middleware.CommandActorContext() on the dispatcher copies the command's actor metadata into the context, and decider.WithEnricher(event.ActorEnricher) on the repository writes it into every emitted event (upstream event/actor_context.go:35-49, middleware/actor.go:18-49). A causation counterpart (CommandCausalityEnricher) links events to the command that produced them. cqrs-htmx wires neither link: repositoryOptions carries only snapshot options and a state cache, and none of the 20 command constructors accept or set metadata. Result: ~25 dispatch sites in usermgmt emit events with zero actor/causation attribution, so the auditlog bridge (auditlog/v4) and dashboardui's audit views render the library's own activity as anonymous. The project lists "Event propagation: event.WithActor" as an integration win — but it exists only as an exported helper for consumers, not in the domain itself. 

// Before: usermgmt/snapshot.go:88 — the complete option list today
func repositoryOptions[State any](config SnapshotConfig) []decider.RepositoryOption[State] {
	opts := snapshotOptions[State](config)
	return append(opts, decider.WithStateCache[State](decider.NewStateCache[State](0)))
	// no WithEnricher — events never inherit the actor
}

// After: two wiring points activate the whole chain
opts = append(opts, decider.WithEnricher[State](event.ActorEnricher))

// usermgmt/service_core.go, next to RegisterCommands:
dispatcher.Use(middleware.CommandActorContext())
Fix Add decider.WithEnricher(event.ActorEnricher) (and ideally CommandCausalityEnricher) to repositoryOptions, and dispatcher.Use(middleware.CommandActorContext()) in NewService after command registration. Then make usermgmt's service methods apply CommandOptionsFromContext(ctx) onto commands before dispatch so HTTP-derived identity actually reaches the metadata.
Misused · High impact

HTTP metadata enrichment silently skips the library's own command pattern

handler.go:347-351 · affects every command embedding *BasicCommand (all 20 identity-model types, datastar-demo)

enrichCommandFromContext applies the context-derived options only when the decoded command's dynamic type is exactly *command.BasicCommand. Every identity-model command is a wrapper struct embedding *BasicCommand — its dynamic type is *RegisterUserCmd etc., so the assertion fails and enrichment is silently skipped (the comment on handler.go:338-341 documents the skip). Upstream solved this exact problem with the MetadataCarrier capability interface (command/capability.go:9-16): "middleware ... type-asserts Command to MetadataCarrier instead of growing the exported Command interface". Because embedding promotes ApplyOptions to the wrapper, a one-line structural interface covers both plain and embedded commands. Compounding factor: usermgmt's HTTP handlers bypass App.Command entirely (they call service methods that dispatch internally), so root enrichment never even runs for the library's own domain — the affected population is consumers' embedded-command endpoints, of which examples/basic/main.go:316 is the only in-repo site that re-applies the options manually. 

// Before: handler.go:347 — exact-type assertion; embedded commands skipped
func enrichCommandFromContext(ctx context.Context, cmd command.Command) {
	if basic, ok := cmd.(*command.BasicCommand); ok {
		for _, opt := range CommandOptionsFromContext(ctx) { opt(basic) }
	}
}

// After: structural — matches *BasicCommand AND every wrapper embedding it
type optionApplier interface { ApplyOptions(...command.Option) }

func enrichCommandFromContext(ctx context.Context, cmd command.Command) {
	if ap, ok := cmd.(optionApplier); ok {
		ap.ApplyOptions(CommandOptionsFromContext(ctx)...)
	}
}
Fix Swap the concrete assertion for the structural ApplyOptions interface (same published API surface, so the hermetic-build rationale in the existing comment still holds), and log at debug level when enrichment finds nothing to apply. Add a regression test dispatching an embedded BasicCommand wrapper through App.Command.
Missed Opportunity · Medium-high impact

usermgmt's internal dispatcher ships bare — 20 commands, zero middleware, no consumer hook

usermgmt/service_core.go:331-347 · usermgmt/config.go (ServiceConfig exposes SecurityHooks for the event bus only)

NewService constructs command.NewDispatcher() and registers all 20 handlers, but never calls Use() — no recovery, no retry, no circuit breaker, no metrics, no tracing on the library's most-travelled write path. The asymmetry is stark: the event bus gets configurable middleware (SecurityHooks.PublishMiddleware/HandlerMiddleware), the command dispatcher gets none, and ServiceConfig offers no field through which a consumer could add any. Meanwhile root's own doc.go:66-85 documents the zero-glue composition and two examples prove it — the capability is one struct field away. 

// After: ServiceConfig gains one field; NewService gains one line
type ServiceConfig struct {
	// CommandMiddleware runs at the CQRS layer for every dispatched command.
	// Applied before projections subscribe; nil = bare dispatcher (today's behavior).
	CommandMiddleware []command.Middleware
}

// service_core.go, after RegisterBotCommands:
dispatcher.Use(config.CommandMiddleware...)
Fix Add CommandMiddleware []command.Middleware to ServiceConfig/EventSourcedConfig (and thread it through setup.Config), applied in NewService. Document a recommended production chain (Recovery → Retry → CircuitBreaker → TypedMetrics) mirroring docs/guides/dispatch-middleware-ordering.md.
Missed Opportunity · Medium impact

No command idempotency on the mutation surface that needs it most

middleware.CommandIdempotency: zero call sites · risk surface: service_register.go:98, service_oauth2_extracted.go:214-336, email_verification.go:155

Register, verify-email, and OAuth link/unlink are exactly the paths where browsers retry and users double-submit. Today the defense is indirect: decider Conflict decisions plus the deliberately idempotent append handlers noted for at-least-once crash semantics. The upstream middleware provides systematic command-ID-keyed dedup with a TTL — one Use() call — and defaults to cmd.ID().String() as the key when no extractor is given (middleware/idempotency.go:57-69). 

dispatcher.Use(middleware.CommandIdempotency(
	store,             // idempotency.Store (in-memory dev, SQL in prod)
	10*time.Minute,    // dedup window
	nil,               // nil = key on cmd.ID().String()
))
Fix Wire CommandIdempotency via the new CommandMiddleware hook (finding 3) once a production-grade idempotency.Store is chosen; document the memory-only caveat for the default in-memory store.
Missed Opportunity · Medium impact

Command persistence never wired — the dashboard's command audit is dead by default

dashboardui/core/capabilities.go:51 (CommandJournal config field) · no command.Store wiring anywhere in usermgmt/setup · examples/dashboard-demo/main.go:43,75 (memory only)

dashboardui renders a full command audit view (list, detail, CSV/JSON export) over command.PersistedCommand — but nothing in the library's core stack ever persists a command, so the view only works for consumers who build their own journal (the demo uses an in-memory store). The unadopted TypedCommandStore[P] (typed_store.go:28) closes the untyped-payload hole at the store boundary. A SQL-backed command journal would also give finding 4's idempotency store a natural home and enable durable outbox semantics later.

Fix Add an optional CommandJournal to the EventSourcedConfig/SQL setup family that persists each dispatched command (type, stream ref, payload, metadata) next to the event journal, and document it as the producer that makes dashboardui's existing read-side live.
Nice to have · Low impact

Small hygiene gaps

service_core.go:331 (dispatcher never closed) · middleware.CommandValidation unused · doc.go:66-85 (guidance without a production chain)

Three low-cost items: (1) Dispatcher.Close() is never called — Service.Close stops projections, eviction loops, and the bus, but not the dispatcher; closing it would convert post-shutdown dispatch attempts into a clean errorfamily error instead of a silently running handler map. (2) CommandValidation could standardize syntactic 400s at the dispatch layer; domain invariants rightly stay in deciders, but duplicate ad-hoc checks in handlers could collapse. (3) No doc shows a complete recommended production middleware chain for usermgmt consumers specifically.

06Conclusion

cqrs-htmx leverages commands structurally at a level most CQRS codebases never reach — full typed coverage, clean decider separation, disciplined error propagation, and a current dependency. It leverages them ecosystem-wise at maybe a third of what the pinned release offers: the audit-trail chain, dispatch middleware, idempotency, and command persistence are all one wiring step away, and two of the four gaps are roughly a dozen lines each. The highest-leverage next change is not a feature — it is connecting the metadata plumbing the library already exports to the domain it already owns.
