The Three Core Transports

Each transport has distinct capabilities and limitations. A complete HTMX-aware CQRS library must speak each one fluently — pushing events, accepting commands, reporting errors, and surviving disconnection — using the right tool for each direction.

HTTP — the contract

Every interaction begins and ends here. Request body carries commands and queries; response body carries results. Status codes encode outcomes; MapError already maps CQRS error families to HTTP statuses. This is the baseline the other transports must match in expressive power, not duplicate.

SSE — the push

Pure server-to-client stream built on HTTP. The browser handles reconnection and replays Last-Event-ID automatically. Perfect for broadcasting domain events, live updates, and progress. Cannot receive commands from the client — by spec.

WebSocket — the channel

Bidirectional, persistent, lowest latency. The only transport that can carry commands and push events without polling. Comes with connection lifecycle, framing, ping/pong, and reconnection complexity that must be surfaced explicitly.

The Full Landscape

HTTP, SSE, and WebSocket are the three core transports — but the web offers twelve more. This catalogues every browser-native and server-to-server communication technology relevant to a real-time CQRS library, with an honest verdict on whether each belongs in cqrs-htmx. Exclusions are documented decisions, not oversights.

Decision Framework

Of the twelve technologies beyond the core three, only WebTransport and Fetch Streaming are legitimate candidates to become new matrix columns — they add capabilities the core transports cannot provide (QUIC datagrams and true bidirectional HTTP/2 streaming). Web Push earns its place as a separate module: it is the only technology that reaches a user when the tab is closed, a capability no live transport can replicate. Everything else is either a different paradigm (gRPC-Web, Webhooks), too niche (WebRTC), or dead (HTTP/2 Server Push, JSONP). The exclusion of each is a deliberate engineering decision, not an omission.

North Star — reached

A consumer of cqrs-htmx can swap transports without rewriting their CQRS handlers. The same command struct flows in via HTTP body, SSE-bridged POST, or WS frame; the same event struct flows out as HTTP response, SSE event, or WS message — with errors carried consistently by the same StructuredError payload type. Verified end-to-end by integration_transport_test.go.

Resolved Gaps & Remaining Boundaries

The four holes that once prevented cqrs-htmx from claiming "full transport coverage" are all closed and tested. What remains are three WebSocket cells that are deliberately out of scope — a consequence of the ownership model, not missing work. cqrs-htmx never owns the WebSocket connection; the consumer's WS library (gorilla, nhooyr, coder, …) does, so ping frames, replay state, and close handlers live there.

Remaining — architectural boundaries, not missing features

WS Heartbeat / Ping

Consumer-owned

WS ping/pong frames are a transport-layer concern owned by the consumer's WS library (e.g. conn.WriteMessage(websocket.PingMessage, nil)). cqrs-htmx writes application messages; it never holds the raw connection. The pattern is documented in the WSBroadcaster and DispatchWSCommand examples.

WS Resume / Replay

No WS spec equivalent

The WebSocket protocol has no Last-Event-ID header and no auto-reconnect — browsers don't replay for you the way they do for SSE. Reconnection and missed-message replay are an application-level contract the consumer must design (typically: reconnect, re-authenticate, fetch snapshot). A WSEventStore could be added if a consumer asks for it.

WS Connection Lifecycle

Consumer-owned

The consumer's read loop owns connection close: defer wsBroadcaster.Unsubscribe(ch) runs when conn.ReadMessage() returns an error, which IS the close hook. Adding a parallel OnClose would duplicate the WS library's own close handler. SSE needs OnDisconnect because SSEStream owns the response writer; WS does not own the socket.

Why three cells stay "missing"

SSE owns its http.ResponseWriter, so the library can heartbeat, replay, and hook disconnects directly. WebSocket hands the upgraded socket to the consumer's library, so cqrs-htmx only ever sees []byte in and writes []byte out. Pushing ping/replay/close into cqrs-htmx would require owning the connection — which means picking (and forcing) one WS library. The deliberate choice is to stay library-agnostic and document the consumer-side patterns instead.

Implementation Record

The Pareto-ordered plan that took cqrs-htmx from "HTTP complete, SSE partial, WS receive-only" to full transport parity. All five items shipped and are covered by tests. Listed in the order they were executed — each one unblocked the next.

1

BroadcastOnError / BroadcastOnErrorFunc ✓

Symmetric to BroadcastOnSuccess. Fires when err != nil and broadcasts a StructuredError (RFC 7807) event. Closes the largest hole in the real-time story: SSE clients learn when commands fail. Shipped in sse_broadcaster.go + structured_error.go.

2

SSEStream.Heartbeat + OnDisconnect ✓

Heartbeat(ctx, interval) sends : keepalive\n\n comment-frame pings on a ticker, stopping on ctx.Done(). OnDisconnect(fn) registers cleanup callbacks. Reverse proxies and corporate firewalls no longer sever idle SSE connections. Shipped in sse_stream.go.

Done commit a78ba49
3

WSMessage encoder + WSBroadcaster ✓

WriteWSMessage / WriteWSMessageInto[T] symmetric to the parser. WSBroadcaster mirrors the SSE Broadcaster for fan-out, with BroadcastOnSuccessWS / BroadcastOnErrorWS hooks (and *Func variants). Both broadcasters share a generic fanOut[T] core. Shipped in ws_encoder.go + ws_broadcaster.go + fanout.go.

Done commit 193f9a4
4

App.DispatchWSCommand / DispatchWSQuery ✓

Bridges incoming WS frames into the CQRS dispatcher. DispatchWSCommand / DispatchWSQuery are methods on App (not a standalone handler) so they reuse the App's lifecycle hooks, timeout, and error wrapping. Decoders are pluggable via WSCommandDecoder / DecodeWSJSON[T]. Makes WebSocket a first-class transport. Shipped in ws_dispatch.go.

Done commit 024a660
5

StructuredError payload type ✓

RFC 7807-shaped type (Type, Title, Status, Detail, Instance) used uniformly across SSE and WS error responses. NewStructuredError(err, r) derives status from MapError and the request ID for tracing. Clients render and handle errors consistently regardless of transport. Shipped in structured_error.go.

Done commit a78ba49
Outcome

Full transport parity achieved: HTTP, SSE, and WebSocket each carry commands, queries, events, and structured errors with a consistent vocabulary. The three WebSocket cells that remain "missing" (heartbeat, replay, lifecycle) are deliberate architectural boundaries — cqrs-htmx never owns the WS socket, so those concerns live in the consumer's WS library. Proposed Payload Contracts

Concrete shapes for the new APIs. RFC 7807 alignment for errors so client code can be transport-agnostic.

Structured Error Payload

Used by BroadcastOnError, WSError frames, and optionally HTTP error bodies. Shape follows RFC 7807. 

// Transport-agnostic structured error. Serialized as JSON for SSE data / WS payload.
type StructuredError struct {
    Type     string // URI or token: "about:blank", "https://errors/rejection"
    Title    string // Short human-readable summary
    Status   int    // HTTP status code (carries family semantics)
    Detail   string // Specific explanation of this occurrence
    Instance string // Request ID / correlation ID for tracing
}
