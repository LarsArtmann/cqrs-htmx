Executive Summary

cqrs-htmx uses go-cqrs-lite's command dispatch, query dispatch, error taxonomy, branded IDs, and event metadata propagation well — but leaves significant power on the table. The headline gaps are: typed handlers (only in the example, not the library), CQRS middleware (dispatcher Use() never exposed), HTTP request metadata (IP/User-Agent not propagated to events), and Retry-After headers for transient errors.

Methodology

Every .go file in the go-cqrs-lite v2.3.x module cache was read. Every exported symbol was catalogued. Every .go file in cqrs-htmx (root + usermgmt + examples) was scanned for go-cqrs-lite imports and symbol references. The intersection defines "currently used." The difference defines "available but unused." Each unused symbol was then evaluated for whether it makes sense in an HTMX-aware CQRS HTTP integration library.

Step 1 — Inventory

Read all 22 go-cqrs-lite v2 modules. Catalogued ~200+ exported symbols across command, query, event, id, codec, dispatcher, schema, snapshot, decider, memory, middleware, projection, listing, signing, otel, catalog, storage, turso, and pebble.

Step 2 — Usage Trace

Scanned every non-test .go file in cqrs-htmx for go-cqrs-lite imports. Found 4 modules actively imported: command/v2, query/v2, event/v2, id/v2. Traced every symbol reference.

Step 3 — Gap Analysis

For each unused symbol, asked: "Does this belong in an HTTP integration library?" Categorized as: makes sense (gap), correctly excluded (not relevant), or already covered by an equivalent mechanism.

Critical Gaps

These are headline v2.3.0 features that cqrs-htmx should expose but currently doesn't. Low effort, high impact.

1. Typed Handler Registration

CRITICAL Low Effort

Problem: The v2.3.0 headline feature command.RegisterTyped[T] and query.RegisterTyped[Q,R] / query.DispatchTyped[T] are used only in the examples/datastar-demo/ — not exposed by the library itself. Consumers who use App.Command() and App.Query() must do manual type assertions in their handlers.

Current — consumer handler (manual type assertion)
cmdDispatcher.Register("CreateUser", func(ctx context.Context, cmd command.Command) error {
createCmd, ok := cmd.(*CreateUserCmd) // runtime assertion
if !ok {
return fmt.Errorf("unexpected type %T", cmd)
}
return createUser(ctx, createCmd)
})
With RegisterTyped[T] — compile-time safe
command.RegisterTyped(cmdDispatcher, "CreateUser",
func(ctx context.Context, cmd *CreateUserCmd) error {
return createUser(ctx, cmd) // no assertion needed
},
)

Recommendation: The library doesn't need to wrap these — consumers can call command.RegisterTyped directly on the dispatcher they pass to Config.Commands. However, the library should document this pattern prominently in README and provide a convenience example. Optionally, expose App.Commands() and App.Queries() accessors so consumers don't need to hold a separate reference.

2. CQRS Dispatcher Middleware Not Exposed

CRITICAL Low Effort

Problem: Both command.Dispatcher and query.Dispatcher have a Use(middleware ...Middleware) method that chains cross-cutting concerns (retry, tracing, metrics, validation, circuit breaker, recovery). The library never calls it, never exposes it through Config, and never documents it.

The go-cqrs-lite middleware/ package provides 24 factories (8 concerns × 3 message types):

Current workaround is manual

Consumers must call cmdDispatcher.Use(middleware.CommandRetry(cfg)) before passing the dispatcher to cqrshtmx.Config{Commands: cmdDispatcher}. This works but is undocumented and easy to get wrong (middleware must be added before Register).

Recommendation: Add Config.CommandMiddleware []command.Middleware and Config.QueryMiddleware []query.Middleware fields. In New(), call cfg.Commands.Use(cfg.CommandMiddleware...) before returning. This is a 4-line change.

High Priority Gaps

These features would meaningfully improve audit trails, client experience, and error handling completeness.

3. HTTP IP & User-Agent Not Propagated to Events

HIGH Low Effort

Problem: The event package provides event.WithIPAddress(ip) and event.WithUserAgent(ua) options. The library has ClientIP(r) (via httputil) and r.UserAgent() available on every HTTP request. But EventOptionsFromContext only propagates UserID, CorrelationID, RequestID, and Deadline — not IP or User-Agent.

This means audit logs and event metadata lose the client's IP address and browser information — critical for security auditing, fraud detection, and debugging.

Recommendation: Extend EventOptionsFromContext (or the middleware) to also capture IP and User-Agent from the request and store them in context. Then propagate them via event.WithIPAddress and event.WithUserAgent.

Proposed: ContextEnrichmentMiddleware enhancement
func ContextEnrichmentMiddleware(extractor UserIDExtractor) func(http.Handler) http.Handler {
return func(next http.Handler) http.Handler {
// Existing: extract userID, correlationID, requestID
// NEW: also store IP + UserAgent in context
ctx = WithIPAddress(ctx, ParseIPAddress(ClientIP(r)))
ctx = WithUserAgent(ctx, NewUserAgent(r.UserAgent()))
next.ServeHTTP(w, r.WithContext(ctx))
}
}

4. Retry-After Header Missing for Transient Errors

HIGH Low Effort

Problem: The error handler maps event.Transient to HTTP 503 (Service Unavailable), but doesn't set a Retry-After header. The rate limiter sets Retry-After correctly for 429 responses, but transient dispatch errors (database timeouts, connection failures) don't.

The event.IsRetryable(err) function exists and returns true for Transient-family errors — it's never called.

Recommendation: In DefaultErrorHandlerWithRedirect, check event.IsRetryable(err) and set Retry-After: 5 (or configurable) when true. This is a 3-line addition.

5. NewConflict & NewCorruption Not Available

HIGH Trivial

Problem: The library creates errors with only 3 of the 5 families: NewRejection (400), NewInfrastructure (500), NewTransient (503). But the error handler familyStatus() handles all 5 families including Conflict (409) and Corruption (422). Consumers have no way to create these errors through the library — they'd need to import event/v2 directly.

This matters because conflict detection (e.g. optimistic concurrency, duplicate email) should map to 409, not 400. The usermgmt submodule uses event.NewRejection for ErrEmailExists which returns 400 when it should arguably be 409 Conflict.

Recommendation: Either re-export the error helpers, or create domain-specific sentinel errors using NewConflict and NewCorruption where appropriate. Consider using event.NewConflict for duplicate-email and optimistic-concurrency errors.

Medium Priority Gaps

These would improve architectural cleanliness and enable advanced use cases.

6. Event Bus → SSE Bridge Missing

MEDIUM Medium Effort

Problem: The library has a full SSE subsystem (Broadcaster, SSEStream, SSEEventStore, ReplayEvents) and a BroadcastOnSuccess hook that broadcasts SSE events on successful dispatch. But there's no bridge to go-cqrs-lite's event.Bus / event.Publisher / event.Subscriber interfaces.

This means consumers who use event sourcing must manually wire their event.Bus to the SSE Broadcaster. The library is perfectly positioned to provide an adapter.

Recommendation: Provide an EventBusToSSEBridge(broadcaster, bus) adapter that subscribes to the event bus and forwards matching events as SSE events. Also consider App.SetEventBus(bus) to auto-bridge dispatch success → event publish → SSE broadcast.

7. CausationID Not Propagated

MEDIUM Low Effort

Problem: The id.CausationID type and event.WithCausationID option exist for tracking cause-effect chains (command → event). The library propagates CorrelationID but not CausationID.

When a command handler emits events, the events should carry the command's ID as their causation ID. Currently there's no mechanism to set this — the library doesn't propagate a command ID through context.

Recommendation: Optionally propagate CausationID via context when a command is dispatched. The command.PersistedCommand has an ID() method that could serve as the causation source.

8. ContextEnricher Pattern Not Adopted

MEDIUM Low Effort

Problem: EventOptionsFromContext manually builds a []event.Option slice by checking each context value individually. The event package provides ContextEnricher (a function type) and CompositeEnricher (combines multiple enrichers) for this exact purpose — cleaner, more composable, and used by the decider.Repository.

Recommendation: Refactor EventOptionsFromContext to use CompositeEnricher internally, or at minimum align with the enricher pattern so consumers can inject custom enrichers.

9. ClientID (Offline-First) Not Propagated

MEDIUM Low Effort

Problem: The id.ClientID type, event.WithClientID, and event.WithClientOccurredAt options support offline-first scenarios (client device attribution, conflict detection). The library doesn't propagate these from HTTP headers.

Recommendation: Add optional Config.ClientIDHeader to extract a client ID from a custom HTTP header (e.g. X-Client-ID) and propagate it via event.WithClientID. Low priority unless offline-first is a use case.

Low Priority Gaps

Nice-to-haves that improve ergonomics but aren't blocking.

10. DecodePayload[T] Not Exposed

LOW

The event.DecodePayload[T] and event.DecodePayloads[T] functions decode event payloads into typed structs. Could be useful for SSE consumers who receive events and need to deserialize them. Currently not re-exported or documented.

11. Pagination.Validate() Not Exposed

LOW

query.Pagination.Validate() returns an error for out-of-range values. DecodePagination delegates to NewPagination which applies defaults silently — no explicit validation error is returned to the client.

Actionable Recommendations

Ordered by impact-to-effort ratio. Each recommendation is independently shippable.

Quick Wins (Low Effort, High Impact)

R1. Expose Dispatcher Accessors

~10 lines

Add App.Commands() *command.Dispatcher and App.Queries() *query.Dispatcher so consumers can call RegisterTyped and Use() without holding separate references.

func (a *App) Commands() *command.Dispatcher { return a.commands } func (a *App) Queries() *query.Dispatcher { return a.queries }

R2. Add Middleware Config Fields

~5 lines

Add Config.CommandMiddleware []command.Middleware and Config.QueryMiddleware []query.Middleware. In New():

if len(cfg.CommandMiddleware) > 0 { cfg.Commands.Use(cfg.CommandMiddleware...) }

R3. Propagate IP + User-Agent

~15 lines

In ContextEnrichmentMiddleware, also store parsed IP and User-Agent in context. In EventOptionsFromContext, append event.WithIPAddress(ip) and event.WithUserAgent(ua).

R4. Retry-After for Transient Errors

~5 lines

In DefaultErrorHandlerWithRedirect:

if event.IsRetryable(err) { w.Header().Set("Retry-After", "5") }

Medium-Term Improvements

R5. Document Typed Handler Pattern

Docs only

Add a README section showing consumers how to use command.RegisterTyped[T] and query.RegisterTyped[Q,R] / query.DispatchTyped[T] with the library. The datastar-demo example already demonstrates this — surface it.

R6. Document CQRS Middleware Usage

Docs only

Add a README section showing how to use go-cqrs-lite's middleware/ package (Retry, Tracing, Metrics, Circuit Breaker) with the library's dispatcher. Show the Use() call before New(cfg).

R7. Use NewConflict for Duplicate Errors

~3 lines

In usermgmt/errors.go, change ErrEmailExists and ErrUserIDExists from event.NewRejection to event.NewConflict. This maps them to HTTP 409 Conflict instead of 400 Bad Request.

R8. Event Bus → SSE Bridge

~50 lines

Provide an adapter that subscribes to event.Bus and forwards events to Broadcaster.Broadcast(). This auto-bridges domain events to SSE without manual BroadcastOnSuccess calls.

Bottom Line

cqrs-htmx is a solid HTMX integration layer with excellent error mapping, strong typing, and correct architectural boundaries. The core dispatch flow is well-designed. However, it underutilizes go-cqrs-lite's typed handler generics, middleware system, and HTTP→event metadata bridging. Closing these gaps requires ~50 lines of code and some documentation — the ROI is exceptionally high.
