Executive Summary

cqrs-htmx is a library, not an application. Its performance profile is defined by per-request allocation overhead, middleware layering cost, and the intentional cryptographic CPU tax of bcrypt. The library is lean, zero-lint, and well-tested. The main opportunities lie in reducing allocations on the form-decode and logging hot paths, and in preventing unbounded memory growth in the in-memory stores.

bcrypt — The Intentional CPU Tax

Production cost = 12 (default)

Intentional

At bcrypt cost 12, each GenerateFromPassword or CompareHashAndPassword takes approximately 200–300ms of pure CPU on a modern processor. This is by design — it makes brute-force attacks economically infeasible.

Throughput implications:
  • Register: ~4 registrations/sec/core (1 hash)
  • Login: ~4 logins/sec/core (1 compare)
  • ChangePassword: ~2/sec/core (compare + hash = ~500ms)

Authorization — Casbin Policy Evaluation

Enforce() on every authorized request

Scales with policy count

The Enforcer.Enforce(sub, res, act) call at authz.go:49 evaluates a PERM matcher against all matching policies. With the RBAC model (authz_types.go:47–61), each evaluation traverses the role graph:

// Casbin matcher: m = g(r.sub, p.sub, r.dom) && r.obj == p.obj && r.act == p.act // g() triggers role-graph traversal per evaluation
Complexity: O(policies × role-hierarchy-depth) per request. Each registered user adds one group policy (service_register.go:93), so evaluation cost grows with the user base. Casbin v3's internal watchers may rebuild indexes on policy mutation, adding spike latency.

Memory / RAM

Memory characteristics: per-request allocations (GC'd), persistent in-memory data structures (unbounded), SSE channel buffers, and rate-limiter entry overhead. The in-memory stores are explicitly documented as non-production, but their growth characteristics matter for development, testing, and any consumer that uses them.

SSE Broadcaster Memory Footprint

Channel buffer: 64 events

Each subscriber gets a buffered channel of capacity 64. At ~24 bytes per SSEEvent (2 strings + int), that's ~1.5KB per subscriber reserved upfront.

Subscriber leak risk

If a handler forgets defer broadcaster.Unsubscribe(ch), the channel and map entry leak permanently. The 64-cap buffer means up to 1.5KB × N leaked subscribers.

Slow consumer drops

Broadcast uses non-blocking select/default. A slow consumer with a full buffer silently drops events — no backpressure, no metric. Memory stays bounded.

User.Clone() — Defensive Copy Cost

Every FindByID and FindByEmail in InMemoryUserStore returns u.Clone() (store.go:56,67,83,99). This allocates a new User struct + a new Roles slice on every read. This prevents aliasing bugs but means every user lookup costs 2 allocations regardless of cache hit.

Tradeoff: Correctness (no shared mutable state) vs. allocation cost. The right call for a library — consumers using SQL stores won't have this pattern.

Network

Wire-level characteristics: payload sizes, caching, streaming protocols, compression, and header overhead. The library is network-efficient — embedded assets are cached aggressively, SSE/WebSocket are lightweight, and body sizes are bounded.

Embedded Assets

HTMX v2.0.9 — 82KB

Cached
  • Embedded via go:embed — served from binary, zero disk reads
  • ETag support — 304 Not Modified on If-None-Match match
  • Cache-Control: max-age=31536000, immutable (1 year)
  • Content-Type set correctly (application/javascript)
  • GET/HEAD only — 405 for other methods
  • Consumers choose the mount path — not auto-wired

Body Size Limits

Bounded
  • Default max body: 10 MB (DefaultMaxBodySize)
  • Per-handler override via WithMaxBodySize
  • Enforced via io.LimitReader(r.Body, maxBodySize+1)
  • Oversized bodies → ErrRequestTooLarge → 413
  • Max password: 128 chars — prevents bcrypt CPU abuse

The Broadcast() method holds an RLock for the entire fan-out loop. At 1,000+ subscribers, this becomes a serialization point — all broadcasts queue behind the lock. Zero allocations throughout (excellent), but latency scales super-linearly per subscriber.

WebSocket Helpers

Protocol helpers only — no WebSocket library dependency. Consumers choose their own WS implementation. The helpers parse HTMX's JSON message format:

  • ParseWSMessage — unmarshals to map[string]any, separates HEADERS
  • ParseWSMessageInto[T] — generic typed parser, re-marshals body after extracting HEADERS (1 redundant marshal)
  • WSOOBHTML — wraps HTML with hx-swap-oob attributes
Note: ParseWSMessageInto does a marshal→unmarshal round-trip on the body (ws.go:168–173) — same pattern as the form decoder. 1 redundant JSON serialization per WS message.

HTTP/2 Support

StatusRecorder (logging.go:122) implements http.Pusher and http.Flusher and http.Hijacker by delegating to the underlying ResponseWriter. This means:

  • HTTP/2 Server Push works through the logging middleware
  • Flushing works (required for SSE through the middleware chain)
  • Hijacking works (required for WebSocket upgrade)

Disk / I/O

The library performs zero disk I/O on any runtime path. All assets are embedded at compile time. The only kernel-level I/O is crypto/rand for cryptographic token generation, which reads from /dev/urandom (getrandom syscall).

go:embed

Zero runtime reads

HTMX JS (htmx.min.js, 82KB) is embedded into the binary at compile time via //go:embed in htmx_embed.go. Served from memory — no file system access.

No file logging

stdout/slog only

All logging goes through log/slog (stdout/stderr). No log file rotation, no disk writes. Consumers configure their own log sinks.

crypto/rand

Kernel syscall

Session tokens (user.go:191) and CSRF tokens (nosurf) use crypto/rand.Read — reads from kernel entropy (getrandom(2)), not a file descriptor. ~32 bytes per session/token.

Not applicable. cqrs-htmx is a backend HTTP integration library with no graphics, compute shaders, video encoding, or any GPU-addressable workload.

Not applicable

Previously Fixed Race Condition

Fixed 2026-06-14: perKeyLimiter.limiter() read entry.lastUsed after releasing the RLock (ratelimit_middleware.go). This caused a data race under concurrent load (~20% race-detector failure rate). The fix reads lastUsed while still holding the RLock, since the field is written under the write lock during refresh. See AGENTS.md gotcha #16.

Goroutine Safety

Safe patterns

  • All exported types are safe for concurrent use
  • Stores use RWMutex with Clone() on read (no aliasing)
  • Broadcaster: Subscribe/Unsubscribe/Broadcast all thread-safe
  • Rate limiter: RLock fast-path, write-lock upgrade on miss
  • App/handlerConfig: immutable after construction (Command/Query return http.HandlerFunc)

Risks

  • SSE handler goroutine leak — if handler doesn't defer Unsubscribe, goroutine + channel leak
  • SSE handler goroutine — each SSE connection holds a goroutine for the connection lifetime
  • Broadcast blocks briefly — RLock held during fan-out; concurrent Subscribe waits
  • No context timeout on SSE Send — a stuck client blocks the write until TCP timeout

Security-Relevant Performance

Where security mechanisms impact performance. Most of these are intentional tradeoffs (bcrypt CPU cost, crypto/rand syscalls), but one — per-request WARN logging on unconfigured CSRF proxies — is an unintended hot-path I/O cost.

Critical CSRF WARN log on every request when TrustedProxies unset

csrf_middleware.go:130–140 — When CSRFConfig.TrustedProxies and TrustedProxiesCIDR are both empty (the default), every non-loopback HTTP request triggers a slog.Warn call. The benchmark output showed this warning spammed hundreds of thousands of times during the CSRF benchmark run.

Impact: Per-request synchronous log I/O on the CSRF hot path. In a real deployment behind a reverse proxy over plain HTTP, this means every request writes a warning line to stderr/stdout. At 10K req/s, that's 10K log lines/sec of identical warnings.
Fix: Log once at middleware construction time (already done for Secure=false), not per-request. Or use sync.Once.
High Per-handler CSRF creates new nosurf.New + ResponseRecorder per request

csrf_handler.go:43–50 — The CSRFProtect(cfg) per-handler option creates a new nosurf.New() handler instance AND a new httptest.ResponseRecorder on every single request. This is significantly more expensive than the global CSRFMiddleware which creates the handler once.

Impact: Allocates a full ResponseRecorder + nosurf internal state per request. The global middleware path should be preferred. The per-handler path exists for selective CSRF on specific routes only.

Intentional Security Costs (No Action Needed)

bcrypt cost 12

Intentional

~250ms CPU per hash/verify. Prevents brute-force. Max password 128 chars prevents CPU abuse. Configurable cost via Service.bcryptCost.

crypto/rand tokens

Intentional

Session tokens (32 bytes) and CSRF tokens use crypto/rand. Kernel syscall, not a performance concern. ~1µs per generation.

CSRF token masking

Intentional

nosurf masks tokens per-request (XOR) to mitigate BREACH attacks. Cheap (nanoseconds), but allocates a new masked token string per GET.

Redirect URL sanitization

Intentional

sanitizeRedirectURL (response.go:252) validates redirects are relative paths only. Zero allocations via inline pathEscapesRoot (no strings.Split).

Findings — Prioritized

All performance findings, sorted by severity. Each includes the location, impact, and a recommended action. Severity reflects impact on production performance, not code quality.

Critical

Critical CSRF WARN log fires on every request (unconfigured TrustedProxies) csrf_middleware.go:130–140

When TrustedProxies and TrustedProxiesCIDR are both empty (the default), isTrustedProxy() logs a slog.Warn for every non-loopback request. The CSRF benchmark spammed this warning hundreds of thousands of times.

Fix: Move the warning to middleware construction time (like the Secure=false warning) or gate it with sync.Once. Effort: Trivial.
Critical Unbounded memory: 4 data structures grow forever store.go · lockout.go · authz_types.go · sse_broadcaster.go

InMemoryUserStore, InMemorySessionStore, AccountLockout, and Casbin policies all grow monotonically. Only SessionStore and Lockout have manual eviction methods. A long-running dev/test process will OOM.

Fix: Document the growth clearly (done in godoc), add a background goroutine example for periodic EvictExpired()/EvictStale(), or add TTL-based auto-eviction. The rate limiter already does this correctly.

High

High Form decode marshal→unmarshal round-trip — top allocation hot path decoder.go:118–132

decodeFormValues converts form data to map[string]any, marshals to JSON, then unmarshals into the target struct. This is 2+ allocations per form POST.

Fix: Use a reflect-based form decoder (or a schema library) to go directly from url.Values to the struct. Tradeoff: behavioral compatibility with the JSON round-trip (arrays, nested objects).
High Per-handler CSRF creates nosurf.New + ResponseRecorder per request csrf_handler.go:43–50

The CSRFProtect(cfg) HandlerOption creates a new nosurf handler instance and a new httptest.ResponseRecorder on every request. Far more expensive than the global middleware.

Fix: Cache the nosurf handler per config (already noted as a design goal). Or document that the global middleware should be preferred.
High Double JSON decode in auth endpoints http.go:148 → 104/123

Auth handlers decode the body into json.RawMessage first, then unmarshal again into the typed request. The first decode is redundant.

Fix: Decode directly into the typed struct with json.NewDecoder(io.LimitReader(...)).Decode(&req). Effort: Low.
High Broadcaster holds RLock during entire fan-out loop sse_broadcaster.go:72–81

At 1,000+ subscribers, Broadcast() holds the RLock for ~208µs, blocking all concurrent Subscribe/Unsubscribe calls. Per-subscriber cost inflates 6× from 1 to 1,000 subscribers.

Fix: Snapshot the subscriber slice under RLock, then release the lock before iterating. This allows concurrent subscribe/unsubscribe during broadcast.

Medium

Medium JSONLogFormatter allocates map + json.Marshal per log line logging.go:69–87

Each JSON log line creates a map[string]any, calls contextFields() (another map), and json.Marshal. ~33 allocs per logged request.

Fix: Use json.Encoder with a pooled buffer, or build the JSON string manually with strings.Builder.
Medium HealthHandler allocates []byte literal per request app.go:304,310

[]byte(`{"status":"ok"}`) is allocated on every health check. Easily avoidable.

Fix: Pre-allocate as a package-level var. Effort: Trivial.
Medium setTriggerWithDetail allocates map + json.Marshal per notification response.go:318

Every HTMX notification creates a map[string]any and marshals it to JSON for the HX-Trigger header.

Fix: Pool the map, or use strings.Builder for simple name:value pairs.
Medium ParseWSMessageInto re-marshals body after HEADERS extraction ws.go:168–173

After extracting HEADERS from the raw map, the remaining fields are re-marshaled to JSON then unmarshaled into the target struct. 1 redundant serialization per WS message.

Fix: Use a two-pass decode or a custom unmarshaler that skips the HEADERS key.
Medium CSRF middleware is the most expensive middleware (~6.5µs overhead) csrf_middleware.go

CSRF GET: ~6,506 ns / ~27 allocs overhead. POST: ~5,433 ns / ~30 allocs. Dominated by nosurf token generation (crypto/rand), cookie handling, and context value storage.

Fix: Most cost is in nosurf (crypto/rand + masking) — unavoidable. The context value and cookie allocations could be reduced but the crypto dominates.

Low

Low contextFields() allocates a map only used by RequestLoggingSlog logging.go:27–39

After inlining context lookups in DefaultLogFormatter, contextFields() is only used by RequestLoggingSlog. It allocates a map[string]string per request.

Limitations & Caveats

  • httptest dominates: httptest.NewRequest + NewRecorder contributes ~5.1KB / 11 allocs / 1.2µs per benchmark iteration. All "overhead" figures in this report are baseline-subtracted, but the raw tables include this noise.
  • ns/op variance: The AMD RYZEN AI MAX+ 395 has aggressive turbo boost and thermal throttling. allocs/op is stable and reliable; ns/op varies ±15%.
  • No real network: Benchmarks use in-process httptest, not real TCP connections. Real-world latency includes kernel network stack overhead.
  • bcrypt test cost: usermgmt benchmarks use bcrypt cost 4 (not 12). Production cost is ~375× higher. Throughput estimates account for this.
  • Single-machine: No distributed benchmarks. The library's stateful components (stores, broadcaster) are single-process only.
  • No load testing: No sustained-load or soak testing was performed. Memory growth under long-running load is inferred from code analysis, not measured.
