00Summary

cqrs-htmx is a library, so the correct measure of OTel adoption is not “does the library import OpenTelemetry” (it deliberately does not — zero imports in library code, ROADMAP.md:221) but “how trivially can a consumer adopt full tracing and metrics.” On that measure the foundation is strong: every version is current, the canonical guide documents three integration paths, and one complete, tested demo exists. What holds the score down is discoverability, not architecture: the upstream decider and storage layers already emit OTel spans for the entire identity domain the moment a global provider is registered — and no cqrs-htmx document says so. Meanwhile docs/observability-wiring.md (last touched 2026-06-29) references dead v3 module paths and makes a false claim about hooks that the newer guide explicitly contradicts.

The bottom line You are one cqrsotel.Setup() call away from end-to-end traces of every command, event, and SQL store operation — the instrumentation is already wired upstream and no-ops until a provider exists. The work is not wiring more code; it is (1) killing the stale contradictory doc, (2) documenting the free spans, and (3) adding the missing HTTP root-span and correlation recipes so traces start at the request instead of the decider.

◆What’s already in place

The audit found deliberate, well-reasoned decisions — not neglect. These five form the baseline every recommendation below builds on.

Dependency-free seam design (the library principle, done right) Zero go.opentelemetry.io imports in library code. The re-export temptation was evaluated and rejected with a dependency-budget rationale (ROADMAP.md:221). example_otel_test.go proves hook-based spans with zero OTel deps.

Perfect version currency otel SDK v1.46.0 in every go.sum = latest stable (released 2026-08-25). go-cqrs-lite/otel/v4 v4.4.0 and prometheus/v4 v4.3.0 are the newest published tags (verified via git tag --sort=-v:refname on the sibling). Nothing to upgrade.
+
Canonical adoption guide with an honest recommendation docs/guides/leveraging-go-cqrs-lite.md §2 maps three paths — (a) dep-free hooks, (b) middleware.CommandTracing/QueryTracing with cqrsotel.NewTracer, (c) prometheus.Setup() for /metrics — and correctly warns that hooks cannot name a span by command type. The decision summary rates OTel adoption “Low effort, High impact (prod readiness).”

Runnable, tested proof examples/observability-demo/main.go:85-121 wires the full stack: cqrsotel.Setup(WithStdoutExporter), recovery → retry → tracing → typed metrics → logging middleware ordering, cqrsprom.Setup(cqrsotel.NewCQRSViews()...), the subtle global-meter-provider bridge (Prometheus owns the reader), and a /metrics endpoint. main_test.go asserts cqrs_operation metrics actually appear.

01Capability Assessment

Feature-by-feature, ordered by impact. Status classes: red = missed opportunity, yellow = partially used, green = fully leveraged.

Missed Opportunity · High impact

The identity domain already emits OTel spans for free — and no document says so

go-cqrs-lite decider/otel.go + decider/decider.go:122 + decider/load.go:118,165 + storage/command_store_save.go:26,61 · 0 mentions in cqrs-htmx docs

go-cqrs-lite’s decider and storage layers create spans through cqrsotel.NewTracer("decider"), which resolves the global tracer provider (sync.Once-cached) and no-ops until one is registered. cqrsotel.Setup() registers globally by default. That means a consumer who makes one Setup call gets decider.execute, decider.load, event.store.save, and event.store.load spans — with aggregate type/id/version attributes — around every RegisterUser, CreateTenant, and SQL journal write across all 4 cqrs-htmx aggregates, with zero middleware. This is the highest-value capability in the entire integration and it is invisible: no guide, no demo callout, no README mention. 

// The entire unlock, verbatim from examples/observability-demo:
provider, err := cqrsotel.Setup(
    cqrsotel.WithService("my-app", "1.0.0", "i-1"),
    cqrsotel.WithSpanExporter(otlpExporter), // prod: OTLP)
// ^ from this line on, every usermgmt command/event/store
//   operation is traced (decider.* + event.store.* spans).
Recommendation Add a “free domain spans” subsection to leveraging-go-cqrs-lite.md §2 and a comment in observability-demo where Setup is called. Consumers on usermgmt.NewService / setup.New get domain tracing without touching a single dispatcher.
Docs Split-Brain · High impact

docs/observability-wiring.md is stale: dead v3 imports and a false claim the canonical guide contradicts

docs/observability-wiring.md (last touched 2026-06-29, commit c91bc387) vs docs/guides/leveraging-go-cqrs-lite.md §1

Three defects: (1) it claims hooks “run inside the dispatch path, so they see the actual command/query type” — false: dispatchContext (handler.go:11-32) invokes beforeDispatch(ctx, r) before decode, so hooks only ever see the HTTP request; the newer guide §1 states exactly this. (2) It teaches the coarse path only (spans named cqrs.dispatch) and never mentions middleware.CommandTracing, NewOTelBundle, prometheus.Setup, or the correlation enricher. (3) It predates the v4 module split and points consumers at otel/v3, middleware/v3, prometheus/v3 — paths that no longer match the published module set. Anyone (human or LLM) landing on the older doc first builds worse instrumentation than the library already enables.

Recommendation Banner the old doc as superseded with a pointer to leveraging-go-cqrs-lite.md §2, or fold its hook-level recipe into §2 path (a) and delete the rest. Applied in this change: a superseded-banner + fact fix at the top of the file.
Missed Opportunity · High impact

No HTTP root-span story — every consumer trace starts at the decider, not the request

not used anywhere · otelhttp appears only as // indirect in go.sum files · guide §2 has no HTTP recipe

Without a request-level span, a trace contains decider.execute with no URL, method, HTTP status, or total latency — and no W3C traceparent extraction, so incoming distributed context is silently dropped. The plumbing is already correct for the fix: the dispatch pipeline uses r.Context() (handler.go:14), so a span opened around the mux nests every decider/storage span under it automatically, and cqrsotel.TextMapPropagator() is registered by Setup. otelhttp (v0.71.0, already in the module graph transitively) is one wrapper away. 

// One line in front of the mux — root spans + traceparent extraction:
handler := otelhttp.NewHandler(mux, "my-app")
// decider.* spans now nest under POST /commands/RegisterUser
// with http.method / http.route / total duration on the root.
Recommendation Add the HTTP root-span recipe (otelhttp + propagator note) to guide §2 and wire it in observability-demo so the demo produces complete traces, not decider-only fragments.
Missed Opportunity · Medium-high impact

Trace correlation never bridges into event metadata — the upstream enricher exists, unwired and unmentioned

context.go:236-269 (domain CorrelationID only) · go-cqrs-lite middleware/enricher.go (OTelCorrelationEnricher) + otel/propagation.go (baggage) · 0 references in cqrs-htmx

cqrs-htmx propagates a domain CorrelationID (branded ULID, event.WithCorrelationID) into metadata, but nothing reads OTel baggage, so a W3C-baggage correlation ID from an upstream service never reaches the event store. Upstream ships the exact bridge: middleware.OTelCorrelationEnricher stamps baggage into otel.correlation_id custom metadata on every event, complementing the domain ULID. The cqrs-htmx side is ready for it (decider enrichers compose via event.CompositeEnricher; the event bus accepts handler middleware via config) — only the recipe is missing. Until it exists, cross-service traces cannot be joined to the audit trail. 

// In repository construction (alongside the state cache):
decider.WithEnricher[UserState](event.CompositeEnricher(
    event.CommandCausalityEnricher,
    middleware.OTelCorrelationEnricher, // baggage → metadata
))
Recommendation Document the two-mechanism correlation model (domain ULID + OTel baggage) in guide §2 with this snippet, so consumers can join traces to the event journal.
Partially Used · Medium impact

The one-call composition root can’t wire observability; ServiceConfig lacks fields EventSourcedConfig has

setup/config.go (no OTel/metrics option) · usermgmt/es_setup.go:44,52 vs service_core.go:75 · applyBusMiddleware called only from NewEventSourcedSetup (es_setup.go:224)

EventSourcedConfig exposes PublishMiddleware and HandlerMiddleware — the exact hooks where bundle.Event() / bundle.Publish() OTel middleware belong. ServiceConfig exposes neither, and setup.New (the recommended onboarding path) offers no observability config at all. Consumers face an all-or-nothing choice: adopt setup.New and forgo event-bus tracing/metrics, or hand-assemble the full stack to get them. The asymmetry also means two config paths with the same name-shaped fields behave differently — a silent API inconsistency.

Recommendation Add PublishMiddleware/HandlerMiddleware to ServiceConfig (routing both constructors through the existing applyBusMiddleware), then consider a setup.Config option that accepts an *middleware.OTelBundle so one call wires tracing into the identity domain.

Partially Used · Low impact

SSE fan-out — the live-UI push path — is a blind spot

root Broadcaster (go-sse hub embedding: Health/OnSubscribe/ OnUnsubscribe) · no spans/metrics emitted on Broadcast

Server-Timing covers request/response latency, but the SSE push path that drives adminui and dashboardui live updates emits nothing: no client-count, no fan-out duration, no replay size. The upstream otel module defines the pattern for go-cqrs-lite’s own transport (sse.fanout span with cqrs.sse.client_count), which does not apply directly since cqrs-htmx embeds go-sse directly — but the existing OnSubscribe/OnUnsubscribe hooks make a periodic gauge trivial to expose, and Health() already exists as a data source.

Recommendation Nice-to-have: document a consumer recipe that records connected clients + broadcast duration from the existing hooks; no library change strictly required.
Fully Leveraged · Keep as is

Dispatch-level tracing + metrics, provider setup, and the Prometheus bridge are done right

examples/observability-demo/main.go:85-121 · guide §2 paths (b)+(c)

The canonical integration is complete and correct against the upstream README: single Setup with resource attributes and shutdown-flush semantics; middleware in the recommended order (tracing wraps metrics); typed metrics keyed by real command type; NewCQRSViews for histogram bucket hygiene; and the documented subtlety that Prometheus must own the global meter provider because cqrsotel.Setup registers a reader-less one. Nothing to improve at this layer — these four capabilities are the score’s foundation.

04Conclusion

For a library, this is a healthy OTel posture held back almost entirely by discoverability. The architecture (zero enforced deps), the versions (all latest), the canonical guide, and one tested demo are exactly right; nothing is misused and nothing needs upgrading. The score moves from 64 toward 90 by finishing the story the code already tells: document the free domain spans, add the HTTP root span and correlation recipes, and give setup.New the option that makes one-call onboarding include observability. The stale wiring doc should not survive another release train — it is the only artifact in the repo that teaches something false.
