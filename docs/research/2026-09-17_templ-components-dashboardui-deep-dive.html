templ-components in dashboardui — Adoption & Utilization Audit

dashboardui imports exactly one of templ-components' five modules and calls exactly one of its 110+ components: icons.IconPathData. Everything else the library offers for a dashboard — StatCard, Badge, EmptyState, Table, Toast, error pages — is hand-rolled in ~800 lines of strings.Builder HTML, CSS, and JS. This audit maps the gap, verifies what actually blocks adoption, and ranks the fixes.

00Summary

The verdict on "is dashboardui using templ-components to the max?" is a clear no — but not for the reasons the codebase believes. Both the module's own migration evaluation (docs/planning/templ-migration-evaluation.md) and its ROADMAP frame adoption as an all-or-nothing templ migration of ~2,800–5,500 lines. That framing is wrong in a load-bearing way: a templ component is just an interface with Render(ctx, io.Writer), and strings.Builder is an io.Writer. Every leaf component can be dropped into the existing render functions one at a time, with tests untouched.

The real gate is different: templ-components emits Tailwind v4 utility classes, ships no compiled CSS, and dashboardui has no Tailwind pipeline. That gate is also already solved in this repo — adminui runs the exact BuildFlow tailwind-build step this audit recommends.

The bottom line dashboardui duplicates ~15 library components (~800 lines of hand-rolled HTML/CSS/JS) behind a false "needs a full templ migration" assumption. The actual blocker is a 5-minute Tailwind v4 setup that adminui already runs. Version currency is perfect (v1.17.0 = latest); icons usage is exemplary; component adoption is near zero.

◆What's already excellent

+
Perfect version currency dashboardui/go.mod pins templ-components/icons v1.17.0 — the family's latest release (2026-09-13), same as adminui. Zero version gap; nothing to upgrade first.
+
The one adoption is the right one, done right layout.go:138–182 uses icons.IconPathData() with typed icons.Name constants and leans on the library's built-in unknown-name fallback (Question icon). For a non-templ architecture, IconPathData is exactly the intended primitive — pulling raw path data instead of forcing a Tailwind-dependent wrapper.
+
CSP discipline that adoption can build on All JS lives in the external, ETag-cached dashboardJS const; zero inline scripts. The library's interactive components (ToastContainer, CopyButton) emit nonce-guarded inline scripts, and dashboardui's middleware already produces per-request nonces via cqrshtmx.RecommendedSecurityMiddleware() — the same setup adminui uses for its toast host.

01Findings

Ordered by impact. Every claim was verified against library source (templ-components v1.17.0) and dashboardui code on 2026-09-17.

Root cause · False planning assumption

The "requires a full templ migration" belief is false — components render into your existing strings.Builder

docs/planning/templ-migration-evaluation.md · ROADMAP.md · verified: a-h/templ v0.3.1020 Component interface

Both planning documents gate all adoption behind "convert ~2,800–5,500 lines / every handler to .templ files". But the entire component catalog is consumable through one method: templ.Component.Render(ctx context.Context, w io.Writer) error. dashboardui's render functions already write into strings.Builder, which satisfies io.Writer. Adoption can proceed leaf-first, one component per change, with the existing string-contains tests passing at every step. The full templ conversion remains optional and independent. 

// Before (handler_overview.go:148): hand-rolled duplicate
func statCard(b *strings.Builder, value, label, variant string) { ... }

// After: same call site, same builder — library component, no .templ file
func statCard(ctx context.Context, b *strings.Builder, value, label string) {
    props := display.DefaultStatCardProps()
    props.Value, props.Label = value, label
    props.ValueID = "stat-processed" // stable hook for live HTMX updates
    _ = display.StatCard(props).Render(ctx, &b) // Builder is an io.Writer
}
Recommendation Rewrite the migration evaluation around the hybrid path: "leaf components via Render(ctx, &b), full templ conversion optional." Every finding below becomes an independent, low-risk change.
Blocking gate · Solved in-repo

Tailwind v4 pipeline is the real adoption gate — and adminui already runs it

dashboardui/layout.go:215–453 (dashboardCSS) · verified: templates/styles.css has 0 hits for bg-blue-600 (docs demo artifact, not a shippable build)

Every templ-components component emits Tailwind utilities (e.g. EmptyState's action class: bg-blue-600 rounded-md dark:bg-blue-500 motion-reduce:transition-none). The library ships no compiled CSS; consumers run the Tailwind v4 CLI with @source scanning, per docs/tailwind-v4-adoption-guide.md ("Manual setup (5 minutes)", BuildFlow provider option A). dashboardui's hand-rolled token system maps 1:1: --accent, --ok, --warn, --err become @theme overrides of --color-tc-primary/success/warning/danger. adminui already generates its stylesheet via the BuildFlow tailwind-build DAG step — the pattern, config, and CI guard exist in this repo. 

/* dashboardui/app.css — entry point (templates/app.css pattern) */
@import "tailwindcss";
@source "../vendor/github.com/larsartmann/templ-components"; /* or module cache */
@custom-variant dark (&:where(.dark, .dark *));
@theme {
  --color-tc-primary: #4f46e5;   /* was --accent */
  --color-tc-success: #16a34a;   /* was --ok */
  --color-tc-warning: #d97706;   /* was --warn */
  --color-tc-danger:  #dc2626;   /* was --err */
}
/* build: tailwindcss -i app.css -o styles.css --minify */
Recommendation Add the Tailwind v4 entry point + BuildFlow tailwind-build step for dashboardui, mirroring adminui (whose generated, minified adminui/styles.css is already the canonical committed artifact). This single change unblocks findings F3–F12.
Missed Opportunity · High impact

StatCard hand-rolled — missing the exact features a live dashboard needs

handler_overview.go:148–158 (statCard) · handlers_projections.go:197–202 · dashboardCSS .stat-card block (~8 rules)

The hand-rolled version renders value + label + a border-color variant string. The library's StatCardProps adds Trend (Up/Down/Warn), Tone (colored icon tiles), Icon, Href (clickable card), HxGet/HxTarget/HxSwap (self-refreshing), and ValueID — a stable element ID designed for live dashboards. dashboardui's overview is precisely that: SSE events trigger JS that re-renders projection tables, yet stat values have no stable hooks, so updates require full panel swaps. 

props := display.DefaultStatCardProps()
props.Value, props.Label = strconv.FormatInt(proj.Processed, 10), "Processed"
props.ValueID = "stat-processed-" + proj.Name
props.Tone, props.Icon = display.StatToneBlue, icons.ArrowPath
// Overview page: <div class="stat-grid"> loop becomes Grid + StatCards
Recommendation Replace statCard() with display.StatCard via the hybrid path; give each value a ValueID so SSE handlers can target values declaratively instead of string-building rows in JS.
Missed Opportunity · High impact

StatusBadge: the same 4-way switch is duplicated in two renderers; the library maps statuses automatically

handler_overview.go:125–135 · handlers_projections.go:183–192 · dashboardCSS .badge-ok/-warn/-err/-neutral

Both renderProjectionRow and renderProjectionDetail hand-code an identical statusKind → badgeClass switch plus raw <span class="..."> markup. The library's display.StatusBadge(status string) maps ~20 status strings (active/pending/error/failed/…) to badge type + status dot automatically, with 6 BadgeTypes, 3 sizes, and pill styling in BadgeProps if custom mapping is wanted.

Recommendation Map dashboardui's statusGood/Warn/Bad once to BadgeType values (a 3-line helper) and render display.Badge everywhere; delete the four .badge-* CSS rules.
Missed Opportunity · High impact

Errors are plain-text http.Error — the library has a family-aware error page system that matches cqrs-htmx's error model exactly

render.go:44–56 (renderError) · also: DLQ detail pages rendering raw errors in <pre> blocks

renderError emits http.Error plain text: no HTML shell, no navigation, no way back, nothing family-specific. The errorpage module's Family enum — Rejection/Conflict/Transient/Corruption/Infrastructure — is the identical set cqrs-htmx maps to HTTP statuses (400/409/503/500/503), so errorpage.FromError(err) and errorpage.ErrorHandler(err, cfg) slot into the existing error-family pipeline with zero translation. It ships WayOut links, cause-chain extraction, timestamps, JSON mode, and a 404 page (WriteNotFound404 with search + link actions). 

cfg := errorpage.ErrorHandlerConfig{
    Nonce: httputil.NonceFromRequest(r),
    HTMLShell: shellFromLayout, // reuse renderLayout's head
}
// handler error path:
errorpage.WriteError(w, err, cfg) // styled, family-aware, navigable
// Dead-letter detail: errorpage.ErrorDetailProps renders the failed
// event's error with family tone + fix guidance instead of bare <pre>.
Recommendation Route renderError through errorpage, add a 404 page for unknown streams/projections, and render DLQ errors with ErrorAlert/ErrorDetail.
Missed Opportunity · High impact

Ten+ hand-built tables with no sorting; the library ships typed, sortable, lazy tables

handlers_events.go, handlers_audit.go, handlers_projections.go, handler_overview.go:199–218, handlers_dlq.go, handlers_aggregates.go, handlers_timetravel.go · dashboardCSS .data-table block

Every list view repeats the same <table class="data-table"> string with hand-managed esc() calls and a hand-rolled sticky-header rule. display.TableProps covers all of it declaratively: TypedHeaders with Sortable + SortDirection (emits aria-sort), Striped/Hover, LazyRows (content-visibility for long event lists), clickable TableRow.Href, Flush for tables inside cards, and a custom Body templ.Component escape hatch. display.DataTable adds URL-driven column sorting — a real UX upgrade for events/commands/queries listings.

Recommendation Convert the highest-traffic tables first (events, audit commands/queries) to display.Table with sortable headers; delete the .data-table CSS block once all ten are migrated.
Partially Used · Medium-high impact

Three hand-rolled JS behaviors (toast, copy, confirm) that the library ships CSP-safe — plus two a11y anti-patterns

layout.go:131–133 + dashboardJS:644–660 (toast) · dashboardJS:558–568 + handler_overview.go:176–186 (copyable) · dashboardJS:620–625 (data-confirm)

Toasts: dashboardui's 15-line JS renderer + .toast-* CSS duplicate feedback.ToastContainer(nonce); adminui already bridges Hx-Trigger to the library's tcShowToast with a thin wrapper that can be ported as-is. Copy: data-copyable turns divs into click targets — no keyboard access, no button semantics, an emoji pseudo-element as the only affordance (.copyable:hover::after 📋). display.CopyButtonProps gives a real <button> with role="status" feedback and a CSP-safe singleton script. Confirm: the generic data-confirm delegation is fine for forms, but htmx.ConfirmDelete covers destructive buttons with typed props. All of these need one plumbing change: thread httputil.NonceFromRequest(r) through pageData into BaseProps.Nonce.

Recommendation Port adminui's toastHost(nonce) wrapper; swap metaRowCopyable/payload copy for display.CopyButton; add a nonce field to pageData.
Missed Opportunity · Medium impact

HTMX failures are silent — GlobalErrorHandling exists for exactly this

dashboardJS (SSE reconnect handled; HTMX swap errors unhandled anywhere)

The SSE loop shows "Reconnecting", but if a boosted HTMX request fails (network blip, 5xx, expired session), the swap just doesn't happen and the user watches a stale dashboard — the worst failure mode for an observability tool. htmx.GlobalErrorHandling(ErrorHandlingConfig{Nonce, MaxErrorHistory, MaxRetries, RetryDelayMS}) adds exponential retry, error history, 401 auto-reload, family-aware JSON error parsing into tcShowToast, and an aria-live announcer.

Recommendation Mount htmx.GlobalErrorHandling in the layout once ToastContainer is in place (they're designed as a pair).
Missed Opportunity · Medium impact

The pagination trio (pager, count line, page-size select) is hand-rolled; three library components cover it

pagination.go:12–104 · dashboardCSS .pagination block

renderPagination (Prev/Next only), renderPaginationInfo ("Showing X–Y of Z"), and renderPageSizeSelector (raw <select> + <option selected> strings) duplicate navigation.Pagination (numbered pages with MaxVisible windowing, QueryParam, ContainerAware), display.ListNote ("Showing N of M…", role="status", renders only when Total > Shown), and forms.Select (labeled, accessible, normalized selected/disabled states).

Recommendation Replace all three; the numbered pager is a UX upgrade over Prev/Next-only for the events and audit listings.
Missed Opportunity · Medium impact

Easy leaf wins: EmptyState, PageHeader, definition rows, Buttons

render.go:59–65 (emptyState) · .page-header markup in 6+ renderers · handler_overview.go:172–186 (metaRow/metaRowCopyable) · .btn/.btn-danger/.btn-accent strings everywhere

emptyState() has no icon, no call-to-action, and no role="status" — display.EmptyStateProps ships all three (Icon, ActionText/ActionHref/ActionAttrs, role="status" baked in). Page titles repeat <div class="page-header"><h2>... where display.PageHeader adds subtitle/breadcrumb/action slots. metaRow key/value tables are display.DefinitionList. The three-button class system is display.Button's 9 variants (including danger) with optional Wire *wire.Action for HTMX attributes.

Recommendation These four are mechanical swaps — ideal first targets to validate the hybrid pipeline end-to-end before touching tables or the shell.
Missed Opportunity · Medium impact

Dark mode follows the OS only — ThemeToggle adds a no-FOUC manual toggle

dashboardCSS @media (prefers-color-scheme: dark) block

Dark mode works but can't be overridden. layout.ThemeScript(nonce) + layout.ThemeToggle(ariaLabel, nonce) provide class-based dark mode with localStorage persistence, system-preference default, and no-flash-on-load — matching the existing color-scheme: light dark meta tag's intent.

Structural · Honest partial fit

Sidebar/AppShell/Base: partial fit — and there's in-repo precedent for hand-rolling exactly this

layout.go:18–133 (renderLayout/renderSidebar) · adminui/layout.templ (documented hand-rolled AppShell for the same reason)

dashboardui's dark sidebar, custom breakpoints, and hamburger/backdrop JS mirror adminui's documented rationale for skipping layout.AppShell (deep theming + custom breakpoints). Two pieces still fit: navigation.SidebarNav (Items{Label, Href, Icon, Active, Section}, CurrentPath-driven active state — replaces the item.Active class logic) and layout.Base's self-hosted-HTMX handling (HTMXSrc=HTMXSelfHost inlines the pinned htmx build with SRI, vs. the current separate /-/htmx.js request). Treat full AppShell adoption as an optional post-migration evaluation, not a finding.

Anti-patterns · Fixed by adoption

Two anti-patterns the library replaces by design

dashboardJS:546–554 (JS-built innerHTML rows) · dashboardCSS:291–292 (div-click copy)

(1) The live-feed handler builds rows with string-concatenated innerHTML from SSE payload fields — data is self-produced today, but the pattern is one refactor away from an injection surface. The library's ValueID/HTMX-refresh model eliminates JS-built HTML entirely. (2) Div-click-to-copy (no keyboard, no semantics) — covered in F7 via CopyButton.
