00 · Summary

The question was “are we using /home/lars/projects/templ-components superbly?” — asked against a repo whose history is the answer’s best evidence. In seventeen days the series moved dashboardui from 0 → 79 → 83 → 94 (2026-09-17 → 09-23) and adminui from 68 → 97. This week a concurrent session rebuilt loginpage on the library — overturning the 2026-09-23 “keep hand-rolled” verdict — and this audit scores that adoption at 95. All three UI modules now pin v1.19.4 (the latest tag, zero behind), no module ships an anti-pattern, and every adoption gate is green.

Census: 242 distinct library identifiers in use across the three modules (adminui 123, dashboardui 98, loginpage 21) at 526 call sites of component/props symbols alone. Six of nine consumer-relevant packages are imported (display, forms, feedback, layout, navigation, errorpage, htmx, icons, utils — eight, counting htmx/icons/utils; only datastar, wire, and charts/echarts sit at zero, all deliberately).

The bottom line. This is superb usage. The remaining tail is four items: document the consumer Tailwind requirement in setup (the one HIGH finding — setup consumers currently get an unstyled login page), file the two-week-old upstream StatusBadge-map patch, swap dashboardui’s eight hand-rolled page headers, and finish two 0.5-partials (loginpage spinner, RelativeTime). None of these are misuses — they are the last mile.

04 · loginpage — 95 (new adoption, reviewed)

What was adopted, deeply: layout.Base via DefaultPageProps with six knobs exercised precisely — Nonce, CSSPath, Favicon suppressed in favor of a templ.SafeURL data-URI, HeadContent for the CSRF meta, HTMXVersion/HTMXSrc suppressed (the page ships no htmx runtime), SEO.NoIndex (login pages must not be indexed), NoThemeScript+BodyClass for SSR-first theming (handler.go:253-269). forms.Input ×3 and display.Button ×4 with every login.js DOM hook pinned via BaseProps.ID (lp-email, lp-reg-email, lp-reg-name, lp-login-btn, lp-register-btn) — the AGENTS.md pinning gotcha, applied. feedback.Alert for the static no-auth case. utils.Class, utils.Ternary, utils.BaseProps throughout.

The injected-config script is hardened (scriptSafeJSON + sanitizeNonce) — the 2026-10-04 injection review’s fixes all survived the rewrite, and the CHANGELOG coherently merges both work streams.

The inline config-JSON script block has no library equivalent (library gap, not a consumer one).

06 · Findings (ordered by impact)

F1 · HIGH · consumer-facing gap

setup consumers get an unstyled login page

The login page now requires a consumer-compiled Tailwind stylesheet (CSSPath, default /app.css), but nothing in the setup surface says so: attachLogin passes no CSSPath (setup/setup.go:313-318), setup/README.md — the canonical config table — contains zero guidance on Tailwind, @source scanning, or the /app.css requirement, and examples/setup-demo (the flagship one-call showcase) ships no CSS wiring at all. A setup consumer following the README gets a structurally correct but visually broken login page. loginpage’s own README documents the requirement — setup users never read it.

Fix (one session): add a “Styling” section to setup/README.md with a copy-paste Tailwind v4 @source snippet scanning github.com/larsartmann/cqrs-htmx/loginpage/v4; wire a minimal stylesheet into setup-demo; consider a setup.Config.LoginCSSPath passthrough. Impact 5 × ease 3.

F2 · MEDIUM · upstream, unfiled for 17 days

statusToBadgeMap still lacks adminui’s statuses

The 2026-09-17 adminui audit’s F6 proposed an upstream patch adding suspended/deleted/verified/enabled to the library’s display.statusToBadgeMap. Verified today: the map (display/badge_templ.go:397-406) still lacks them, and no upstream issue exists. adminui compensates with manual BadgeType maps (util.go:26,43) — correct, but the partial persists. File the issue upstream; adopt StatusBadge when it lands.

F3 · MEDIUM · the last dashboardui gap

Eight hand-rolled .page-header blocks vs display.PageHeader

audit.templ:89,116 · projections.templ:90 · aggregates.templ:61 · snapshots.templ:44 · dlq.templ:26,51,126. Closing this lifts dashboardui to a computed 97–100 under rubric v1 and retires the only full capability gap in the fleet. Verify the dark-token shell survives the swap (the 09-23 report’s caveat).

F4 · LOW · loginpage 0.5-partial

Hand-built spinner markup in login.js

login.js:144-145 injects a hand-written SPINNER_HTML span. A hidden server-rendered feedback.Spinner inside each submit button + JS visibility toggle would keep the markup library-owned and visually identical. Small, but it is loginpage’s only partial.

F5 · LOW · lying config doc

Config.AccentColor documents a power it no longer has

config.go:89 says AccentColor “overrides the button/highlight color” — but since the rewrite, styling is Tailwind-only and the value reaches only the SVG favicon (util.go’s own validator comment admits this). A consumer tuning accent colors for buttons will see nothing change. Re-doc the field (or rename toward FaviconAccent) before the next train.

F6 · LOW · queued swap, unchanged

dashboardui RelativeTime narrow swap still queued

Snapshot-detail “Created” timestamps (SSE live rows correctly excluded) — open since 2026-09-23, trivial when touched next.

F7 · INFO · documentation

Undocumented divergence: loginpage × recipes.AuthLayout

The recipe exists upstream (split-screen branding panel) and was the 09-23 audit’s swap #1. Not adopting it is the right call — the single centered card is the module’s identity — but the choice is recorded nowhere in loginpage. One README sentence prevents the next audit from re-litigating it.
