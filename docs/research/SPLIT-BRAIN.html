00What is a split brain?

A split brain is a data-model disease: the same domain fact is encoded in two or more places that are updated by different code and can disagree. It is distinct from duplication-for-transparency (e.g. a read-model projection that is deliberately derived from a single write model). The test is simple: if the two representations can legitimately diverge, it is a split brain. Below, every finding passes that test.

The codebase is otherwise disciplined — branded IDs, pure fold functions, strong authMode enums. These findings are mostly the residue of a migration from a legacy roles-on-User model to a membership/Casbin model, plus the natural drift between an independent submodule and its root. They are fixable.

01Roles live in three places

Critical · silent authorization inconsistency

A user's roles — the single most security-sensitive fact in the system — are modeled in three independent locations that are updated by different event handlers and can disagree:

Read model (legacy path, still live)
User.Roles []Role // user.go:24
set by eventRolesUpdated // es_readmodel.go:66-76
Membership aggregate (the "new" way)
MembershipState.Roles []Role // es_membership_state.go:12
set by MemberAdded/MemberRolesChanged

The write model explicitly dropped roles during the membership migration:

// usermgmt/es_state.go:11-12 // UserState is the aggregate state for the User, reconstructed by folding events. // Roles are NOT tracked here — managed by the Membership aggregate and CasbinProjection. type UserState struct { // ...no Roles field (es_state.go:13)

But the read model never got the memo. User.Roles still exists, and UserReadModel.Handle still folds eventRolesUpdated to populate it. Meanwhile a third authority — the Casbin projection — derives policies from membership events. So a consumer reading user.Roles can see a different role set than Authz.RolesForActor returns for the same user, depending on which command path last ran (UpdateRolesCmd legacy vs UpdateMemberRolesCmd new).

usermgmt/es_events.go:13 UserRegisteredPayload.Roles []Role # legacy event still carries roles usermgmt/es_events.go:18 RolesUpdatedPayload.Roles []Role # legacy event still carries roles usermgmt/es_migration.go:29 MigrateRolesToMemberships(...) # the half-finished bridge usermgmt/user.go:67 HasRole(...) # reads the legacy field
Drift risk: An admin calls Service.UpdateRoles (legacy) → User.Roles updates but memberships do not. Authz.Authorize (Casbin) now disagrees with user.HasRole. The UI shows one role set; enforcement uses another. This is an authorization-bypass-shaped hole.
Fix: Finish the migration. Remove User.Roles, HasRole, the eventRolesUpdated branch in the read model, RolesUpdatedPayload, and UpdateRolesCmd. Make MembershipReadModel / Authz.RolesForActor the only source of roles. MigrateRolesToMemberships is the one-way valve that makes this safe.

02Two UserID types

Critical · same concept, incompatible types

"User ID" is one concept, but it has two type definitions in two modules with different backing representations and a manual string bridge:

Root module — ULID-backed
// context.go:13
type UserID = id.UserID // ULID, go-cqrs-lite
usermgmt — string-backed branded
// usermgmt/id.go:15
type UserID = brandid.ID[userBrand, string]

Both are named UserID, both claim to brand the same domain concept, but they are not assignable to each other. Crossing the module boundary requires .Get() / NewUserID(s) string round-trips (e.g. es_readmodel.go:57: NewUserID(aggID.String())). The AGENTS.md even documents this as a permanent "bridge" — but a bridge between two types of the same concept is a split brain that has been normalized.

Drift risk: Validation differs — root requires a valid ULID, usermgmt accepts any string. A usermgmt UserID built from a non-ULID string silently fails id.ParseUserID on the root side, and vice-versa. Context-key sentinels (userIDKey{} root vs userContextKeyType{} usermgmt) mean the two contexts do not share identity either.
Fix: Pick one canonical UserID definition and re-export it from the other module, or define a shared identity sub-module both depend on. The cleanest option is to make usermgmt's branded type the canonical one and have root alias it — or adopt go-cqrs-lite's id.UserID everywhere and drop go-branded-id for users.

03Two rate-limit configurations, different algorithms

Critical · reinvented mechanism, divergent semantics

Rate limiting exists twice, with different names, different algorithms, and different field sets:

Aspect Root RateLimiterConfig usermgmt RateLimitConfig
Location ratelimit_config.go:48 usermgmt/http.go:89
Algorithm Token bucket (golang.org/x/time) Fixed-window counter (hand-rolled)
Key Pluggable KeyExtractor Hardcoded per-IP
Burst Burst field None
Eviction min-heap LRU + TTL + MaxKeys None (unbounded map)
Hooks OnAllowed / OnRejected / RejectionHandler None

The usermgmt one is a strict subset of the root's capability, reimplemented from scratch as perIPRateLimiter + rateLimitEntry (http.go:98-107). The AGENTS.md's claim that "all use the shared RateLimitConfig type" is misleading — they are two unrelated types that happen to share a substring.

Drift risk: The hand-rolled fixed-window limiter has no eviction and no burst handling, so under load it both leaks memory and behaves differently from the root limiter. Two algorithms for "limit this" means tuning, observability, and edge-cases all diverge.
Fix: Delete usermgmt/http.go's RateLimitConfig, rateLimitEntry, and perIPRateLimiter. Have HandlerConfig hold root RateLimiterConfig values and build a *RateLimiter per endpoint group. The root module already solves this better.

04Actor identity, two models

High · lost kind discrimination at the boundary

"Who is acting" is modeled two ways depending on which module you are in:

Root context API — untyped string
// context.go:141,147
WithActorID(ctx, actorID string)
ActorIDFromContext(ctx) string
usermgmt — typed discriminated union
// usermgmt/id.go:74
type ActorID struct {
  kind ActorKind; raw string // user | bot
}

usermgmt has a rich ActorID that distinguishes humans (ActorUser) from bots (ActorBot) at the type level. But when identity crosses into the root module's context, it is flattened to a bare string — the kind is lost. Two models for the same "actor" concept, and the typed one cannot survive the boundary.

Fix: Promote usermgmt's ActorID (or a shared equivalent) into the context API so WithActorID carries the kind. This pairs naturally with fixing split brain #2 (canonical identity types).

05Twin setup constructors re-implement the same wiring

High · duplicated infrastructure wiring

NewService(ServiceConfig) and NewEventSourcedSetup(EventSourcedConfig) both build the exact same event-sourced infrastructure, line for line, in parallel:

usermgmt/service_core.go NewService usermgmt/es_setup.go NewEventSourcedSetup wrapEventStore(cfg.StoreWrapper, ...) wrapEventStore(cfg.StoreWrapper, ...) applyBusMiddleware(...) applyBusMiddleware(...) decider.NewRepository(store, bus, UserDecider()) decider.NewRepository(store, bus, UserDecider()) ...x4 aggregates ...x4 aggregates NewAuthz() / NewCasbinProjection() NewAuthz() / NewCasbinProjection() NewUserReadModel() / x4 NewUserReadModel() / x4 StartProjections(...) StartProjections(...)

The shared helpers (wrapEventStore, applyBusMiddleware, journalFromStore) were already extracted — good — but the orchestration of those helpers is copy-pasted. es_setup.go:104 even admits it: "Applies security hooks ... at the same points as NewService." Two copies of the same wiring that must be kept in sync by hand.

Drift risk: If the repo-creation order, projection-start sequence, or error-handling changes in one constructor, the other silently diverges. The SecurityHooks unification was a reaction to exactly this drift; the underlying duplication remains.
Fix: Make NewService call NewEventSourcedSetup internally and adopt its *EventSourcedSetup as the source of infrastructure. Service then adds only its own concerns (dispatcher, sessions, WebAuthn, TOTP, OAuth2) on top. One wiring, one place.

06Legacy event structs duplicate event-sourced payloads

High · two event families + double emission + 1 ghost

Domain events are represented by two parallel struct families. The event-sourced payloads (es_events.go) are the real persisted events; the legacy *Event structs (events.go) feed the old EventHandler callback:

Legacy (events.go) Event-sourced (es_events.go) Emitted?
UserRegisteredEvent UserRegisteredPayload twice (direct + bridge)
RolesUpdatedEvent RolesUpdatedPayload twice (direct + bridge)
UserLoggedInEvent — never (ghost)
— UserDeletedPayload, CredentialAdded, ... no legacy shadow

The legacy set is incomplete (no UserDeletedEvent, CredentialAddedEvent, etc.), so it has already drifted from the real event taxonomy. Worse, emission is doubled: service methods emit directly (service_register.go:101, service_misc.go:32) and a bus bridge re-emits the same structs from projections (service_core.go:395,404). When an EventHandler is configured, it receives UserRegisteredEvent / RolesUpdatedEvent twice.

Finally, UserLoggedInEvent (events.go:21) is a ghost: defined, documented as "emitted after a successful login," but never referenced anywhere outside its own declaration. Passwordless auth produces no login event.

usermgmt/events.go:21 type UserLoggedInEvent struct {...} // GHOST: 0 usages outside the definition usermgmt/service_core.go:334 svc.bridgeEventHandler(bus) // bridge IS wired usermgmt/service_register.go:101 s.emit(req.ID, UserRegisteredEvent{...}) // AND direct emit
Fix: Delete events.go's legacy structs and the EventHandler callback entirely (consumers should subscribe to the bus). That removes the double emission, the ghost, and the incomplete shadow taxonomy in one cut. If the callback must stay for compat, route it only through the bridge and delete the direct s.emit calls.

07SSE/WS broadcaster twins & naming asymmetry

Medium · parallel API surface, inconsistent naming

The transport-agnostic core was already extracted into fanOut[T] (fanout.go) — a real strength. But the two outer types still mirror each other field-for-field and method-for-method, with an asymmetric naming convention:

SSE — no suffix
Broadcaster // sse_broadcaster.go:21
BroadcastOnSuccess(name, data)
BroadcastOnSuccessFunc(fn)
BroadcastOnError(name)
BroadcastOnErrorFunc(fn)
WS — WS suffix
WSBroadcaster // ws_broadcaster.go:37
BroadcastOnSuccessWS(msg)
BroadcastOnSuccessWSFunc(fn)
BroadcastOnErrorWS()
BroadcastOnErrorWSFunc(fn)

Additionally, the implementation is internally inconsistent: BroadcastOnSuccess / BroadcastOnSuccessWS inline their own err-check loop, while their *Func siblings delegate to the shared fanOut.broadcastOnSuccessHook. Four near-identical hook constructors that should be one generic helper.

Fix: Since both already embed *fanOut[T], expose the hook builders once on fanOut (generic over T) and drop the per-type wrappers, or at minimum make the SSE methods carry an SSE suffix for symmetry.

08The Email type exists but is barely used

Medium · validated type bypassed by raw string

A validated, normalized Email value type exists:

// usermgmt/email.go:13 type Email string // + ParseEmail / MustParseEmail (RFC 5322, normalized)

But virtually every consumer uses raw string instead — User.Email (user.go:22), UserState.Email (es_state.go:14), UserRegisteredPayload.Email (es_events.go:11), RegisterRequest.Email, every command struct. The validated Email appears almost only in ExportUser. Validation runs in ParseEmail, then the result is immediately .String()'d back to an unvalidated string that flows everywhere.

Drift risk: A raw string email can be un-normalized, untrimmed, or structurally invalid by the time it reaches a comparison or uniqueness index. The type exists to prevent exactly this — it just isn't enforced at the boundary.
Fix: Make User.Email, the payload/command structs, and RegisterRequest.Email use Email. Construct at the HTTP boundary via ParseEmail; store the validated value.

09Two Casbin wrapper layers

Medium · two abstractions over one engine

Casbin authorization is wrapped twice:

Root — minimal interface
// authz.go:11
type Enforcer interface {
  Enforce(...any) (bool, error)
}
// + AuthorizeMiddleware
usermgmt — rich wrapper
// authz_types.go:110
type Authz struct { enforcer *casbin.Enforcer }
// + Policy / GroupPolicy / EnforceResult

Root's Enforcer is satisfied directly by *casbin.Enforcer; usermgmt's Authz is a richer domain wrapper with its own Policy/GroupPolicy types and an enforcerAdapter (authz_types.go:192) to satisfy root's interface. Two abstraction layers over the same engine, neither referencing the other's vocabulary.

Fix: This is lower priority — the adapter pattern makes it work — but usermgmt's Authz could satisfy root's Enforcer contract directly via the existing adapter, and the root could document Authz as the reference implementation rather than leaving two unconconnected layers.

10Credential fields cloned by hand between two structs

Medium · manual field-copy rot

WebAuthnCredential (credential.go:7) and CredentialAddedPayload (es_events.go:37) share eight identical fields:

WebAuthnCredential CredentialAddedPayload ID []byte ID []byte PublicKey []byte PublicKey []byte AttestationType string AttestationType string Transports []string Transports []string AAGUID []byte AAGUID []byte SignCount uint32 SignCount uint32 BackupEligible bool BackupEligible bool BackupState bool BackupState bool Name string Name string // + CreatedAt time.Time (payload omits it; uses evt.OccurredAt)

They are bridged by newCredentialFromPayload (credential.go:23) — a hand-written field-by-field copy. Add a field to one struct and forget the other (or the copy function) and the credential silently loses data on the round-trip.

Fix: Define a CredentialCore struct embedding the shared eight fields; embed it in both WebAuthnCredential and CredentialAddedPayload. The copy becomes a single core assignment. Same pattern applies to ExternalAccount vs ExternalAccountLinkedPayload.

♦What the model already gets right

These were checked and are genuinely single-sourced — credit where it is due.

+
fanOut[T] generic hubThe SSE/WS fan-out core was correctly unified into one generic type — only the outer shells remain parallel (split brain #7).
+
authMode enumauthNone/authRequired/authAuthorized makes invalid auth states unrepresentable — no stringly-typed auth mode anywhere.
+
Branded TenantID / BotIDUnlike UserID, the tenant and bot identifiers are each defined exactly once and consistently branded.
+
SessionOrigin typed unionSessionOrigin (DirectLogin / Impersonation) is a clean interface-based union — exactly the pattern the rest of the model should follow.
+
Pure fold functionsfoldUser / foldMembership / foldTenant / foldBot are pure, side-effect-free state transitions — the write model is clean.

↺Consolidation plan

Ordered by impact-to-effort ratio. Each step is independently shippable.

Delete the ghost + stop double emission

Remove UserLoggedInEvent; delete the direct s.emit calls in service_register.go/service_misc.go, keeping only the bus bridge. Cheapest win, kills the double-delivery bug. (Split brain #6)

Finish the roles migration

Remove User.Roles, HasRole, the eventRolesUpdated read-model branch, RolesUpdatedPayload, UpdateRolesCmd, and the legacy RolesUpdatedEvent. Make Authz.RolesForActor the sole source. Run MigrateRolesToMemberships for existing stores. (Split brain #1)

Adopt the root rate limiter in usermgmt

Delete usermgmt/http.go's limiter; have HandlerConfig use root RateLimiterConfig. Removes an unbounded map and an inferior algorithm. (Split brain #3)

Unify UserID + ActorID

Pick one canonical UserID across both modules; make WithActorID carry the typed ActorID (kind + raw) instead of a bare string. (Split brains #2, #4)

Make NewService delegate to NewEventSourcedSetup

Service adopts *EventSourcedSetup for infra; adds only dispatcher/sessions/auth on top. (Split brain #5)

Enforce the Email type at boundaries

Switch User.Email and the command/payload structs to Email. (Split brain #8)

Dedupe credential/external-account fields

Introduce shared embedded core structs; collapse the hand-written copies. (Split brains #10, #7)

★Verdict

The data model is 80% excellent — pure folds, branded IDs, typed unions. But one security-critical fact (roles) is modeled three times, and the root/usermgmt boundary has fossilized into permanent string bridges. Fixing split brain #1 (roles) alone removes the only finding that can cause an authorization inconsistency. The rest is consolidation.
