01Findings

Fixed

Script breakout via config JSON in the application/json block

loginpage/page.templ:81 · loginpage/handler.go (buildPageData)

The client config JSON is embedded via templ.Raw("<script id=\"loginpage-config\">" + p.configJSON + "</script>"). Empirically verified: encoding/json/v2's json.Marshal does not HTML-escape (unlike encoding/json v1), so a Config value such as CredentialName: "</script><script>alert(1)</script>" terminated the script block and injected executable markup. AuthPrefix had the same exposure. Inputs are consumer-controlled config, not remote input — but the module's contract is to render whatever Config says safely.

Fix (applied) scriptSafeJSON now escapes < > & to \u003c-style escapes after marshaling (safe: those characters only occur inside JSON string literals). Regression tests assert the payload never reaches the rendered body.
Fixed

<style> injection via AccentColor

loginpage/page.templ:16 · loginpage/config.go (withDefaults)

templ.Raw("<style>:root{--lp-accent:" + p.Accent + ";}"...) embeds AccentColor unescaped in a raw style block; a value containing </style><script> breaks out. The same value is also embedded in the SVG data-URI favicon (SafeURL — the href attribute itself IS escaped by templ, verified in the generated code, so the favicon is not a breakout path on its own). AccentColor was never validated despite being documented as "any CSS color" — no legitimate CSS color contains markup or quote characters.

Fix (applied) validateAccentColor rejects < > & " ' \ ` at construction (New/NewPageData fail fast). rgb()/color-mix()/var() notations still accepted; tested.
Fixed

CSSPath accepted executable schemes

loginpage/page.templ:18 · loginpage/util.go

Config.CSSPath was rendered as a plain templ href — templ HTML-escapes attributes but does not sanitize URL schemes, so javascript:alert(1) produced a clickable link.

Fix (applied) validateStylesheetURL accepts only root-relative paths and absolute http(s) URLs; everything else fails at construction with an actionable message.
Fixed

Doc split brain: OAuth2Buttons "empty slice hides all buttons"

loginpage/config.go:100

The field doc claimed an empty slice hides all OAuth2 buttons, but buildPageData auto-populates buttons whenever the slice is empty — there is no way to force-hide auto-detected providers. Behavior (auto-detect, matching the README) is right; the comment lied.

Fix (applied) Comment corrected to describe actual behavior; the missing force-hide option is filed in TODO_LIST.
