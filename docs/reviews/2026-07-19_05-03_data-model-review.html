What is excellent

Strong branded-type discipline for identifiers

UserID = id.UserID, BotID = brandid.ID[botBrand, string], TenantID = brandid.ID[tenantBrand, string], ActorID = brandid.ID[actorBrand, string], CorrelationID = id.CorrelationID, RequestID, ImpersonatorID = ActorID. The brandid.ID[Brand, Raw] generic pattern makes accidental cross-type substitution a compile error. This is the right way to use Go generics for type safety.

Generics used where they earn their keep

MaterializeProjection[V any, K fmt.Stringer] — typed projection state. fanOut[T any] — typed event channel. RenderPaginatedJSON[T](), DecodeJSON[T]() — typed decoder/renderer pipeline. None are gratuitous; each eliminates a real duplicate-type family.

Duck-typed interfaces for optional deps

Enforcer matches casbin without importing casbin. TemplComponent matches templ's Render without importing templ. HTTPStatusCarrier for errors. This is textbook "accept interfaces, define structs" — and at the package boundary it keeps the dep tree small.

authMode closed enum prevents impossible states

type authMode int with three unexported constants (authNone, authRequired, authAuthorized). The only way to set the mode is through Authorize(...) / RequireAuth(), which transition none → required → authorized in order. Impossible to skip required and reach authorized. This is the model the rest of the codebase should aspire to.

Problems found

Critical Email branded type exists but is not used in User

The codebase defines type Email string with a validating ParseEmail(raw) (Email, error) constructor (lowercases, trims, RFC 5322 check). But User.Email is string, not Email. Same for UserState.Email, ChangeEmailCmd.Email, UserRegisteredPayload.Email, etc.

Why it matters: The entire point of branding Email is lost. Any string can land in User.Email without validation. You have a typed validator that the type system ignores.

Fix:

// usermgmt/user.go
type User struct {
    ID    UserID
    Email Email       // ← was string
    ...
}

This is a breaking change to JSON consumers (no — JSON tags stay the same, only the Go type changes). Event payloads use encoding/json/v2 which marshals Email identically to string. Pure type-safety win, zero serialization impact.

High User lifecycle encoded as bool — impossible states representable

User has EmailVerified bool, TOTPEnabled bool. UserState has Deleted bool, DeleteReason string. A Deleted=true user still has populated Email, Credentials, etc. — nothing in the type system prevents reading credential data from a deleted user.

Fix: Model lifecycle as a closed enum or interface union:

type UserLifecycle int
const (
    LifecycleActive UserLifecycle = iota
    LifecycleDeleted // UserDeleted carries DeleteReason
)

Or, more aggressively, two types: ActiveUser and DeletedUser, where read-models choose which to accept. (Likely too invasive — start with the enum.)

High Two different ActorID shapes for the same concept

Root: type ActorID = brandid.ID[actorBrand, string] — a flat branded ID.
usermgmt: type ActorID struct { kind ActorKind; raw string } — a kind-discriminated struct (kind ∈ {User, Bot}).

These model the same concept (who performed an action) with different shapes. Cross-module code must convert. AGENTS.md documents this, but documenting a model split doesn't fix it.

Fix: Converge on usermgmt's discriminated shape (it carries more info), or push the discrimination into a wrapping type Actor { ID ActorID; Kind ActorKind } with a flat ActorID. Pick one, apply everywhere.

Medium User vs UserState vs UserView vs UserReadModel — four parallel shapes

The User domain has 4 struct types that overlap heavily: User (entity), UserState (event-sourced fold state), UserView (read-model), UserReadModel (projection). Fields are duplicated across all four. Adding a field means touching 4 types.

Fix: Define a single UserCore with the shared fields, embed it in the others with their specific additions (timestamps, deleted-state, etc.). Same pattern already used for credentialCore.

Medium HandlerConfig.Secure *bool — pointer-as-tristate anti-pattern

Documented as: nil defaults to true, new(bool) for false. This is the classic "pointer to encode optionality" anti-pattern. Consumers must read the godoc to know what nil means.

Fix: type SecureMode int with SecureDefault, SecureTrue, SecureFalse. Or: invert the API to Insecure bool (zero value = secure, the safe default).

Medium TOTPSecret []byte in User — secret material in domain entity

The TOTP secret lives in UserState/User directly. While tagged json:"-" for transport safety, the domain entity still carries cryptographic material. This couples the User aggregate to one specific MFA implementation.

Fix: Move to a separate TOTPState owned by the TOTP strategy module — the same way WebAuthn credentials have their own store. Keeps User auth-strategy-agnostic.

Medium AccountLockout uses map[string]uint keyed by raw string

Keys are user identifiers (email? ID?), but typed as raw string. If the key scheme ever changes (email → UserID), old locks silently become orphans.

Fix: map[UserID]uint or map[Email]uint. Make the key type explicit.

Low Session struct lacks lifecycle modeling

Sessions have implicit states: active, expired, revoked. The Session type has timestamps but no explicit status. A revoked session is indistinguishable from an active one in the type — only the store knows.

Closed-union pattern recommendation (the authMode template)

The authMode pattern in root is exemplary. Apply it to the five stringly-typed enums. Template:

// Before
type Action string

// After — sealed via unexported ctor
type Action string

var (
    ActionRead   = Action("read")
    ActionCreate = Action("create")
    ActionUpdate = Action("update")
    ActionDelete = Action("delete")
)

// Valid reports whether a is one of the defined Actions.
func (a Action) Valid() bool {
    switch a {
    case ActionRead, ActionCreate, ActionUpdate, ActionDelete:
        return true
    }
    return false
}

Or, for full compile-time sealing, use a generic sealed-pattern:

// Sealed is a marker type for closed string unions.
type Sealed[T ~string] struct{ v T }

func (s Sealed[T]) String() string { return string(s.v) }

Prioritized redesign

  1. Adopt Email branded type in User — highest leverage, zero serialization impact. ~1 hour.
  2. Seal the 5 stringly-typed enums — eliminates typo class of bugs across authz. ~3 hours.
  3. Extract UserCore shared struct — embed in User/UserState/UserView/UserReadModel. ~4 hours.
  4. Replace *bool on HandlerConfig.Secure with explicit tristate. ~1 hour.
  5. Decide ActorID shape (one type, not two) — cross-module consistency. ~1 day, breaking change.
  6. Move TOTPSecret out of User — strategy-module isolation. ~1 day, breaking change.
