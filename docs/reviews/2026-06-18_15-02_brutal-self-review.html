~100 lines of copy-pasted broadcaster code → eliminated via generic fanOut[T]

sse_broadcaster.go + ws_broadcaster.go → fanout.go (commit 7267abf)

The Broadcaster (SSE) and WSBroadcaster were structurally identical — same fields, same Subscribe/Unsubscribe/Broadcast/SubscriberCount logic. The only difference was the channel element type: chan SSEEvent vs chan string.

Fixed

Timeout split brain → unified into single nil-safe timeoutCtx

app.go:270 (commit 7267abf)

timeoutCtx(ctx, *handlerConfig) checked per-handler timeout override, then fell back to App timeout. dispatchTimeout(ctx) only checked App timeout — it was a verbatim subset of timeoutCtx's fallback branch. Two functions doing the same thing with subtly different behavior was a maintenance trap.

Fixed: Made timeoutCtx nil-safe for *handlerConfig (guards cfg != nil before reading cfg.timeout). Removed dispatchTimeout entirely. WS dispatch now calls a.timeoutCtx(ctx, nil) — the same method the HTTP path uses.

Fixed

channelPtr misplaced → moved to fanout.go

sse_broadcaster.go:37 → fanout.go:90 (commit 7267abf)

The channelPtr helper is transport-agnostic (returns the pointer identity of any channel) but was defined in sse_broadcaster.go. WS code depended transitively on an "SSE" file for a shared utility.

Fixed: Moved channelPtr to fanout.go alongside the generic fanOut[T] type that uses it. Both broadcasters now import it from the transport-agnostic file, not from each other's transport-specific file.

03Parity Gaps — All Closed

Fixed

WS Broadcaster missing Func variants → added BroadcastOnSuccessWSFunc + BroadcastOnErrorWSFunc

ws_broadcaster.go (commit 7267abf) — now has 4 hook constructors matching SSE

SSE had BroadcastOnSuccessFunc(fn) and BroadcastOnErrorFunc(fn) for dynamic event generation. WS only had the static BroadcastOnSuccessWS(msg) and BroadcastOnErrorWS(). Consumers who needed dynamic WS messages had no hook to use.

Fixed: Added BroadcastOnSuccessWSFunc(fn) and BroadcastOnErrorWSFunc(fn). WS now has full 4-hook parity with SSE. 4 new Ginkgo specs verify both dynamic variants.

Accepted

WS dispatch flow parallels HTTP dispatch flow — structural, not duplication

ws_dispatch.go vs handler.go — intentionally separate paths

The WS dispatch methods mirror the decode → nil-check → timeout → dispatch → error-wrap → hook flow from the HTTP path. The error-wrapping idiom fmt.Errorf("%w: %s: %w", ErrDispatchFailed, cmdType, err) appears in both paths.

Decision: Leave as-is. The two paths are structurally similar but intentionally separate because the WS path has no http.ResponseWriter, no handlerConfig, and returns (error) instead of writing a response. Forcing them into a shared helper would require so many conditionals that it would be harder to read than the current parallel implementation. The error-wrapping idiom is a 1-line pattern — not worth extracting for 6 call sites.
