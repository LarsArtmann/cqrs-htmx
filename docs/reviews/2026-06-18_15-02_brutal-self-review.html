02What's Fucked Up

Critical

~100 lines of copy-pasted broadcaster code

sse_broadcaster.go:23-100 vs ws_broadcaster.go:30-104

The Broadcaster (SSE) and WSBroadcaster are structurally identical — same fields, same Subscribe/Unsubscribe/Broadcast/SubscriberCount logic. The only difference is the channel element type: chan SSEEvent vs chan string.

This is a textbook case for Go generics. A fanOut[T any] type eliminates all duplication while both broadcasters keep their exact public API via struct embedding.

// CURRENT: ~100 lines duplicated
type Broadcaster struct {
    mu sync.RWMutex
    subscribers map[uintptr]chan SSEEvent
}
type WSBroadcaster struct {
    mu sync.RWMutex
    subscribers map[uintptr]chan string
}

// AFTER: one generic implementation
type fanOut[T any] struct { ... }
type Broadcaster struct { *fanOut[SSEEvent] }
type WSBroadcaster struct { *fanOut[string] }
Critical

Timeout split brain — dispatchTimeout reinvents timeoutCtx

app.go:270-282 vs ws_dispatch.go:208-213

timeoutCtx(ctx, *handlerConfig) checks per-handler timeout override, then falls back to App timeout. dispatchTimeout(ctx) only checks App timeout — it's a verbatim subset of timeoutCtx's fallback branch. Two functions doing the same thing with subtly different behavior is a maintenance trap.

Fix: Make timeoutCtx nil-safe for handlerConfig or extract a shared appTimeout(ctx) that both paths call.

Critical

channelPtr misplaced in SSE file

sse_broadcaster.go:37 — used by ws_broadcaster.go:51,62

The channelPtr helper is transport-agnostic (returns the pointer identity of any channel) but lives in sse_broadcaster.go. WS code depends transitively on an "SSE" file for a shared utility. This is a misplaced-definition smell that will confuse anyone reading the WS code.

03Parity Gaps

Gap

WS Broadcaster missing Func variants

sse_broadcaster.go has 4 hook constructors; ws_broadcaster.go has only 2

SSE has BroadcastOnSuccessFunc(fn) and BroadcastOnErrorFunc(fn) for dynamic event generation. WS only has the static BroadcastOnSuccessWS(msg) and BroadcastOnErrorWS(). Consumers who need dynamic WS messages have no hook to use.

Gap

WS dispatch reinlineates the dispatch flow instead of reusing it

ws_dispatch.go:90-148 vs handler.go:57-94

The WS dispatch methods copy the decode → nil-check → timeout → dispatch → error-wrap → hook flow from the HTTP path. The error-wrapping idiom fmt.Errorf("%w: %s: %w", ErrDispatchFailed, cmdType, err) appears 4 times in ws_dispatch.go and 2 times in handler.go. This pattern should be extracted.

Note: Some duplication is unavoidable because the WS path has no http.ResponseWriter and no handlerConfig. But the error-wrapping and hook-firing can be shared.

04Honest Answers

Did I lie?

No. All claims verified: golangci-lint run reports 0 issues. Tests pass with -race. Build compiles. All files under 350 lines. The LSP warnings (errchkjson, exhaustruct, typecheck) are confirmed stale false positives — the authoritative CLI is clean.

What did I forget?

  • The generic refactor. I created WSBroadcaster by copy-pasting Broadcaster and changing the type. This is the #1 thing I should have done differently. Generics exist for exactly this case.
  • WS Func variants. I added BroadcastOnSuccessWS and BroadcastOnErrorWS but forgot their Func counterparts that SSE has. Incomplete parity.
  • Moving channelPtr. I used it from ws_broadcaster.go without noticing it's defined in sse_broadcaster.go. Misplaced dependency.

Is this production-ready?

Yes, but it could be cleaner. The code works correctly, has comprehensive tests, and ships zero breaking changes. But the duplication is a maintainability debt that compounds — any fix to the snapshot logic or buffer size needs to be applied in two places. The generic refactor pays for itself immediately.

Split brains?

One: dispatchTimeout vs timeoutCtx. They do the same thing with subtly different behavior. This is a split brain.
