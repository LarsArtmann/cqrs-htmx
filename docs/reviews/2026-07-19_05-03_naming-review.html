Naming Review

cqrs-htmx · 2026-07-19 · Types and functions in root + usermgmt + adminui + loginpage

Naming score: 8.2 / 10 — Strong domain-aligned vocabulary, with the Service god-object as the main naming-architecture issue.

What is excellent

  • Domain-accurate aggregate names: User, Membership, Tenant, Bot, Credential, Session — all real domain nouns, no UserData/Info/Record junk for the core types.
  • Branded IDs follow the same suffix: UserID, BotID, TenantID, ActorID, CorrelationID, RequestID, ImpersonatorID. Consistent vocabulary across modules.
  • Honest verb vocabulary: Register, Authenticate, Logout, BeginLogin, FinishLogin, SuspendTenant, ReactivateTenant. Names describe the domain action, not the implementation.
  • Composition helper names match function: Chain, Authorize, DecodeJSON, RenderTempl, NotifySuccess, PushURL. All say what they do.
  • No Impl suffix anywhere. Clean.
  • No Factory/Builder overuse — constructors are New*, as Go convention dictates.

Issues found

High Service — too vague for a type with 52 methods

The usermgmt Service type has 52 methods spanning User, Tenant, Membership, Bot, OAuth2, Impersonation, Auth, Credential, and lifecycle domains. Service tells the reader nothing — it's the DDD equivalent of Manager. It earns its generic name because it does everything.

This is primarily an architecture problem (see architecture review — god-object), but the naming symptom is: the name has become a substitute for decomposition. Decompose into UserService, TenantService, OAuth2Service, etc. and the names naturally sharpen.

Medium Vague *Data suffix in adminui (9 occurrences)

adminui has 9 struct types ending in Data: auditData, dashboardData, pageData, PageData, tenantDetailData, tenantsListData, userDetailData, usersListData, navItem. Data says "I contain stuff" without saying what.

Fix: Name them after the page/fragment they render: DashboardViewModel, TenantDetailVM, UsersListVM, NavItem. ViewModel is honest — these are templates-bound view models, not domain data.

Medium AuthHandler — does Handler mean HTTP or auth?

usermgmt's AuthHandler is an HTTP handler that mounts auth routes. But Handler alone is ambiguous (auth handler? event handler? command handler?). The root module uses HandlerOption, HandlerConfig, where Handler = HTTP handler. The vocabulary overlaps.

Fix: AuthRoutes or AuthEndpoint — clearer that it's an HTTP route registration helper, not a runtime handler.

Medium OAuth2UserInfo — leaks the transport into the type name

The struct represents the user profile returned by an OAuth2 provider. UserInfo embeds both the OAuth2 protocol context and the OpenID Connect term "UserInfo endpoint". A reader who doesn't know OIDC sees OAuth2UserInfo and wonders what kind of info.

Fix: OAuth2Profile — the standard term for "claims/data returned about the user".

Medium sessionOriginInfo — unexported, but still vague

Internal type, but OriginInfo is a Data/Info smell. What does it carry? Looking at usage: it's the metadata about how a session was created (provider, IP, user agent).

Fix: sessionOrigin or sessionProvenance.

Medium pageData vs PageData — case-only split

loginpage has both pageData (unexported) and PageData (exported). Case-only name collisions for different concepts confuse readers. Two different types are doing similar work.

Fix: Rename to clarify roles — e.g. LoginPageData (exported) vs pageRenderContext (internal).

Low dummyMaterializeStringer — production code with "dummy" name

Defined in usermgmt non-test code. dummy in production signals "I haven't decided what this is yet." It's a stringer implementation used to satisfy fmt.Stringer for MaterializeProjection testing/demo purposes.

Fix: If it's a test fixture, move to _test.go. If it's a production utility, rename to staticStringer or fixedStringer.

Low handlerConfig vs HandlerConfig — unexported twin

Root has both handlerConfig (unexported, internal pipeline cfg) and HandlerConfig (exported, in usermgmt — CSRFConfig et al). Different concepts, same base word. Not a bug — but a reader grepping for "handlerConfig" must disambiguate.

Renaming recommendations (ranked)

  1. Service → decompose — As above; the rename falls out of decomposition.
  2. adminui *Data → *ViewModel or *VM — 9 types clarified.
  3. AuthHandler → AuthRoutes — removes Handler-overload ambiguity.
  4. OAuth2UserInfo → OAuth2Profile — standard OIDC terminology.
  5. sessionOriginInfo → sessionOrigin — drop the vague suffix.
  6. pageData → pageRenderContext — disambiguate from exported PageData.
  7. dummyMaterializeStringer — move to test or rename to staticStringer.
