## Dependency Graph Between Files

The previous modularization analysis (go-modularize session, 2026-05-27) concluded that "the errors↔response↔csrf cycle prevents splitting." **This analysis was wrong.** These aren't import cycles — they're shared constants within one flat package. When split into packages, they become clean one-way dependencies:

```
htmx         → zero internal deps
security     → zero internal deps
ratelimit    → zero internal deps
httputil     → zero internal deps (only external httputil)
context      → zero internal deps (only go-cqrs-lite/pkg/id)

errors       → htmx (just one header constant)
recovery     → errors
response     → htmx (headers + IsHTMXRequest)
notify       → response
authz        → context

middleware   → htmx + context + errors
csrf         → htmx + errors + response
csrf_handler → csrf
csrf_helpers → csrf
decoder      → (needs App type only)
logging      → context

options      → authz + csrf + errors + htmx + response + decoder + notify
handler      → app + errors
app          → command + query + context + errors + middleware + options + everything
```

**Zero cycles. Clean DAG.**

### Self-Contained Clusters (no internal deps)

These files can become standalone modules with zero internal dependencies:

| Cluster       | Files          | External Deps          |
| ------------- | -------------- | ---------------------- |
| **htmx**      | `htmx.go`      | None                   |
| **security**  | `security.go`  | None                   |
| **ratelimit** | `ratelimit.go` | `golang.org/x/time`    |
| **httputil**  | `httputil.go`  | `larsartmann/httputil` |
| **context**   | `context.go`   | `go-cqrs-lite/pkg/id`  |

## Options Considered

### Option A: Sub-packages within root module

Reorganize into sub-packages (`cqrs/`, `htmx/`, `authz/`, `csrf/`, etc.) but keep one `go.mod`.

| Pro                      | Con                                                |
| ------------------------ | -------------------------------------------------- |
| Cleaner organization     | Same dependency weight for consumers               |
| No import path breakage  | No actual dependency isolation                     |
| Easy to do incrementally | Doesn't solve the Unix "do one thing well" problem |

**Assessment:** Organizational improvement only. A consumer who only needs HTMX response types still pulls in Casbin, nosurf, and the entire dependency tree.

### Option B: Sub-modules (full modularization)

Split into 8+ independent Go modules, each with its own `go.mod`.

```
cqrs-htmx/
├── go.work
├── htmx/           # MODULE — 0 external deps (SwapStrategy, HTMXRequest, headers)
├── errors/         # MODULE — go-error-family, event (sentinel errors, MapError)
├── authz/          # MODULE — casbin (Enforcer interface, Authorize)
├── csrf/           # MODULE — nosurf, htmx, errors (CSRF middleware, helpers)
├── middleware/     # MODULE — htmx + context + errors + logging + ratelimit + security + recovery
├── decode/         # MODULE — 0 deps (form/JSON decoders)
├── contextx/       # MODULE — go-cqrs-lite/pkg/id (UserID, CorrelationID, RequestID)
├── httputil/       # MODULE — larsartmann/httputil (WriteJSON, ClientIP)
├── app/            # MODULE — command, query, wires everything
├── usermgmt/       # already exists
├── integration_test/ # already exists
└── examples/
    └── datastar-demo/  # already exists
```

**Consumer who only needs HTMX response builder:** `go get github.com/larsartmann/cqrs-htmx/htmx` — zero heavy deps.

### Option C: Hybrid (extract 1-2 focused modules)

Keep most things flat, extract only clearly independent modules.

| Pro                 | Con                                          |
| ------------------- | -------------------------------------------- |
| Quick wins          | Inconsistent — some things modular, some not |
| Low risk            | Doesn't solve the core problem               |
| Learn incrementally | May create awkward boundaries                |

### Option D: Leave as-is

| Pro                  | Con                                   |
| -------------------- | ------------------------------------- |
| Zero effort          | God-package violates Unix principles  |
| Zero breakage        | 164 exported symbols in one namespace |
| Consumer convenience | No dependency isolation               |

## Negatives of Option B (Sub-modules)

### 1. Consumer breaking change — the biggest concern

Every current consumer does:

```go
import cqrshtmx "github.com/larsartmann/cqrs-htmx"
```

After modularization, that import path **stops working** for moved types. A consumer using `cqrshtmx.RecoveryMiddleware` would need:

```go
import "github.com/larsartmann/cqrs-htmx/middleware"
```

Go doesn't support module aliases. We _could_ keep the root package as a thin re-export layer (`type RecoveryMiddlewareFunc = middleware.RecoveryMiddlewareFunc`) but that only works for types, not functions or constants.

**Impact:** Every consumer must update imports. This is a v2-level breaking change.

### 2. 8+ go.mod files to maintain

Every dependency bump (e.g., go-cqrs-lite v1.5.1 → v1.6.0) means editing 8+ go.mod files. The `go.work` helps with builds but not with version alignment. One module on v1.5.0 and another on v1.5.1 creates subtle bugs.

**Mitigation:** Automated tooling (dependabot, renovate) can handle multi-module bumps. The `go.work` ensures local development uses consistent versions.

### 3. Most consumers want everything

A typical consumer uses App + Command + Query + CSRF + Recovery + SecurityHeaders. That's 6 imports from 4 modules. The flat package gives them 1 import. Is the dependency isolation worth the import complexity?

**Counter-argument:** Some consumers only want HTMX helpers, or only the error mapping, or only the middleware chain. These consumers currently pay the full dependency cost.

### 4. Versioning strategy becomes mandatory

With 8 modules, you need to decide:

| Strategy             | Pros               | Cons                                |
| -------------------- | ------------------ | ----------------------------------- |
| Shared version tag   | Simple, consistent | All modules bump even if unchanged  |
| Independent semver   | Precise, flexible  | Complex, easy to get wrong          |
| Root-only versioning | Simple             | Sub-modules have ambiguous versions |

Wrong choice creates dependency hell for consumers.

### 5. Integration testing complexity

The `integration_test/` module already exists to test cross-module bridges. Every new module pair multiplies the test surface. The full middleware chain test we just wrote touches 6 modules — it needs to live somewhere that imports all of them.

### 6. The "god package" may actually be cohesive

Unlike typical god-packages with unrelated concerns, these 19 files form a **single integration layer**. `app.go` needs `errors.go` which needs `htmx.go` which needs `response.go`. They're all "HTMX-aware CQRS HTTP integration." The Unix question is: **is this one thing or eight?**

The go-modularize skill says: "Can you describe the module in one sentence? If not, the boundary is wrong." Our honest attempt: _"HTMX-aware CQRS HTTP integration with Casbin authorization, CSRF protection, rate limiting, security headers, request logging, panic recovery, branded ID context enrichment, and error mapping."_ That's eight things, not one.

## Previous Modularization Analysis

The go-modularize session on 2026-05-27 concluded:

> "Root module is intentionally a single flat package. 19 files form a cohesive 'HTMX-aware CQRS HTTP integration' library. The errors↔response↔csrf cycle prevents further splitting. Sub-package extraction would harm consumer UX."

**This conclusion was wrong** because:

1. The "cycle" is not an import cycle — it's shared constants in one package that would be clean one-way imports when split
2. "Cohesive" is overstated — 5 of 19 files have zero internal dependencies
3. Consumer UX argument ignores consumers who only need parts of the library

The analysis is preserved in `docs/modularization/PROPOSAL.md` and `docs/modularization/DEPENDENCY_GRAPH.md`.
