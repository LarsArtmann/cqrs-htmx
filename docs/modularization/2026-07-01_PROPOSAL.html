The Confirmed Cycle: errors ↔ response ↔ csrf

Three edges form an inseparable triangle:

  1. errors.go → response.go: uses ContentTypePlain, ContentTypeJSON, ContentTypeProblem, JSONKeyError, JSONKeyStatus
  2. response.go → csrf_config.go: uses defaultCSRFHeaderName (line 174)
  3. csrf_config.go → errors.go: uses ErrForbidden (line 38), ErrCSRFConfig, ErrorHandler type

Additionally: Core ↔ Errors bidirectional (sentinels flow both ways), Core ↔ SSE bidirectional (notification types in response.go, HandlerOption in notify.go). Six of eleven clusters participate in cycles. Extraction of any single cluster is impossible without first breaking the cycle through refactoring.

Verdict: KEEP ROOT AS-IS

Three reasons:

  1. The cycle blocks it. Breaking the errors/response/csrf triangle requires moving ContentType constants, CSRF header names, and sentinel errors to neutral locations. The refactoring cost exceeds the benefit for a library where these concerns are genuinely co-dependent.
  2. Consumer UX is a feature. The library is called "cqrs-htmx." Consumers expect import cqrshtmx "..." and get everything. Sub-package imports (cqrshtmx/ratelimit, cqrshtmx/sse) would be hostile UX.
  3. Leaf clusters are too small. Rate limiting (2 files, 361 LOC) and HTMX serving (3 files, 265 LOC) don't justify separate modules. No composability payoff: no consumer uses rate limiting without the CQRS handler.

Critical Finding

Transitive Dependency Bloat

usermgmt/service_core.go:44-72 (Service struct)

The Service struct directly holds webauthn *webauthn.WebAuthn and oauth2Providers map[string]*oauth2Provider. This means every consumer of usermgmt transitively pulls in:

  • github.com/go-webauthn/webauthn (+ go-webauthn/x, go-tpm, cbor, msgp)
  • golang.org/x/oauth2
  • github.com/coreos/go-oidc/v3 (+ go-jose, golang-jwt)
  • github.com/pquerna/otp (+ boombuler/barcode)
  • modernc.org/sqlite (+ libc, mathutil, memory — ~15 MB of CGO-free SQLite)

A consumer who wants only user registration + role management + sessions gets all five heavy dependency trees whether they use those features or not. This is Go module failure mode FM#2: Transitive dep bloat.

Root cause: The Service struct is a God object (30+ fields, 9 service_*.go files are methods on it). Auth implementations are wired directly as concrete types, not interfaces.
Important Finding

Pure Domain Layer is Trapped Inside

usermgmt/es_*.go (31 files, ~3,200 LOC)

The event-sourcing domain layer (4 aggregates: User, Bot, Membership, Tenant) has zero infrastructure dependencies. The foldUser(), foldMembership(), foldTenant(), foldBot() functions and all decide*() functions are pure domain logic depending only on go-cqrs-lite and domain value types.

This clean seam is trapped inside the god-package. A consumer who wants to test or reuse just the domain logic must import the entire usermgmt package — dragging in WebAuthn, OAuth2, SQLite, and Casbin.

The Clean Seams (if refactoring is pursued)

  1. WebAuthn (4 files): go-webauthn import localized to webauthn_adapter.go + webauthn_service.go. Clean isolation boundary.
  2. OAuth2 (2 files): oauth2/go-oidc confined to oauth2.go. Provider discovery/exchange is self-contained.
  3. TOTP (2 files): pquerna/otp in totp.go only. TOTPConfig is a plain struct (Issuer, Window) with no otp-lib types.
  4. SQL persistence (5 files): database/sql + modernc/sqlite behind sql_*.go. Session store is completely independent of event store.

Each of these could become a sub-package that isolates its heavy dep. Consumers who don't import the sub-package don't pull the dep.

04The Unix Pipe Test

The Unix philosophy test for modules: "Does each module do one thing well? Can consumers compose it with other modules like Unix pipes — importing only what they need?"

usermgmt Fails the Pipe Test — But With Caveats

The failure is real but nuanced. WebAuthn, OAuth2, and TOTP are not separate domains — they're authentication strategies for the same domain (user management). The question is decomposition depth, not domain count:

  • Right depth: One module for user management (domain cohesion)
  • Wrong depth: Bundling all auth implementations in the core package, forcing their deps on all consumers

The fix is sub-package isolation within the same module — not splitting usermgmt into separate modules. This preserves domain cohesion while eliminating dep bloat.

Immediate Hygiene Fixes (Safe, Non-Breaking)

v0.0.0 Version Normalization

Internal module references use real versions (v3.3.0, v3.0.0) instead of v0.0.0. Since replace directives make the version irrelevant for resolution, v0.0.0 eliminates pseudo-version churn (e.g., v0.0.0-20240115120000-abcdef123456) that pollutes every go mod tidy and PR diff.

Affected modules: usermgmt, adminui, integration_test, admin-demo, basic

Future: usermgmt Sub-Package Extraction (Debt Plan)

Not executed in this review. This is a major architectural refactoring with breaking API changes to a published v3 library. Documented as a plan for future work.

The proposed target structure (future, not now):

usermgmt/ # ONE module — domain cohesion preserved ├── *.go # core: domain types, ES domain, service, HTTP ├── webauthn/ # sub-package: go-webauthn isolated here ├── oauth2/ # sub-package: oauth2/oidc/go-jose isolated ├── totp/ # sub-package: pquerna/otp isolated └── sql/ # sub-package: database/sql + modernc/sqlite isolated

This requires the Service struct to use interfaces for auth concerns instead of concrete types. The WebAuthn/OAuth2/TOTP implementations would register as plugins implementing those interfaces. Consumers who don't import the sub-packages don't get the deps. This is the Unix pipe model applied within a single module.
