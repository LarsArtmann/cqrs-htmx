01The go-cqrs-lite Layer Reference

go-cqrs-lite is the authoritative reference for Unix-style module decomposition in this ecosystem. It has 54 Go modules organized into 8 CI-enforced layers. Every module does one thing well. Every module composes like a Unix pipe. The layering is authoritative — defined in scripts/check-module-layers.sh and enforced in CI.

The 8-Layer Model (CI-Enforced)

Layer 0 — Leaf primitives (zero go-cqrs-lite deps)
id/ · dispatcher/ · codec/ · kv/
Layer 1 — Domain types & interfaces
event/ · command/ · query/ · scheduling/
Layer 2 — Domain services
schema/ · snapshot/ · projection/ · idempotency/ · deriver/
Layer 3 — Aggregate orchestration
decider/ · graph/ · scenario/ · projectionhost/
Layer 4 — Infrastructure primitives
storage/memory/ · signing/ · encryption/ · otel/
Layer 5 — Adapters & implementations
storage/ · watermill/ · middleware/ · listing/ · transport/http/ · transport/grpc/ · prometheus/ · storage/pebble/ · storage/turso/
Layer 6 — Composition presets (bundler layer)
stack/ · stack/memory/ · stack/sqlite/ · stack/postgres/ · stack/pebble/ · stack/turso/
Layer 7 — Top-level integration
catalog/ · integration/ · stack/bench/

The Unix Principle Embodied

Each go-cqrs-lite module is a pipe. event/ defines what an event IS. storage/ defines how events are STORED. stack/sqlite/ wires them together. A consumer picks modules from each layer and composes them in main.go — exactly like piping grep | sort | uniq. No module reaches across layers. No module bundles unrelated concerns.

Dependency Budgets (CI-Enforced)

Every module has a maximum production dependency budget. New deps require explicit review. This is the mechanism that prevents god-modules from forming.

Module Layer Budget Unix Lesson
dispatcher/ 0 0 deps Pure interface — nothing else needed
id/ 0 3 deps Identifiers are a leaf concern
projection/ 2 2 deps Replay logic needs only event + id
decider/ 3 10 deps Orchestration is allowed broader reach
stack/ 6 13 deps Composition presets bundle by design
integration/ 7 21 deps Test suites are allowed the most

usermgmt has NO budget — and it shows

usermgmt has ~30 direct/indirect production dependencies. If it had a budget (which it should), it would be flagged immediately. For comparison: go-cqrs-lite's decider/ (L3, the orchestration layer) has a budget of 10. usermgmt — which is conceptually at the same layer — has 3× that.

04Root Module: Keep As-Is

46 production files in one flat package cqrshtmx. The prior proposal (2026-05-27) concluded "don't split" when there were 19 files. File count has since grown 2.4× — but the analysis still holds. Here's why, through the Unix philosophy lens:

Unix Principle: "Do one thing well"

The root module's one thing: "HTMX-aware CQRS HTTP handler integration with auth, CSRF, and real-time." The 46 files are all facets of this single concern. SSE, WebSocket, rate limiting, server timing — these aren't separate domains; they're transport mechanisms for the same CQRS-over-HTTP integration.

The Cycle That Blocks Extraction

Three edges form an inseparable triangle that prevents any cluster from being extracted:

  1. errors.go → response.go: ContentTypePlain/JSON/Problem, JSONKeyError/Status
  2. response.go → csrf_config.go: defaultCSRFHeaderName (line 174)
  3. csrf_config.go → errors.go: ErrForbidden (line 38), ErrCSRFConfig, ErrorHandler

Additionally: Core ↔ Errors bidirectional. Core ↔ SSE bidirectional. Six of eleven clusters participate in cycles. The flat package IS the correct boundary.

Consumer UX is a feature, not a bug

The library is called "cqrs-htmx." Consumers expect import cqrshtmx "..." and get everything. Sub-package imports (cqrshtmx/sse, cqrshtmx/ratelimit) would be hostile UX with zero composability payoff: no consumer uses SSE without the CQRS handler. The leaf clusters (rate limiting: 2 files, 361 LOC; HTMX serving: 3 files, 265 LOC) are too small for separate modules.

The Layer Violation

go-cqrs-lite would never put storage/ (L5), stack/sqlite/ (L6), and decider/ (L3) in the same module. It would never put signing/ (L4) and event/ (L1) in the same module. Yet usermgmt does exactly this: domain logic, SQL persistence, stack presets, and auth implementations are all in one package usermgmt.

If usermgmt had go-cqrs-lite's CI layer enforcement, it would fail immediately. The "module" is doing 6 things, not 1.

Critical

Transitive Dependency Bloat (FM#2)

usermgmt/service_core.go:44-72 (Service struct)

The Service struct directly holds concrete types from 5 heavy libraries:

  • webauthn *webauthn.WebAuthn → go-webauthn + go-tpm + cbor + msgp
  • oauth2Providers map[string]*oauth2Provider → oauth2 + go-oidc + go-jose
  • totpConfig *TOTPConfig → pquerna/otp + barcode
  • SQL stores → modernc/sqlite + libc + mathutil (~15 MB)
  • Casbin → casbin/v3 + govaluate

A consumer who wants only user registration + roles + sessions gets all 5 dep trees. In go-cqrs-lite, a consumer who wants only decider/ imports decider/ and gets exactly 10 deps — no SQLite, no signing, no encryption unless they opt in.

Important

Pure Domain Layer Trapped Inside

usermgmt/es_*.go (31 files, ~3,200 LOC)

The event-sourcing domain layer (fold/decide for 4 aggregates) has zero infrastructure deps. It depends only on go-cqrs-lite + domain value types. This is exactly what go-cqrs-lite's L1-L3 modules provide. But it's trapped inside the god-package — testing or reusing just the domain logic forces importing WebAuthn, OAuth2, SQLite, and Casbin.

go-cqrs-lite's example/user/ demonstrates the right pattern: it's a main package (an application) that composes 14 go-cqrs-lite modules. It doesn't bundle them — it wires them in main.go. usermgmt should evolve toward this composition model.

What go-cqrs-lite's example/user Teaches Us

84 files, 1 package.
Domain types + SQL + WebAuthn + OAuth2 + TOTP + HTTP + Casbin all in package usermgmt. Service struct is a composition root that also owns domain logic. Consumer gets everything whether they want it or not.

example/user pattern (target)

Domain types in separate files. Infrastructure wired in main.go. Consumer picks decider/ + storage/sqlite/ + watermill/ and composes. No bundling. No forced deps.

The Fix Is Not Splitting Modules — It's Sub-Package Isolation

WebAuthn, OAuth2, and TOTP are not separate domains — they're authentication strategies for the same domain (user management). The decomposition error is depth, not domain count:

  • Right depth: One module for user management (domain cohesion)
  • Wrong depth: Bundling all auth implementations as concrete types in the core package

The fix mirrors go-cqrs-lite's pattern: storage/memory/, storage/pebble/, storage/turso/ are sub-modules that each isolate their heavy dep. Consumers import only the storage backend they need. usermgmt should do the same with auth backends.

07Missing CI Enforcement

This is the highest-leverage improvement available. go-cqrs-lite has 5 CI scripts that prevent exactly the kind of degradation usermgmt experienced. cqrs-htmx has zero. Without enforcement, layer violations accumulate silently — exactly what happened as usermgmt grew from 9 to 84 files.

What go-cqrs-lite Enforces (That We Don't)

CI Script What It Catches go-cqrs-lite cqrs-htmx
check-module-layers.sh Module depends on higher layer YES NO
Dependency budgets Module exceeds max production deps YES NO
check-module-isolation.sh Module fails GOWORK=off build YES NO
check-version-drift.sh Siblings at different versions YES NO
check-replace-directives.sh Absolute paths, missing replaces YES NO
Key insight: go-cqrs-lite didn't prevent god-modules by being smarter — it prevented them by adding a CI script that fails the build when a module exceeds its dependency budget or depends on a higher layer. The mechanism is a shell script, not good intentions.

Honest Assessment

The v1 review (earlier today) identified the usermgmt god-package as "dep bloat." The v2 review, informed by go-cqrs-lite's layer model, reframes it more precisely: usermgmt is a layer violation. It bundles L1-L6 concepts in one package, something go-cqrs-lite would never allow. The ECOSYSTEM_BOUNDARIES contract ("depend only on go-cqrs-lite") is broken by 7 heavy external deps.

The real gap isn't the god-package itself — it's the missing CI enforcement that allowed it to form. go-cqrs-lite prevents this degradation with shell scripts that fail the build. Adding equivalent scripts to cqrs-htmx is the highest-leverage improvement: it prevents future layer violations and creates a forcing function for the v4 sub-package extraction.

The root module's flat package is confirmed correct by the Unix principle: it does one thing well (HTMX-aware CQRS HTTP integration), and the errors→response→csrf cycle makes it structurally indivisible. Consumer UX (one import) is the right contract for a library at this layer.
