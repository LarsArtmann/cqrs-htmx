Classification: Clean Workspace Mode

The project is in clean workspace mode. go.work coordinates all 7 modules. No replace directives in go.work. Replace directives in integration_test/go.mod and examples are correct (needed for GOWORK=off CI builds). The cross-module DAG is acyclic with zero mutual imports between root and usermgmt.

The core problem is NOT module boundaries — it's the god-PACKAGE inside usermgmt The 2026-05-27 proposal concluded "do not split root" based on 19 root files. Root has since grown to 40 files but remains a cohesive "HTMX-aware CQRS HTTP integration" library. However, usermgmt exploded from 9 → 71 production files. A single Go package now hosts 4 event-sourced aggregates (User, Bot, Membership, Tenant), 5 authentication subsystems (WebAuthn, OAuth2/OIDC, TOTP, email verification, sessions), Casbin authorization, SQL stores, HTTP handlers, and import/export. This violates the Unix principle: "do one thing well."

03Proposed Structure

Recommendation: Package-level decomposition, NOT module splitting Keep usermgmt as a single Go module (preserves consumer UX: one go get). Decompose the internal structure into sub-packages with a root facade. This addresses the god-package problem without breaking import paths or adding versioning complexity. Dependency isolation via sub-modules is documented as a future option driven by consumer demand.

04DAG Verification

The proposed structure forms a clean directed acyclic graph:

domain/          ← zero internal deps (foundation)
    ↑
eventsource/     ← depends on domain/ only
    ↑
authz/           ← depends on domain/ only (CasbinProjection → eventsource events)
store/           ← depends on domain/ only
webauthn/        ← depends on domain/ only
oauth2/          ← depends on domain/ only
totp/            ← depends on domain/ only
    ↑
usermgmt (root)  ← facade: embeds/composes webauthn, oauth2, totp services
    ↑
httpapi/         ← depends on usermgmt Service + all sub-packages

No cycles. Every arrow points "downward" toward domain/. The facade pattern ensures the Service struct can delegate to subsystems without creating upward dependencies.

07Breaking Change Analysis

Package decomposition with backward-compatible facade

The root usermgmt package will re-export all public types and functions from sub-packages. Consumers who import usermgmt.Service, usermgmt.UserID, usermgmt.NewService etc. will see zero changes. Only consumers who reach into internal file structure (which doesn't exist as packages today — it's all one flat package) would be affected, and that's not possible since there are no sub-packages today.

Symbol Category Current Import Path After Decomposition Breaking?
Service, NewService, ServiceConfig usermgmt usermgmt (facade re-exports) No
UserID, User, Session, Email usermgmt usermgmt (type aliases) No
AuthHandler, routes usermgmt usermgmt (re-exports) No
RegisterCommands, EventSourcedConfig usermgmt usermgmt (re-exports) No
Internal types (foldUser, decide*) Not exported Move to eventsource/ No (already unexported)

08Migration Strategy

1

Extract domain/ package (Tier 1 — foundational)

Move user.go, id.go, email.go, credential.go, external_account.go, domain errors into usermgmt/domain/. Add type aliases in root usermgmt package for backward compat. Verify: go build ./... + go test ./... pass.

2

Extract authz/ package (Tier 1)

Move authz_types.go, authz_policies.go, authz_roles.go into usermgmt/authz/. Depends on domain/ only. Re-export Authz, AsEnforcer from root.

3

Extract store/ package (Tier 2)

Move store.go, sql_session_store.go, sql_event_store.go into usermgmt/store/. Depends on domain/ only.

4

Extract eventsource/ package (Tier 2 — largest)

Move all es_*.go files (35 files across 4 aggregates) into usermgmt/eventsource/ with sub-directories per aggregate. Depends on domain/ + authz/. Re-export RegisterCommands, EventSourcedConfig, StartProjections.

5

Extract webauthn/, oauth2/, totp/ packages (Tier 3)

Each subsystem into its own package. The Service struct embeds each subsystem's service. Methods are promoted via embedding (preserves flat API) or delegated via wrapper methods.

6

Extract httpapi/ + internal/ (Tier 4 — polish)

Move HTTP handlers into usermgmt/httpapi/. Move crypto.go, random.go, eviction.go into usermgmt/internal/. Update flake.nix per-module apps if needed.

7

Update documentation (Tier 4)

Update AGENTS.md file listing, docs/modularization/DEPENDENCY_GRAPH.md, and add an ADR for the package decomposition decision.

09Risk Assessment

# Risk Likelihood Mitigation
1 Service struct embedding breaks method resolution (ambiguity) Low Each subsystem service has distinct method names. Test via go build after each step.
2 CasbinProjection depends on event types from eventsource/ — circular if authz/ imports eventsource/ Medium Keep CasbinProjection in eventsource/ (it's a projection, not authz core). Authz/ defines the interface; eventsource/ implements the projection.
3 Re-export type aliases don't preserve method sets Low Use type UserID = domain.UserID (type alias, not type definition). Aliases preserve method sets.
4 Consumer reaches into usermgmt internal types that move Low Current flat package has no sub-packages. Moving unexported types is safe.
5 Build system (flake.nix) breaks on new package paths Low flake.nix uses go test ./... (pattern match). No path-specific logic.
6 Test files reference types that moved Medium Test files stay in root package; they use re-exported types. go test resolves via aliases.

10Build System Impact

flake.nix: No changes needed. The nix apps use go test ./... and go build ./... which automatically discover new packages. The per-module GOWORK=off apps are unaffected — package decomposition is within the usermgmt module.

CI: No changes. The module count stays at 7. The go.work file is unchanged.

Lint: golangci-lint run uses ./... pattern. New packages are automatically included.

13Coupling Analysis — Symbol-Level

Since all files are in one Go package today, coupling is through symbol usage (not imports). This analysis maps which subsystems reference symbols from other subsystems.

From → domain authz store eventsource webauthn oauth2 totp
domain — 0 0 0 0 0 0
authz uses — 0 0 0 0 0
store uses 0 — 0 0 0 0
eventsource uses uses* 0 — 0 0 0
webauthn uses 0 0 0 — 0 0
oauth2 uses 0 0 0 0 — 0
totp uses 0 0 0 0 0 —

* eventsource → authz: CasbinProjection calls authz.AddRoleForUser, authz.RemoveAllRolesForUser. This is the ONLY cross-subsystem dependency beyond domain/. It means CasbinProjection must live in eventsource/ (which depends on authz/), not in authz/ (which must not depend on event types).

The coupling graph is nearly perfectly layered. All subsystems depend on domain/ only. The one exception (eventsource → authz for CasbinProjection) is a clean one-way dependency. WebAuthn, OAuth2, and TOTP are completely independent of each other — they could be extracted as separate modules in Phase 2 with zero refactoring.

14Alternative Approaches Comparison

Criterion Status Quo Package Decomposition (proposed) Sub-Module Extraction
Consumer breakage None None (type aliases) High (import path changes)
God-package fix 71 files, 8 concerns 8 packages, max ~15 files each Same + module isolation
Dependency isolation go-webauthn pulled by all Same module = same go.mod Per-module go.mod
CI parallelization 1 test run 1 test run (same module) N parallel test runs
Versioning complexity 1 version tag 1 version tag N tags per release
Effort 0 ~4-6 hours ~2-3 days + consumer migration
Reversibility — Trivial (merge packages) Hard (consumer migration)
Decision: Package decomposition now, sub-module extraction later. The proposed approach fixes the god-package (the real problem) with zero consumer breakage and full reversibility. Sub-module extraction becomes trivial AFTER decomposition — the clean package boundaries are the prerequisite. Extract modules only when consumer demand for dependency isolation materializes.

15Self-Review Refinements (Phase 4)

Critical evaluation against the go-modularize checklist. Five gaps identified and addressed:

# Question Finding Resolution
1 What about test files? 74 test files in usermgmt — placement unclear Tests co-locate with sub-packages (domain/user_test.go). Root Service tests stay in root package.
2 Where does import_export.go go? Cross-cutting: uses Service + HTTP + file I/O httpapi/import_export.go. Validation (ImportUser.Validate) moves to domain/.
3 Where does events.go bridge go? Backward-compat callback bridging bus → consumer Stays in root package — bridges Service to external callbacks.
4 Embedding method ambiguity? Service embeds 3+ subsystem services Not a risk. Each subsystem has distinct method names. Verified: zero collisions across 71 files.
5 Is eventsource/ (35 files) too coarse? 4 aggregates + infrastructure Sub-directories: eventsource/user/, bot/, membership/, tenant/. Shared infra stays in root.
Verdict: Proposal stands. No fundamental flaws. The 5 refinements are clarifications, not redesigns.

Phase 2 (Future, Opt-in): Dependency Isolation via Sub-modules

If consumer feedback shows dependency overreach (e.g., "I only want basic user management but get go-webauthn + go-oidc + pquerna/otp"), extract webauthn/, oauth2/, totp/ as independent sub-modules: 

usermgmt-webauthn/    → go.mod depends on go-webauthn
usermgmt-oauth2/      → go.mod depends on x/oauth2 + go-oidc
usermgmt-totp/        → go.mod depends on pquerna/otp

This gives true dependency isolation: consumers who don't need WebAuthn don't pull in go-webauthn. But this should be driven by real demand, not premature modularization. The package decomposition in this proposal is the prerequisite — it creates the clean seams that make future module extraction trivial.
