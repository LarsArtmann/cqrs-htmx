# go-cqrs-lite v3.1.0 Adoption Opportunities

> Created 2026-06-25 after upgrading all 7 modules from v3.0.0 → v3.1.0.
> v3.1.0 is a feature release with zero breaking changes (+69 API exports).

## Status: Version Bump Complete, Feature Adoption Pending

The version bump itself is done — all `go.mod` files declare `v3.1.0`, all tests
pass, lint is clean. This document tracks the **real feature adoption
opportunities** that require architectural work beyond a dependency upgrade.

## Opportunities Sorted by Impact / Effort

### 1. SQL-Backed Read Models (HIGH impact, HIGH effort)

**Current state**: All 4 usermgmt read models (`UserReadModel`,
`MembershipReadModel`, `TenantReadModel`, `BotReadModel`) are pure in-memory
`map + sync.RWMutex` projections. Data is lost on restart.

**v3.1.0 enables**: `storage.SQLViewStore` + `ViewMapper[V]` + `AutoMapper`
provide SQL-backed `kv.ViewStore` with:
- Column-mapped views via struct tags (`view:"col_name"`)
- Server-side WHERE/ORDER BY/LIMIT/OFFSET (`ViewQuerier`)
- O(1) counting (`ViewCounter`)
- Chunked batch upsert (`ViewBatchSetter`, SQLite 999-param aware)
- Tombstone column for soft-delete filtering (`TombstoneQuerier`)

**Migration path**:
1. Add `view:"..."` struct tags to `User`, `Membership`, `Tenant`, `Bot` types
2. Generate `ViewMapper` via `storage.AutoMapper[V](tableName)`
3. Create `storage.NewSQLiteViewStore` / `NewSQLViewStore` in `ServiceConfig`
4. Wrap read models to delegate to `kv.ViewStore` instead of in-memory maps
5. OR: adopt `stack.Materialize[V,K]` for automatic projection handling

**Blocker**: Requires restructuring all 4 read models. The current
`event.Projection` interface (Name/Handle/EventTypes) would either coexist with
or be replaced by `stack.Materialize.HandlerFunc()`.

**Dependency**: Needs `storage/v3` (already a dep) and potentially `stack/v3`
(not currently imported by usermgmt).

---

### 2. Stack Preset Adoption (HIGH impact, HIGH effort)

**Current state**: usermgmt hand-wires its own event store + bus + projection
setup in `es_setup.go` (~130 LOC) and `es_projection_setup.go` (~140 LOC).

**v3.1.0 enables**: `stack/memory.New()`, `stack/sqlite.New(dsn)`,
`stack/postgres.New(dsn)` wire everything in one call:
- Event store + bus + command/query/snapshot/checkpoint stores
- Read-model KV store (`Bundle.ReadModels`)
- `CatchUpSubscriber` for replay+live projection with automatic dedup
- `Materialize[V,K]` for declarative projection handling
- `GracefulClose(ctx)` for production shutdown
- Multi-DB split (`WithEventDB`/`WithQueryDB`/`WithViewDB`)

**Migration path** (per upstream `docs/MIGRATION_TO_STACK.md`):
1. Replace manual event store creation with stack preset
2. Replace manual journal replay + `bus.SubscribeAll` with `CatchUpSubscriber`
3. Replace manual projection handling with `stack.Materialize`
4. Use `stack.Repository[State]` instead of `decider.NewRepository` directly

**Blocker**: Would change `ServiceConfig`/`EventSourcedConfig` public API.
The `SecurityHooks` (StoreWrapper, PublishMiddleware, HandlerMiddleware) need
rethinking — they wrap individual infra components that a Bundle would own.

**Risk**: The `SecurityHooks` pattern is the main integration point for
signing/encryption. Stack presets don't expose the same injection points.

---

### 3. `closeBus` Cleanup Pattern (LOW impact, LOW effort)

**Current state**: `es_setup.go:87-94` — `closeBus(bus)` type-asserts to
`io.Closer` and calls `Close()`. Called at 7 error-return sites.

**v3.1.0 enables**: `stack.MultiCloser` / `stack.FuncCloser` for structured
cleanup. But importing `stack/v3` just for closer helpers isn't worth the
dependency.

**Verdict**: Not worth it. The current pattern is correct and clear.

---

### 4. SQLite WAL Tuning (MEDIUM impact, LOW effort)

**Current state**: `SQLSessionStore` and `SQLEventStore` (alias over upstream)
manage their own connections.

**v3.1.0 enables**: `synchronous=NORMAL` in WAL mode gives 3-10x better write
throughput without durability loss (safe with WAL).

**Migration path**: Add `PRAGMA synchronous=NORMAL` after enabling WAL in
`SQLSessionStore.Open()`.

**Blocker**: `SQLEventStore` delegates to upstream — the tuning is already
applied there. Only `SQLSessionStore` (which manages its own schema) would
benefit.

---

### 5. Typed Command/Query Metadata (LOW impact, LOW effort)

**Current state**: We don't use `command.Metadata` or `query.Metadata` at all.
Our `MetadataKeyActorID`/`MetadataKeyImpersonatorID` constants write to **event**
metadata via `event.WithCustom()`.

**v3.1.0 enables**: `event.CustomData[K]` provides typed metadata keys for
command/query metadata (ADR-0031). Each module now owns its own `MetadataKey`
type.

**Verdict**: Not applicable. We'd need to start using command/query metadata
first, which isn't a current requirement.

## Deprecated APIs in v3.1.0 (None Affect Us)

| Deprecated API | Replacement | We use it? |
|---|---|---|
| `query.Handler` type alias | `TypedHandler[Q, R]` | No — we use our own `App.Query` |
| `event.WithReplay(ctx, bool)` | `WithProcessingMode(ModeReplay)` | No |
| `storage/sql.NewOwnedDBHandle(db, dialect, ownDB)` | `NewBorrowedDBHandle` / `NewOwningDBHandle` | No |
| `storage/sql.OwnedDBHandle.SetOwnership(bool)` | Construction-time ownership | No |
| `catalog.ErrorExporter` | `Exporter[error]` | No |
