## Scoring Methodology

Each task is ranked by a **Priority tier (P0–P9)** derived from four dimensions:

| Dimension          | Weight | Meaning (this is a library/SDK — "customer" = downstream developer)       |
| ------------------ | ------ | ------------------------------------------------------------------------- |
| **Importance**     | High   | Correctness/regression risk + unblocks other work. Bugs beat polish.      |
| **Impact**         | High   | How much the system improves (durability, perf, maintainability).         |
| **Effort**         | Gate   | Every task capped at **≤ 12 min**. Bigger items are split into sub-tasks. |
| **Customer value** | High   | Benefit to consumers importing cqrs-htmx (production-readiness wins).     |

**Priority tiers** (execution order):

| Tier | Theme                      | Why now                                                               |
| ---- | -------------------------- | --------------------------------------------------------------------- |
| P0   | Regression investigation   | Coverage drop is a correctness signal — resolve before declaring done |
| P1   | Quick wins (already built) | `OptimizeSQLiteDB` exists but is unwired — free performance           |
| P2   | Graceful shutdown          | Resource leaks today (bus/store/projections never closed)             |
| P3   | SQL-backed read models     | **Highest customer value** — data survives restart = production-ready |
| P4   | Stack preset adoption      | Removes ~270 LOC hand-wired infra; unlocks Materialize + CatchUp      |
| P5   | Postgres / scale           | Multi-DB split + LISTEN/NOTIFY for production deployments             |
| P6   | Read-model cache           | `kv.Cache` (Otter-backed) for hot-path reads                          |
| P7   | Typed metadata             | `event.CustomData[K]` for command/query metadata                      |
| P8   | CI / automation            | Errorfamily + coverage gates to prevent silent regressions            |
| P9   | Polish                     | Naming, doc hygiene, stale checksums                                  |

## Key De-risking Finding

The prior planning doc flagged stack-preset adoption as **BLOCKED by SecurityHooks**.
Upstream verification disproves this: `stack.Bundle` accepts
`WithEventStore(s event.Store)` and `WithBus(bus event.Bus)` options
(`stack/options.go:83,105`). This means **pre-wrapped stores/buses can be
injected into a Bundle** — SecurityHooks are preserved. The blocker is gone;
the work is re-scoped from "blocked" to "investigation spike + migration".

Verified real v3.1.0 APIs (all exist in upstream `~/projects/go-cqrs-lite/`):

- `stack.New(opts...)` → `*Bundle` with `Close()`, `GracefulClose(ctx)`, `Database()`, `CatchUpSubscriber()`
- `stack/sqlite.New(dsn, opts...)`, `WithOptimizations()`, `WithForeignKeys()`, `WithEventDB(dsn)`
- `stack.Materialize[V, K fmt.Stringer]{Store, KeyFromEvent, OnCreate, OnUpdate, OnTombstone...}`
- `Bundle.CatchUpSubscriber()` → replay+live+dedup subscriber (replaces manual journal replay)
- `stack.MultiCloser` / `stack.FuncCloser`
- `storage.SQLViewStore[V,K]`, `NewSQLiteViewStore[V,K]`, `AutoMapper[V](table)`, `AutoMapperWithTombstone[V](table,col)`
- `storage.SQLiteEnableWAL`, `storage.SQLiteApplyOptimizations`, `SQLiteInitSchema`
- `storage.PostgresBus` (LISTEN/NOTIFY)
- `event.CustomData[K]`, `event.MergeCustomMaps`

## Phase Details

### P0 — Regression Investigation (4 tasks, ~34 min)

**Goal**: Explain the usermgmt coverage drop (88.7% → 82.3%) before declaring the
upgrade complete. A 6.4pt drop with no code added is a red flag.

- **T01**: Run `go test ./... -coverprofile` in BOTH workspace mode and
  `GOWORK=off` for usermgmt. Compare totals. Determines if 82.3% is real or a
  measurement-boundary artifact.
- **T02**: `go tool cover -func` + `-html` to find the specific functions losing
  coverage. Look for new unexported code or dead branches.
- **T03**: `git log --since=<88.7% report date> -- usermgmt/` — enumerate added
  files / changed files. New untested files dilute the percentage.
- **T04**: Write the finding. If real drop → add tests (separate task). If
  artifact → document the correct measurement method.

### P1 — SQLite Optimization Wiring (6 tasks, ~42 min)

**Goal**: The `OptimizeSQLiteDB` helper is built and tested but **called nowhere**.
Wire it so tests/benchmarks run with production-like PRAGMAs and consumers see it
used in examples.

- **T05–T06**: Add `OptimizeSQLiteDB(ctx, db)` after `sql.Open` in test helper +
  benchmarks.
- **T07**: Audit integration_test (may have no SQLite — quick confirm).
- **T08**: Prove SQLSessionStore + SQLEventStore coexist on one WAL-tuned DB.
- **T09–T10**: Examples are what consumers copy — show them the call.

### P2 — Graceful Shutdown (7 tasks, ~66 min)

**Goal**: Today `Service.Stop()` only stops the eviction goroutine. The event bus
(GoChannel), projections, and stores are **never closed** — resource leak on
shutdown. v3.1.0 `stack.Bundle.GracefulClose(ctx)` + `MultiCloser` fix this.

- **T11**: Enumerate every closable resource the Service owns.
- **T12–T13**: `Close()` (immediate) + `GracefulClose(ctx)` (bounded).
- **T14**: `closeBus` (7 error sites doing `io.Closer` type-assert) → `MultiCloser`.
- **T15**: Test idempotency + `goleak`-style goroutine-leak check.
- **T16**: `EventSourcedSetup` owns store+bus → expose `Close()`.
- **T17**: Document lifecycle in AGENTS.md.

### P3 — SQL-Backed Read Models (21 tasks, ~200 min) — HIGHEST CUSTOMER VALUE

**Goal**: All 4 read models are in-memory maps — **data lost on restart**.
`storage.SQLViewStore[V,K]` + `AutoMapper[V]` make them persistent + queryable.
This is the single biggest production-readiness win.

Pattern per aggregate (User/Membership/Tenant/Bot):

1. Add `view:"col"` struct tags (or a `*View` DTO)
2. Verify key type implements `fmt.Stringer` (Materialize constraint)
3. Build `SQL*ReadModel` over `NewSQLiteViewStore[V,K]`
4. Migrate query methods to `kv.ViewQuery` DSL (WHERE/ORDER/LIMIT)
5. Tests (contract-style, like the session-store suite)
6. Wire into `ServiceConfig` (T36) + `es_setup.go` (T38)
7. Integration test: events → projection → restart → data survives (T37)

### P4 — Stack Preset Adoption (7 tasks, ~76 min)

**Goal**: Replace ~270 LOC of hand-wired infra (`es_setup.go` + `es_projection_setup.go`)
with `stack/sqlite.New(dsn)`. De-risked by the finding that `WithEventStore`/`WithBus`
preserve SecurityHooks.

- **T39**: Spike proving the injection works with wrapped store+bus.
- **T41**: `NewSQLiteEventSourcedSetup(dsn)` — new constructor, non-breaking.
- **T42**: `Bundle.CatchUpSubscriber()` replaces manual `journal.ReadAll` +
  `bus.SubscribeAll` + dedup (~140 LOC → ~5 LOC).
- **T43**: `stack.Materialize[V,K]` can replace the manual `Handle()` switches in
  read models (optional, evaluated after P3 ViewStore work).

### P5 — Postgres / Scale (4 tasks, ~42 min)

**Goal**: Production Postgres support via `stack/postgres.New` + multi-DB split
(I/O isolation) + optional `PostgresBus` (LISTEN/NOTIFY for multi-process).

### P6–P9 — Cache / Metadata / CI / Polish (10 tasks, ~80 min)

Low-risk, interleavable. Coverage gate (T55) directly prevents a repeat of the
P0 coverage-drop mystery.
